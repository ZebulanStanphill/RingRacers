# VibeRant Metal

VibeRant Metal runs the VibeRant driver (`src/hardware/r_viberant`) on Apple's Metal for hardware rendering on
macOS. It draws what VibeRant D3D and VibeRant Vulkan draw because they share driver code. As in VibeRant Vulkan
([vulkan-backend.md](vulkan-backend.md)), the driver calls Direct3D 12 and the backend implements the calls it uses.

macOS builds enable `SRB2_CONFIG_VIBERANT_METAL` by default, list **VibeRant Metal** in the Renderer setting, and
select it in a new config. The driver test passes on GitHub's virtual macOS GPU ("Apple Paravirtual device"), an
Apple M4 Pro, and an Intel Iris Plus Graphics 645 (`tests/README.md`, "Metal driver harness"). With Metal API and
shader validation enabled, the game played a replay on every map on the first two GPUs and on 89 maps on Intel
without validation reports. The captured frames matched VibeRant Vulkan within the differences between GPUs
("What was tested, and what wasn't").

Nobody was at the Macs during these tests: they ran unattended over the network, with both screens locked except
for part of the first day, and the screen pictures come from a runner. The owner has since played it by hand on the
MacBook Pro ("Not tested" says what that covered). See "What a person at a Mac should look at" for the remaining
visual checks.

## How

`src/hardware/r_viberant/metal/` implements `ID3D12Device` and the interfaces it creates in Objective-C++ on
Metal. It covers the same dozen interfaces and about 70 methods as vk12. `mtl12_bases.h`, generated by
`vulkan/gen_bases.py
--backend mtl12`, defines every method as "not implemented". mtl12 overrides the methods the driver calls and
logs any call it hasn't implemented.

On macOS, set `-DSRB2_CONFIG_VIBERANT_METAL=OFF` to build without the driver, as before. CMake rejects combining
Metal with Direct3D 12 or Vulkan through MoltenVK. The build defines `HAVE_VIBERANT_METAL` alongside
`HAVE_VIBERANT` ("the driver is built"), so `Core_Metal()` is a constant, true with `HAVE_VIBERANT_METAL`.
The project states CMake 3.14, but configuration stops below 3.16 for Metal because 3.16 introduced Objective-C++
support. The game's target enables automatic reference counting for its Objective-C++ files.

- **Device creation** (`viberant_core.cpp`). `rr_mtl12::CreateDevice` creates the system's default `MTLDevice`
  and its command queue. A program without a window that supplies no device gets the first device that isn't
  low-power.
- **Waiting for the GPU** (`Core_Wait`). mtl12's fence waits for Metal's command buffers without a Win32 event.
- **Shaders** (`viberant_pipeline.cpp`). Built-in shaders use Vulkan's SPIR-V headers (`r_vulkan_shaders/*.h`).
  Runtime shaders also reach mtl12 as SPIR-V (`D3DCompile` off Windows is `rr_spirv::CompileHlsl`). mtl12
  translates both to Metal Shading Language.
- **Root signature** (`r_viberant.cpp`). mtl12 builds in the `RR_ROOT_SIGNATURE` layout (`rr_spirv::kRoot`) and
  accepts a token in place of Direct3D's serialized signature.
- **Headers**. As on Linux, mtl12 uses Microsoft's DirectX-Headers and `vulkan/vk12_win.h`. Both that header and
  `spirv_shader.h` are independent of Vulkan.

Include Metal before Direct3D's declarations and include no Apple headers after them. Both define `BOOL` (a 32-bit
integer in Direct3D and a `bool` in Objective-C), and Microsoft's `interface` macro breaks `@interface`.
`mtl12_internal.h` renames Direct3D's `BOOL`. The public header, `mtl12.h`, is plain C++ and passes Metal objects
as `void *` so the driver's C++ files and a presenter can include it.

## Shaders

`rr_spirv::PatchShader` gives every input and output of a stage the location its HLSL semantic stands for, as for
Vulkan. `TranslateToMsl` (`mtl12_msl.cpp`, plain C++ around SPIRV-Cross) then writes the stage as Metal Shading
Language 2.1, with explicit indices for the registers:

| Register | SPIR-V binding | Metal index |
| --- | --- | --- |
| constant buffers `b0` to `b5` | 0 to 5 | buffer 0 to 5 |
| textures `t0` to `t10` | 16 to 26 | texture 0 to 10 |
| samplers `s0`, `s1` | 32, 33 | sampler 0, 1 |
| the vertex buffer | | buffer 30 |

Vertex attributes use their input locations (`POSITION` 0, `NORMAL` 1, `COLOR0` 2, `TEXCOORD0` 4, ...), and
stages link by location. glslang declares every register of `shaders.hlsl` in every stage. SPIRV-Cross identifies
which registers the Metal function reaches, but a function can still name a register its compiled code never
reads, such as an add-on shader's unused view constants. On macOS 13 and later, mtl12 uses reflection on the first
pipeline state for each pair of functions. Draws bind what Metal says the pipeline uses. Validation requires every
used resource to be bound and warns about unused buffer bindings.

`newLibraryWithSource` compiles the source with fast math disabled. Otherwise Metal's compiler assumes it can
reorder the arithmetic that must select the same palette entries and colormap rows as the other backends.

The driver makes hundreds of pipeline states from two dozen shaders, so mtl12 shares compiled functions by their
SPIR-V bytes. Pipeline states own the functions. The cache tracks each function only while a pipeline state uses
it. Built-in functions last as long as the device. An add-on shader's functions and cached SPIR-V leave when the
driver retires the last pipeline state using them, after replacement or unload. The cache is locked because
prewarming builds pipeline states on a worker thread.

## Mapping

| Direct3D 12 | mtl12 |
| --- | --- |
| clip space, viewport, depth range, winding | Same as Direct3D: y up in clip space, viewport origin at top left, depth 0 to 1, and front faces by screen winding. No flip (vk12 needs a viewport of negative height) |
| `SV_Position.w` in pixel shaders | Metal's fragment position has `1/w`, as OpenGL's does; glslang's `--hlsl-dx-position-w` already writes the reciprocal into the SPIR-V |
| the root signature: 6 root constant buffers, 11 tables of one texture, 2 tables of one sampler | the two functions’ argument tables at the indices above. A draw sets only changed bindings, or just the offset for an unchanged buffer |
| a root constant buffer named by GPU virtual address | a synthetic address range per buffer, resolved to a buffer and offset |
| descriptor heap slots | records of a texture or a sampler |
| views | a view of all of a texture's mips is the texture; one of fewer is a texture view the resource keeps. A view of another format than its texture's isn't implemented (the driver has none) |
| a null view | a 1x1 (or 1x1x1) texture of the view's format, written as zero by a command buffer of its own when it is made: a submission like the driver's, so fences wait for it and its failure is the device's. If it can't be set up, the view is left empty (a draw that needs it is skipped, with a line in the log) and the next null view of that kind tries again |
| resource states and `ResourceBarrier` | nothing: Metal tracks what textures are used for. A target that stops being one ends its pass |
| `OMSetRenderTargets`, draws | a render pass that loads and stores everything, begun at the first draw after the targets are set and ended by whatever can't be in one (a copy, a clear, other targets). One color target, and a depth target of its size (the driver's always are) |
| `ClearRenderTargetView`, `ClearDepthStencilView` | the load action of the next pass on that target. If the target is used otherwise first (copied, handed to a shader, the list closed), a pass of its own with no draws. Only whole targets: a clear of rectangles isn't implemented (the driver has none) |
| one pipeline state for any targets | a Metal render pipeline state per formats of the targets, the description's own made with the object, so that the driver's prewarming still compiles ahead of time. Lists, strips, and lines are a draw's argument in Metal |
| depth and stencil tests in the pipeline state | an `MTLDepthStencilState` made with it; a pass without a depth target gets one that tests nothing |
| cull mode, winding, depth bias, depth clip, stencil reference, blend factor, viewport, scissor | set on the encoder, when they differ from what it has. The scissor rectangle is cut to the targets, and a draw with an empty one is skipped, since Metal accepts neither |
| vertex buffers | buffer index 30, with the stride of the input layout |
| copies | consecutive copies share a blit encoder |
| committed and placed resources, heaps | every resource is a Metal texture or buffer of its own. A heap holds no memory: the driver's 16 MB texture heaps and its offsets into them are bookkeeping here, checked for fit only. `GetResourceAllocationInfo` reports the texels' size in Direct3D's 4 KB or 64 KB class |
| upload and readback heaps, `Map` | buffers in shared storage, mapped for life; other buffers and all textures are private to the GPU |
| command allocators | a list takes a command buffer from the queue on each reset |
| fences, `Signal`, waits | a value that completes with the last command buffer of the submission it was signaled after |

| autorelease pools | the driver's thread is the game's main loop, which is C++ and has none, so every call of mtl12's and the presenter's that can autorelease brings its own, the destructors included: a Metal texture or buffer autoreleases its device as it is deallocated |

## The window

The Metal presenter (`metal/mtl_present.mm`) replaces the game's OpenGL window with a similar Metal window, as
Vulkan does ([vulkan-backend.md](vulkan-backend.md), "The window"). It creates the second window with
`SDL_WINDOW_METAL`, SDL's Metal view, and its `CAMetalLayer`, hides the first, and sets `sdlmain.h`'s `window`
to the second. The video code uses that window for sizing, fullscreen, and input. When Software takes over, the
OpenGL window returns in the Metal window's state and shows Software's frames.

Startup shows only one window. The OpenGL window starts hidden and `I_ShowDeferredWindow` shows it only when a
renderer that uses it takes over. On quit with VibeRant Metal, the presenter closes the Metal window and leaves
the OpenGL window hidden for the video system to destroy. Previously it restored the OpenGL window as for
Software, briefly showing an empty window that, in fullscreen, could be on its way into its own Space. The
presenter's last log line reports SDL's state for the OpenGL window. It reads "closed the Metal window as the game quits; the
game's OpenGL window is hidden".

- **Size.** The layer's drawables are the size of the window's content in points, not in the display's pixels: the
  game's window isn't a high-resolution one (it is made without `SDL_WINDOW_ALLOW_HIGHDPI`), so on a Retina display
  the system scales the frame up, as it does Software's and Legacy GL's. SDL's view keeps the drawable size at the
  window's as the window changes, and the presenter takes each drawable's own size as the size to place the frame in.
  The presenter logs each new size: "1280x720 drawables for a window of 1280x720 points on a display with 2 pixels
  per point (the system scales the frame up) and 60 frames per second". On that MacBook Pro, the 2560x1600 panel
  defaults to looking like 1440x900. In fullscreen the system doubles the 1440x900 drawable to its 2880x1800
  backing, then fits it to the panel. Even drawables sized in pixels couldn't make the picture pixel-sharp on
  that scaled display. At one pixel per point, as on the Mac mini's 1920x1080 monitor, the drawable matches the
  screen's pixels.

  Software's frames there are the same size. Without `SDL_WINDOW_ALLOW_HIGHDPI`, SDL disables
  `wantsBestResolutionOpenGLSurface`. Apple says this view "uses a 1 pixel per point framebuffer regardless of
  the backing scale factor" and that "the rendered surface contents are also magnified". Both renderers supply
  frames in points for the system to magnify, so VibeRant Metal is no sharper than Software, as intended.
  The presenter leaves the layer's default linear `magnificationFilter`. Apple's documentation doesn't specify
  the filter for OpenGL surfaces, so check a Retina display to see whether they look identical.
- **Placement.** As on other desktop presenters, the driver draws into Screen Scaling's Integer or 1:1
  rectangle, or uses linear filtering to fill the largest rectangle of the frame's aspect ratio. The BGRA8 drawable
  is render-target-only (`framebufferOnly`), so the driver draws into it. A copy from the RGBA8 screen wouldn't work.
- **Colors.** The drawable uses `BGRA8Unorm`, which stores the frame values without an sRGB conversion.
  `MatchWindowColors` ensures the `CAMetalLayer` has its window's color space so the display treats the frame like
  Software's OpenGL frame. Since SDL 2.26, SDL gives every window it creates sRGB (the SDL commit says OpenGL
  "was getting a much more saturated colorspace" before). The system matches OpenGL output from sRGB to the display.
  Apple says content on a layer without a color space "isn't color-matched", so the same Metal frame would look
  more saturated than Software's on a display wider than sRGB, such as a MacBook's P3 panel.
  On both Macs the system had
  already given the layer the window's color space when the presenter looked (macOS 27 and macOS 15.8, SDL 2.30.9),
  so nothing changed there, and the log says which it was: "colors are matched to the display as the OpenGL window's
  are: the layer has its window's color space, "sRGB IEC61966-2.1" (the system gave it), and the display's is "Color
  LCD"" on the MacBook, whose panel is the wide-gamut one, and the same with a display that is itself "sRGB
  IEC61966-2.1" on the Mac mini. Taking the layer's color space away on purpose and letting the presenter set it
  gives the same line with "set here". So the earlier sentence here, that the layer had no color space and showed
  the frame's values as they were, was wrong about the layer, and the two renderers were being treated alike before
  this change as well. This is from documentation and logs: nobody has compared the two renderers on a wide-gamut
  panel, by eye or with a meter.
- **Vsync** is `vid_wait`, as the layer's `displaySyncEnabled`, set again whenever the setting changes. On the
  MacBook's 60 Hz display, with the screen unlocked, a replay drawn as fast as it goes took 16.76 ms per frame with
  `vid_wait` on and 7.47 ms with it off. Behind a locked screen the system hands drawables back at a pace of its
  own, whatever the setting (8.4 ms per frame on the Mac mini, on or off).
- **Fullscreen** is SDL's: a Space of its own for the window. The system doesn't make one while the screen is
  locked, so there the game stays in its window; with SDL's hint against Spaces
  (`SDL_VIDEO_MAC_FULLSCREEN_SPACES=0`) the window covers the screen as it is. Both ways the layer's drawables follow
  the window to the display's size and back.
- **Changing the renderer in fullscreen** now takes the OpenGL window out of its Space and hides it before
  creating the Metal window. On a MacBook Pro (macOS 15.8, SDL 2.30.9), the OpenGL window left its Space in
  0.56 s, then the Metal window entered its Space in 0.6 s and remained on the display. The transitions ran in
  sequence, as in the other direction. `capture.py` fails a run if its log shows the OpenGL window leaving a
  Space while the Metal window is in one. A locked Mac has no Spaces to test this with.

  The earlier MacBook Pro test showed that switching from Software to VibeRant Metal left fullscreen, went back
  and forth, and ended on a Space other than the one on the display. VibeRant Metal to Software worked. The log
  showed that hiding the fullscreen OpenGL window (`SDL_HideWindow`) made SDL take it out of its Space (0.7 s),
  show it again when the transition ended, put it back into a Space because it was fullscreen and visible (0.6 s),
  and finally hide it, taking it out again (1.7 s). Each transition took the display away from the Metal Space.

  The review had raised the possibility of overlapping animations, a leftover Space, or the game ending up in a
  window. The presenter logs each window entering and leaving a Space (`WatchSpaces`, from AppKit notifications).
  The earlier test on an unlocked macOS 15 runner had shown only the Metal window entering a Space (0.55 to
  0.67 s) on the switch from Software. Hiding the OpenGL window on its inactive Space caused no transition. On
  the reverse switch, the OpenGL window entered a Space (0.6 s), then the Metal window left its Space as it was
  destroyed (0.7 to 1.1 s). SDL waited for each transition. Screen pictures showed the requested renderer
  fullscreen after every change, no frames were withheld from an out-of-sight window, and the game kept running.
- **A window nobody sees.** The presenter checks `NSWindow`'s occlusion state and skips regular presentation
  while none of the window is on screen. The game still draws and submits the frame. The display returns
  drawables, so asking for one from a minimized, hidden, covered, or off-Space window waits a second and returns
  none. A locked screen or sleeping display also counts as out of sight.
- **In case the system is wrong about that.** To keep the picture moving if AppKit incorrectly reports a visible
  window as out of sight, the presenter still presents probes when it expects a drawable without waiting.
  `mtl_present_seen.h` implements the decision in plain C++ so it can be tested. Two limits apply:

  - *The count of drawables out.* Metal reports when the system is done with each drawable (`addPresentedHandler`,
    macOS 10.15.4). Of three drawables, one can be on screen and one outstanding with a third still free. A probe
    goes out when at most one earlier drawable is unreported. With prompt reports, a visible window can get a
    probe after each report, up to a frame per refresh. If the system accepts none, two probes go out and the
    game avoids waiting. Both Macs' own GPUs reported within a quarter of a second behind locked screens.
  - *A pause after a slow drawable.* If a probe waits more than a quarter of a second for a drawable or gets none,
    probes pause for a second, then two, doubling to five minutes until thirty probes in a row are quick or the
    window is in sight.

  If at least three reports are late and they account for more than one in twenty (`ReportsLate`), only the
  pause limits probes. On GitHub's virtual displays, reports came about a second late even for a visible window,
  in nearly all cases in one run and in a quarter in others. Drawables were available immediately, but counting
  outstanding drawables stalled the picture for a second with each late report. On such a system, a truly
  out-of-sight window makes the game wait a second for a drawable at intervals that double to five minutes.

  A window the game minimized or hid, or one without a size, gets no frames. A new window gets probes until the
  system puts it on screen and reports it visible. Before 10.15.4, Metal provides no such reports, so only the
  first frame goes out regardless, as before.

  The runner was the only unlocked display available for the five attempts. The first treated a report with no
  presentation time as a drop and waited a second, but every runner report lacked a time. The second allowed a
  probe only with no outstanding drawable, and the third allowed one outstanding. Reports could be a second late,
  and screen pictures two seconds apart showed a stalled picture with both rules. The fourth bypassed the count
  when most reports were late. In the next run a quarter were late, and the picture stalled for that quarter's
  seconds.

  `-mtlblind` makes the presenter treat the window as out of sight regardless of AppKit for `capture.py`'s
  `blind` scenes. `metal_present_seen` tests the decision with a model of the layer and display with prompt and
  late reports (`tests/README.md`). See "What was tested, and what wasn't" for scene results.
- **A layer without a drawable.** If a visible window gets no drawable, the frame goes unshown and the presenter
  retries after a quarter of a second, doubling up to four seconds if the layer still gives none. Failed probes
  pause as above. The log reports when presentation stops and resumes. When the window is returned or closed, it
  counts presented frames, skipped frames, frames without a drawable, and probes, including which were shown or
  dropped. It also reports average and worst drawable wait times.
- **`-mtlunseen`** presents every frame regardless of AppKit's occlusion report for unattended tests. Both Macs
  kept supplying drawables with the screen locked, including with the MacBook's display asleep.
- **`-mtlcheck`** reads back the first three drawables for each window and every sixtieth thereafter, along with
  their source frames. Once the copies finish, `mtl_present_check.h` requires black outside the rectangle and
  compares mean RGB values on a grid of up to 8 by 8 blocks. Each block's channel means must be within one level
  at the frame's own size or six levels when scaled. At the frame's own size, at most 0.1% of its pixels may
  differ by more than one level in any RGB channel.
  It is plain C++ with its own test. The log records each drawable and marks a mismatch "FAILED". Game screenshots
  and capture-mode frames read the driver's screen before presentation, so they miss a black window or swapped red
  and blue. Readback requires turning off `framebufferOnly` and is for tests. It checks the presented texture.
  Inspect the screen to see what the display did with it.
- **The game's headers.** Keep the game's headers out of `mtl_present.mm` because they conflict with Apple's.
  A C++ file implements `mtl_present_game.h` to supply the window, icon, Screen Scaling setting, log, and
  `I_Error`.

What the presenter uses of mtl12 (`mtl12.h`):

- `void *Device()`: the `id<MTLDevice>`, not retained, for the `CAMetalLayer`.
- `HRESULT WrapTexture(void *texture, ID3D12Resource **resource)`: a drawable's `id<MTLTexture>`
  (`BGRA8Unorm` or `RGBA8Unorm`) as a resource in `D3D12_RESOURCE_STATE_PRESENT` that the driver can draw into and
  copy to. The resource retains the texture. The presenter wraps each frame's drawable and retires the wrapper
  with the frame's commands.
- `void PresentWithNextSubmit(void *drawable)`: the next `ExecuteCommandLists` presents this
  `id<CAMetalDrawable>` with its last command buffer. Applies to that one submission.

## Validation

Set Metal's validation variables before creating the device (`man MetalValidation`). `MTL_DEBUG_LAYER=1` stops
the program at the first API misuse, and `MTL_DEBUG_LAYER_WARNING_MODE=assert` also stops it at the first warning.
`MTL_SHADER_VALIDATION=1` checks shader reads and writes at run time. The device log line identifies validation by
the wrapper classes: `MTLDebugDevice` for API validation and `MTLGPUDebugDevice` or `MTLLegacySVDevice` for
shader validation.

Enable `DeviceOptions::validation` (`Core_VulkanValidation` through the game's `-mtldebug`, the counterpart of
`-vkdebug`) to report which passes failed in each command buffer. `rr_mtl12::ValidationErrors()` counts failed
command buffers and the shader validation faults logged with them, such as reading an unbound texture. Completion
handlers run on Metal's threads and save their messages for the driver's thread to log.

## Autorelease pools

Open an autorelease pool in every mtl12 or presenter function that calls Metal, AppKit, or Core Animation. The
game's C++ main loop has no pool, and SDL opens one only inside its calls. Objective-C frameworks put objects
the caller doesn't own in the thread's innermost pool for release when it drains. Cocoa's main thread has a
pool per event-loop turn. Without a pool, autoreleased objects stay for the life of the thread.

On both Macs, `OBJC_DEBUG_MISSING_POOLS=YES` logged each object autoreleased without a pool by thread. A replay
logged about a thousand reports on the driver's thread, mostly for the thousand textures freed at shutdown.
A library loaded to trace the calls showed they were all the device, which `-[IOGPUMetalResource dealloc]`
autoreleased each time the driver released a texture or buffer outside a pool. Each kept eight bytes and a
device reference that was never released. Resource, pipeline-state, and list destructors and the completion
handler now open pools. The same replay has no driver-thread reports, which `capture.py hardware` checks in the
`autorelease` scene (`tests/README.md`, "On a Mac").

Metal and Core Animation still report four to eight per presented frame on their own threads and from their own
code (`CAMetalLayer`, a presented drawable's arrays and numbers, and a frame-pacing record) on macOS 15 and 27.
The driver's completion-handler pool doesn't change the count. They don't accumulate in normal runs. With the
debug variable off (the runtime leaks what it reports when it is on), the M4 Pro presented 39,614 frames in
eleven minutes, with memory between 272,912 and 273,024 KB from the first minute onward.

## A command buffer that fails

Any failed Metal command buffer counts as device removal to the driver. Metal reports the GPU error per command
buffer (`MTLCommandBufferError`), such as a timeout, page fault, out-of-memory error, invalid resource, or device
removal. Direct3D 12 reports GPU work failures as removal. A failed buffer can finish some uploads, draws, and
copies, with no indication of which finished, while the driver already counts the textures as uploaded.

After the first failure, mtl12 fences read as `UINT64_MAX`, waits fail, and the queue's `Signal` returns the
failure. The fence's own `Signal` still returns success.
`GetDeviceRemovedReason` maps Metal's code to `DXGI_ERROR_DEVICE_REMOVED` for removal, `DXGI_ERROR_DEVICE_HUNG`
for timeouts or a device taken away after too many timeouts, `DXGI_ERROR_DRIVER_INTERNAL_ERROR` for internal
errors, and `DXGI_ERROR_DEVICE_RESET` for the rest. The driver ends the frame as for a removed Direct3D 12
device, stopping the game with an error naming the reason. The log includes Metal's description and code.
Recovery requires restarting the renderer to create a new device.

Previously, only Metal device removal counted. Other failures were logged and their fences completed as if work
had finished, so a readback could return unwritten pixels. No command buffer has failed on any tested GPU.
The driver test injects a failure with `FailNextSubmissionForTest` (`tests/README.md`, "Metal driver harness").

## Apple's paravirtual GPU

On "Apple Paravirtual device", mtl12 ends render passes after 48 draws and blit encoders after 96 copies to
avoid a driver assertion. `CreateDevice` identifies the device by its class (`AppleParavirt...`). The next
draw or copy opens another encoder. Results are the same because mtl12's passes load and store everything.
Other devices have no limit.

The virtual GPU on GitHub's macOS runners and on any VM made with Apple's Virtualization framework passes
commands to the host in chunks of 131,072 bytes per encoder. If an encoder ends within four bytes of filling
its last chunk, the driver tests the next encoder's first command against the old fill on the same command buffer.
It concludes the command won't fit the new, empty chunk and asserts
(`-[AppleParavirtCommandBuffer endCurrentChunk]`, "`_commandCurrentStorage.currentOffset`").

A race's 3D view uses one pass of about 600 draws and 350,000 bytes. Draw sizes vary, so that pass is estimated
to end at such a fill about once in 16,000 frames. It first happened 80 frames into Aerial Highlands, in the
screen copy after the 3D view. Running that frame under `lldb` on a runner exposed the assertion and the driver
code around it. Measurements there (macOS 15.8, shader validation on) were 350 to 620 bytes for a draw with its
buffer bindings, 68 for a pipeline state, 20 for a texture, 850 for a new pass, and up to 200 for a copy.

The limits stay under one chunk even at twice the measured sizes. With them, 213 replays (436,000 frames) ran
without the assertion. Without them, the estimate is one stop every eight replays. `-mtldebug` exposed the same
bug sooner because Metal ends each pass with a small blit encoder of its own. It runs with the limits too.

## What can differ from the other backends

The driver uses the same logic, shaders, textures, and states as Vulkan. Another shader compiler can round the
last bit differently, and Metal uses 32-bit float depth where Direct3D uses 24-bit depth. Other differences:

- **Depth bias** on a float depth buffer uses the depth value's own precision as its unit in place of 1/2^24,
  as on Vulkan devices without 24-bit depth.
- **Strips** always restart at index 0xFFFF (or 0xFFFFFFFF) in Metal. Direct3D 12 restarts only when the pipeline
  state enables it. The driver never enables it, and it would take a strip of 65,536 vertices to tell.
- **`SV_VertexID`** counts from the draw's first vertex in Metal and Vulkan, and from zero in Direct3D. The
  driver's only use draws from vertex zero.

### Replays on every map

`capture.py sweep` runs a separate game with `-metal` for the first staff ghost on each of 213 maps in frame
capture mode. It samples five level times per map, yielding 1,002 frames because some replays end earlier.
A run requires exit status 0, a frame capture summary, and at least one captured frame. The number of files
must match the summary's count of screenshots taken. The script also requires at least one presented frame, with
at most 20 frames or one twentieth of the frames given to the presenter, whichever is greater, left unpresented.
Validation messages, failed command buffers, "not implemented" lines, driver errors, and GPU waits the driver gave
up on fail the run. The sweeps below predate the presentation count requirement, but include the counts.
See `tests/README.md` ("Metal frames") for what a run checks about the window.

- **The runner**: all 213 clean, twice, with 436,000 frames presented to the window on the way.
- **The M4 Pro**, four games at a time, presenting with `-mtlunseen`: all 213 exited with 0 and wrote their 1,002
  frames in each of three sweeps, with 436,371 frames presented in each. The first, of the code as the runner had
  passed it, had shader validation messages in 29 replays, which the runner's and the Intel GPU's validation
  don't give, since they don't check what a vertex function puts out: "INF or NAN detected in interpolant" for the
  sky's vertex function in 21 maps, for the polygons' in seven, and for the sprites' in two. Each was a fault in
  code shared with the other renderers ("What the M4 Pro's validation found", below). With those fixed, the third
  sweep is clean on all 213, and its 1,002 frames are the first sweep's to the pixel.
- **The Intel Iris Plus 645**: two games at a time, presenting to its unlocked screen: the replays of 89 of the 213
  maps (every third map of the list, and every map this section names), 103 runs in all, exited with 0 with nothing
  reported, wrote their 424 frames, and presented 214,032 frames. A first sweep of all the maps, three games at a
  time, was more than this GPU keeps up with ("Speed", below) and doesn't count: 188 replays ran and exited with 0,
  none with a validation message, but 110 of their 835 screenshots were never written.

The paravirtual GPU's limit on encoders ("Apple's paravirtual GPU", above) is off on both Macs: their device lines
name `AGXG16SDevice` and `MTLIGAccelDevice`, and no log has the line that announces the limit.

### What the M4 Pro's validation found

Validation found three faults in code shared by every hardware renderer.

- **The sky dome's caps had no texture coordinates.** `HWR_SkyDomeVertex` never wrote them, so the two fans that
  close the dome sampled the sky texture at whatever `malloc` had left in the vertex array: infinities and
  not-a-numbers in 21 maps' replays with that build, zeros with another. That was the frame that had changed between
  two runs on the runner: Neon Resort at level time 700, where the camera is pitched up on a slope, had 198 dim
  pixels in the top 43 rows of the black sky in one run of four. Giving the caps random coordinates on the M4 Pro
  (temporary instrumentation) changes 202 pixels in the top 41 rows of that frame, over the same columns, and none
  of the frame at 650. The caps now get the middle of the texture's first texel. Ten more replays of Neon Resort to
  700 on the M4 Pro gave ten identical frames, and seven on the Intel GPU seven.
- **A sprite two near planes from the camera** has a clip-space z of exactly zero, where the sprite shader's
  clipping hack (`80 / z`) is infinite. The Gust Planet and Malign Egg Shrine replays each had one for a frame.
  The shader now treats a zero divisor as a tiny positive number.
- **A sprite without height**, in a sector whose light changes at 3D floors, got texture coordinates divided by its
  height. Seven maps' replays have one. The renderer now skips it.

None of the three changed a pixel of the 1,002 frames on the M4 Pro: a sprite at the pole or without height shows
nothing either way, and no captured frame of that build had a cap in view with anything but zeros behind it.

### The frames

`compare.py` compares frames pixel by pixel. A differing pixel counts as "Beyond texel edges" if, in either
direction, the other frame has no match in the 3 by 3 neighborhood centered on that pixel. A match is within
eight levels per RGB channel. A texture coordinate on an edge can sample either texel. Two GPUs disagree on
that choice more often than two backends on one GPU.

| Frames of | against | differ: median, 95% of frames under, worst | more than one level apart | beyond texel edges: frames at most 0.02%, above 0.1% |
| --- | --- | --- | --- | --- |
| the runner (1,002) | VibeRant Vulkan on a Radeon (RADV, Linux) | 0.141%, 0.756%, 20.0% | 0.024%, 0.169%, 3.27% | 936, 11 |
| the M4 Pro (1,002) | the runner | 0.002%, 0.026%, 0.100% | the same | 1,002, 0 |
| the M4 Pro (1,002) | the Radeon | 0.141%, 0.754%, 20.0% | 0.024%, 0.166%, 3.25% | 939, 12 |
| the Intel GPU (424, of 89 maps) | the M4 Pro | 0.094%, 0.241%, 6.84% | 0.089%, 0.213%, 1.22% | 387, 8 |
| the Intel GPU (424) | the runner | 0.093%, 0.226%, 6.84% | 0.087%, 0.214%, 1.23% | 387, 7 |
| the Intel GPU (424) | the Radeon | 0.208%, 1.435%, 19.8% | 0.085%, 0.215%, 3.28% | 389, 11 |

The M4 Pro closely matches the runner's virtual GPU, as expected if its host is also Apple silicon. The largest
difference (0.1%) is in distant fine textures. The runner's Neon Resort frame with the cap has the most pixels
beyond texel edges (171). The Intel GPU differs from both by a tenth of a percent, almost entirely at texel edges. Its eight frames with more than 0.1% of the pixels beyond them, against the M4 Pro, are fine
textures far away (Daytona Speedway and Blizzard Peaks Classic), two effects that come out differently on the Intel
Mac than on the ARM ones, as they do between other systems (Test Track's puff of dust at 350, Haunted Ship's effect
at 70), and Vermilion Vessel's wall (below). Its frame that differs most, Dragonspire Sewer 1 at 70 with 6.8%, is
bands of water one level apart.

Against the Radeon, the differences are the ones the runner had, on the same frames:

- **One level on blended surfaces.** Where a translucent surface is blended over another (water above all), whole
  bands of one color come out one level apart, up to a fifth of the frame in nine frames of water levels
  (Dragonspire Sewer, Deluged Metroplex, Whirl Waters, Aquatic Cathedral, Water Palace, Thunder Piston, Honeycomb
  Hollow, Carnival Night, Chemical Facility). It is the Radeon that rounds differently, not Metal: four of those
  frames were drawn again with the Vulkan backend on lavapipe, Mesa's CPU device, and the runner's frames differ
  from lavapipe's in 0.04% to 2% of the pixels where the Radeon's differ from lavapipe's in 5.6% to 22%.
  The Intel GPU agrees with Apple's: its frames of Deluged Metroplex, Whirl Waters, and Aquatic Cathedral are within
  0.15% of the M4 Pro's and 13% to 20% from the Radeon's. The same rounding is why the driver test's grouped water scene starts from another green on Vulkan.
- **Texel edges**, more than 0.1% of the pixels beyond them in eleven frames:
  - five at level time 70 (Mega Sandopolis, Mega Scrap Brain, Dragonspire Sewer 2, Zoned City, Barren Badlands, up to
    2.9%), where it is the Linux build's game that differs: effects around the kart at the start are other ones than
    in the frames an earlier commit's Windows build drew under Wine, which Metal's frames match (0.05% at most). The
    Linux and Windows builds differed in the same frames when VibeRant Vulkan was compared with VibeRant D3D;
  - Test Track at 350 (0.39%), a puff of dust behind the kart that is placed differently on each system;
  - Haunted Ship at 70 (0.37%), the effect in one plane with another that already differed between Vulkan and
    Direct3D 12;
  - Daytona Speedway at 350 and 1400, and Blizzard Peaks Classic at 350 and 1400 (0.13% to 0.23%), fine textures
    far away, where texel edges are everywhere.
- **One depth tie.** In Vermilion Vessel at 1400, a strip of a distant red wall shows the sky through a stipple:
  about 870 pixels on the runner and 950 on the M4 Pro, in the same place with another pattern. The Intel GPU draws the wall whole.
  So does the Radeon, with either of its backends. A sky wall (the invisible polygon that keeps the sky
  in front of what is behind it) lies in the wall's plane there, and which of two surfaces in one plane shows is
  decided by rounding, pixel by pixel. Software shows no wall there at all, only sky. It is the only such place the
  1,002 frames have, so depth isn't less precise on Metal in general; it would take a change to the hardware
  renderer, for every backend, to settle it.

The frames that stand out in each comparison were looked at, with a sample of ordinary ones from each Mac.

### What a person at a Mac should look at

Checks 1 and 4 to 7 were done on the MacBook Pro ("Not tested"); the rest are open there, and all of them on the
M4 Pro. With the Mac unlocked, start the game from a terminal to keep the log (`<home>/ringracers/latest-log.txt` has it
too). Allow ten minutes for most of the checks the logs alone can't settle.

1. **Start it as it comes** (fullscreen, VibeRant Metal). Right: the intro and the title screen fill the screen,
   letterboxed if the screen isn't 16:10. Wrong: a window, a black screen, or a picture in a corner.
2. **Sharpness on a Retina display.** Options → Video → Advanced → Renderer: look at the same scene in Software and
   in VibeRant Metal. Right: equally sharp (neither is pixel-sharp on a scaled Retina mode). Wrong: one clearly
   softer or blockier than the other.
3. **Colors on a MacBook's own display.** The same scene in both renderers again, or the title screen. Right: the
   same colors. Wrong: VibeRant Metal more saturated (reds and greens above all). The log's line "colors are matched
   to the display" should name the window's color space and "(the system gave it)" or "(set here)".
4. **Change the renderer in fullscreen**, Software and back, twice. Right: after a second or two of the system's
   animation the game is on the whole screen again and the keys work without a click; Mission Control (Control-Up)
   shows one Space for the game and no empty one. Wrong: the desktop, a black Space, the game in a window, or keys
   that do nothing. The log has a line for each window's way into and out of a Space.
5. **Quit from fullscreen and from a window**, through the menu. Right: the game is gone. Wrong: an empty window
   that flashes or flies into a Space as it goes.
6. **Hide it and bring it back** while a race or a replay runs: minimize to the Dock and restore, Command-H and
   back, another Space and back (Control-Left and Right), a window dragged over it and away, lock the screen and
   unlock it, close the lid and open it. Right: the picture is moving again at once each time. Wrong: a picture
   that stands still while the sound goes on. Afterwards the presenter's last line in the log says how many frames
   "went to a window the system called out of sight": if that is a large number although the window was in plain
   sight, the system's report was wrong and the safeguard was what kept the picture going, which is worth telling.
7. **`vid_wait` on and off** (the console, or Options → Video): on, the motion is even and nothing tears; off, the
   frame rate is higher and tearing is possible.
8. **Options → Video → Advanced with Software selected**: the lines above the Renderer row should describe VibeRant
   Metal, not VibeRant D3D and Direct3D 12.
9. **A second display, if there is one**: drag the window across, and go fullscreen on each. Right: the picture
   fits each display. Wrong: a stretched or offset picture after the move.
