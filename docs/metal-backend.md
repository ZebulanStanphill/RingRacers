# VibeRant Metal

VibeRant Metal is the VibeRant driver (`src/hardware/r_d3d12`) running on Apple's Metal: a hardware renderer for
macOS that draws what VibeRant D3D and VibeRant Vulkan draw, because it is the same driver code. It is built like
VibeRant Vulkan ([vulkan-backend.md](vulkan-backend.md)): the driver keeps calling Direct3D 12, and a backend
underneath implements the part of Direct3D 12 it calls.

**State.** A macOS build of the game has it and starts with it: `SRB2_CONFIG_VIBERANT_METAL` is on by default there, the
Renderer setting lists **VibeRant Metal**, and a new config uses it. It has run on three GPUs: the virtual one of
GitHub's macOS runners ("Apple Paravirtual device"), an Apple M4 Pro, and an Intel Iris Plus Graphics 645. On each
the driver test passes (`tests/README.md`, "Metal driver harness") and the game plays a replay on every map, or on
the Intel GPU on 89 of them, with Metal's API and shader validation on and nothing reported, drawing the frames
VibeRant Vulkan draws to within what two GPUs differ by (below, "What was tested, and what wasn't"). Nobody has
played it, and nobody has looked at a Mac's screen it drew on: the two Macs were tested over the network,
unattended, with their screens locked for all but a part of the first day. The pictures that exist are of a
runner's screen. "What a person at a Mac should look at", at the end, is the list that follows from that.

## How

`src/hardware/r_d3d12/metal/` implements `ID3D12Device` and the interfaces made from it (the same dozen interfaces
and about 70 methods as vk12) in Objective-C++ on Metal. `mtl12_bases.h`, generated by `vulkan/gen_bases.py
--backend mtl12`, defines every method of those interfaces as "not implemented", and mtl12's classes override the
ones the driver calls; a method the driver starts to use and mtl12 lacks says so in the log.

The build define is `HAVE_VIBERANT_METAL`, beside `HAVE_VIBERANT` ("the driver is built"), and the CMake option is
`SRB2_CONFIG_VIBERANT_METAL`: on by default on macOS, and `-DSRB2_CONFIG_VIBERANT_METAL=OFF` builds without the driver, as the game was
before. A macOS build has this backend and no other: not Direct3D 12, and not Vulkan through MoltenVK (asking for
either beside it stops the configuration). `Core_Metal()` is therefore a constant, true with
`HAVE_VIBERANT_METAL`. The backend needs CMake 3.16, the first that knows Objective-C++ as a language (the rest of the
project states 3.14, and the configuration says so when it stops), and its files are compiled with automatic
reference counting, which the game's target sets for its Objective-C++ files. What differs per backend, and where
the driver asks:

- **Device creation** (`d3d12_core.cpp`): `rr_mtl12::CreateDevice` makes the system's default `MTLDevice` (or, for
  a program without a window that is given none, the first device that isn't a low-power one) and its command queue.
- **Waiting for the GPU** (`Core_Wait`): mtl12's fence waits for Metal's command buffers; it has no Win32 event.
- **Shaders** (`d3d12_pipeline.cpp`): the built-in shaders are the SPIR-V the Vulkan backend is built with (the
  same generated headers, `r_vulkan_shaders/*.h`), and shaders compiled at run time reach mtl12 as SPIR-V too
  (`D3DCompile` off Windows is `rr_spirv::CompileHlsl`). mtl12 turns SPIR-V into Metal Shading Language itself.
- **The root signature** (`r_d3d12.cpp`): mtl12 has `RR_ROOT_SIGNATURE`'s layout built in (`rr_spirv::kRoot`) and
  takes a token in place of Direct3D's serialized one.
- **Headers**: Microsoft's DirectX-Headers and `vulkan/vk12_win.h`, as on Linux. That header and `spirv_shader.h`
  have nothing of Vulkan in them.

Direct3D's headers and Objective-C's don't mix freely: both define `BOOL` (a 32-bit integer and a `bool`), and
Microsoft's define `interface` as a macro, which `@interface` doesn't survive. mtl12's files include Metal first and
then Direct3D's declarations with their `BOOL` under another name (`mtl12_internal.h`), and nothing of Apple's
after. The public header, `mtl12.h`, is plain C++ and passes Metal's objects as `void *`, so the driver's C++ files
and a presenter can include it.

## Shaders

`rr_spirv::PatchShader` gives every input and output of a stage the location its HLSL semantic stands for, as for
Vulkan. `TranslateToMsl` (`mtl12_msl.cpp`, plain C++ around SPIRV-Cross) then writes the stage as Metal Shading
Language 2.1, with explicit indices for the registers:

| Register | SPIR-V binding | Metal index |
| --- | --- | --- |
| constant buffers `b0` to `b5` | 0 to 5 | buffer 0 to 5 |
| textures `t0` to `t10` | 16 to 26 | texture 0 to 10 |
| samplers `s0`, `s1` | 32, 33 | sampler 0, 1 |
| the vertex buffer | | buffer 30 |

A vertex shader's inputs are attributes numbered as their locations (`POSITION` 0, `NORMAL` 1, `COLOR0` 2,
`TEXCOORD0` 4, ...), and the stages link by location. glslang declares every register of `shaders.hlsl` in every
stage; the Metal function takes only the ones its code reaches, and SPIRV-Cross says which. A function can still name
a register that its compiled code never reads (an add-on shader's unused view constants), so the first Metal pipeline
state made of a pair of functions is made with reflection (macOS 13 and later), and what Metal says the pipeline
uses is what a draw binds: Metal's validation wants everything used to be bound, and warns about a buffer bound for
nothing.

The source is compiled with `newLibraryWithSource`, with fast math off: Metal's compiler otherwise assumes it may
reorder arithmetic, and the shaders pick palette entries and colormap rows by arithmetic that must come out as on
the other backends. Compiled functions are shared by the bytes of their SPIR-V, since the driver makes hundreds of
pipeline states from two dozen shaders. The pipeline states own them: the cache only knows where a function is while
a pipeline state is made of it, so the built-in shaders' functions last as long as the device, and an add-on
shader's go, with the cache's copy of its SPIR-V, when the driver retires the last pipeline state made of it (when
the add-on is replaced or unloaded). The driver's prewarming makes pipeline states on a worker thread, so the cache
is locked.

## Mapping

| Direct3D 12 | mtl12 |
| --- | --- |
| clip space, viewport, depth range, winding | Metal's are Direct3D's: y up in clip space, the viewport's origin at the top left, depth 0 to 1, and front faces by winding on screen. Nothing is flipped (vk12 needs a viewport of negative height) |
| `SV_Position.w` in pixel shaders | Metal's fragment position has `1/w`, as OpenGL's does; glslang's `--hlsl-dx-position-w` already writes the reciprocal into the SPIR-V |
| the root signature: 6 root constant buffers, 11 tables of one texture, 2 tables of one sampler | the argument tables of the two functions, at the indices above; a draw sets what the encoder doesn't already have, and only a buffer's offset when the buffer is the same |
| a root constant buffer named by GPU virtual address | each buffer gets a made-up address range; the address resolves to a buffer and an offset |
| descriptor heap slots | records of a texture or a sampler |
| views | a view of all of a texture's mips is the texture; one of fewer is a texture view the resource keeps. A view of another format than its texture's isn't implemented (the driver has none) |
| a null view | a 1x1 (or 1x1x1) texture of the view's format, written as zero by a command buffer of its own when it is made: a submission like the driver's, so fences wait for it and its failure is the device's. If it can't be set up, the view is left empty (a draw that needs it is skipped, with a line in the log) and the next null view of that kind tries again |
| resource states and `ResourceBarrier` | nothing: Metal tracks what textures are used for. A target that stops being one ends its pass |
| `OMSetRenderTargets`, draws | a render pass that loads and stores everything, begun at the first draw after the targets are set and ended by whatever can't be in one (a copy, a clear, other targets). One color target, and a depth target of its size (the driver's always are) |
| `ClearRenderTargetView`, `ClearDepthStencilView` | the load action of the next pass on that target. If the target is used otherwise first (copied, handed to a shader, the list closed), a pass of its own with no draws. Only whole targets: a clear of rectangles isn't implemented (the driver has none) |
| one pipeline state for any targets | a Metal render pipeline state per formats of the targets, the description's own made with the object, so that the driver's prewarming still compiles ahead of time. Lists, strips, and lines are a draw's argument in Metal |
| depth and stencil tests in the pipeline state | an `MTLDepthStencilState` made with it; a pass without a depth target gets one that tests nothing |
| cull mode, winding, depth bias, depth clip, stencil reference, blend factor, viewport, scissor | set on the encoder, when they differ from what it has. The scissor rectangle is cut to the targets, and a draw with an empty one is skipped, since Metal accepts neither |
| vertex buffers | buffer index 30, with the stride of the input layout |
| copies | a blit encoder; consecutive copies share one |
| committed and placed resources, heaps | every resource is a Metal texture or buffer of its own. A heap holds no memory: the driver's 16 MB texture heaps and its offsets into them are bookkeeping here, checked for fit only. `GetResourceAllocationInfo` reports the texels' size in Direct3D's 4 KB or 64 KB class |
| upload and readback heaps, `Map` | buffers in shared storage, mapped for life; other buffers and all textures are private to the GPU |
| command allocators | nothing: a list takes a command buffer from the queue each time it is reset |
| fences, `Signal`, waits | a value that completes with the last command buffer of the submission it was signaled after |
| a removed device | any command buffer that Metal fails (below, "A command buffer that fails") |
| `D24_UNORM_S8_UINT` | `Depth32Float_Stencil8`: Apple's GPUs have no 24-bit depth, and every Metal device has this format |
| `IDXGIAdapter3::QueryVideoMemoryInfo` | the device's recommended working set size as the budget and its allocated size as the usage; no adapter if the device recommends nothing |
| timestamp queries | read as zero. Metal has no timestamp a command list can write between two commands (its counter sample buffers aren't on every device), so the driver's GPU times say 0 ms |
| a sampler's `MipLODBias` | not implemented: Metal's samplers have none. The driver never sets one; mtl12 logs it if one is ever set |
| releasing objects | objects are released on the last `Release`, and Metal's command buffers keep what they use alive besides |
| autorelease pools | the driver's thread is the game's main loop, which is C++ and has none, so every call of mtl12's and the presenter's that can autorelease brings its own, the destructors included: a Metal texture or buffer autoreleases its device as it is deallocated |

## The window

The game's window is made for OpenGL, which shows the Software renderer's frames. As with Vulkan
([vulkan-backend.md](vulkan-backend.md), "The window"), the presenter (`metal/mtl_present.mm`) makes a second
window like the first for Metal (`SDL_WINDOW_METAL`, with SDL's Metal view and its `CAMetalLayer`), hides the first,
and makes the second the game's window (`sdlmain.h`'s `window`), which is what the video code sizes, makes
fullscreen, and takes input from. When Software takes over, the first window comes back as the second one was. The
OpenGL window is made hidden and only shown once a renderer that presents on it is the one the game runs with
(`I_ShowDeferredWindow`), so starting the game shows one window. Quitting shows none: when the game ends with
VibeRant Metal, the presenter closes the Metal window and leaves the OpenGL window as it is, hidden, for the video
system to destroy a moment later. (It used to bring it back as for Software: a window nothing had drawn into, shown
for the moment before it went, and from fullscreen on its way into a Space of its own.) The log's last line of the
presenter says what SDL says of that window then: "closed the Metal window as the game quits; the game's OpenGL
window is hidden".

- **Size.** The layer's drawables are the size of the window's content in points, not in the display's pixels: the
  game's window isn't a high-resolution one (it is made without `SDL_WINDOW_ALLOW_HIGHDPI`), so on a Retina display
  the system scales the frame up, as it does Software's and Legacy GL's. SDL's view keeps the drawable size at the
  window's as the window changes, and the presenter takes each drawable's own size as the size to place the frame in.
  The log says so with each new size: "1280x720 drawables for a window of 1280x720 points on a display with 2 pixels
  per point (the system scales the frame up) and 60 frames per second". That line is from a MacBook Pro whose
  2560x1600 panel is set, as it comes, to look like 1440x900: fullscreen there is a 1440x900 drawable, which the
  system doubles to its 2880x1800 backing and then fits to the panel. So on that display the picture isn't
  pixel-sharp, and couldn't be made so by drawables in pixels either, since nothing on it is; on a display of one
  pixel per point (a Mac mini's 1920x1080 monitor) the drawable is the screen's pixels. That is the size Software's
  frames have there too: the game's OpenGL window isn't a high-resolution one either (SDL turns
  `wantsBestResolutionOpenGLSurface` off without `SDL_WINDOW_ALLOW_HIGHDPI`), and Apple's documentation of that
  property says that such a view "uses a 1 pixel per point framebuffer regardless of the backing scale factor" and
  that "the rendered surface contents are also magnified". So both renderers hand the system a frame in points and
  the system magnifies it, and VibeRant Metal is not sharper than Software, which is the aim. What the documentation
  doesn't say is with what filter the system magnifies an OpenGL surface; a layer's default is linear
  (`magnificationFilter`), which the presenter leaves. Whether the two look exactly alike on a Retina display is
  therefore something only a look at one can tell.
- **Placement.** The driver's placement draws each frame into the drawable, as on the other desktop presenters: at
  Screen Scaling's Integer or 1:1 rectangle, or scaled with linear filtering to the largest rectangle of the
  frame's aspect ratio. A drawable is BGRA8 and only a render target (`framebufferOnly`), which a draw suits and a
  copy from the RGBA8 screen wouldn't.
- **Colors.** `BGRA8Unorm`, not an sRGB format, so the frame's values go into the drawable as they are. What the
  display makes of them is a matter of color spaces, and the aim is that it makes of them what it makes of
  Software's frames in the game's OpenGL window. SDL gives every window it makes the sRGB color space (since SDL
  2.26; the commit that did it says OpenGL "was getting a much more saturated colorspace" before), and the system
  matches what OpenGL draws in such a window from sRGB to the display. A `CAMetalLayer` has no color space unless it
  is given one, and Apple's documentation of the property says that its content then "isn't color-matched": on a
  display of a wider gamut than sRGB, such as a MacBook's P3 panel, the same frame would look more saturated from
  VibeRant Metal than from Software. So the presenter sees to it that the layer has its window's color space
  (`MatchWindowColors`), which is the OpenGL window's, since the same SDL makes both. On both Macs the system had
  already given the layer the window's color space when the presenter looked (macOS 27 and macOS 15.8, SDL 2.30.9),
  so nothing changed there, and the log says which it was: "colors are matched to the display as the OpenGL window's
  are: the layer has its window's color space, "sRGB IEC61966-2.1" (the system gave it), and the display's is "Color
  LCD"" on the MacBook, whose panel is the wide-gamut one, and the same with a display that is itself "sRGB
  IEC61966-2.1" on the Mac mini. Taking the layer's color space away on purpose and letting the presenter set it
  gives the same line with "set here". So the earlier sentence here, that the layer had no color space and showed
  the frame's values as they were, was wrong about the layer, and the two renderers were being treated alike before
  this change as well. This is from documentation and logs: nobody has compared the two renderers on a wide-gamut
  panel, by eye or with a meter.
- **Vsync** is `vid_wait`, as the layer's `displaySyncEnabled`, set again whenever the setting changes. On the
  MacBook's 60 Hz display, with the screen unlocked, a replay drawn as fast as it goes took 16.76 ms per frame with
  `vid_wait` on and 7.47 ms with it off. Behind a locked screen the system hands drawables back at a pace of its
  own, whatever the setting (8.4 ms per frame on the Mac mini, on or off).
- **Fullscreen** is SDL's: a Space of its own for the window. The system doesn't make one while the screen is
  locked, so there the game stays in its window; with SDL's hint against Spaces
  (`SDL_VIDEO_MAC_FULLSCREEN_SPACES=0`) the window covers the screen as it is. Both ways the layer's drawables follow
  the window to the display's size and back.
- **Changing the renderer in fullscreen** trades two windows, each of which wants a Space of its own, and a review
  feared two animations at once, a Space left over, or a game that ends up in a window. The presenter now writes each
  window's way into and out of a Space to the log (`WatchSpaces`, from AppKit's notifications), and on a runner
  (macOS 15, where the screen isn't locked) the order was this. Software to VibeRant Metal: the Metal window goes into
  a Space, in 0.55 to 0.67 s, and hiding the OpenGL window afterwards, which is then on a Space that isn't showing,
  is no transition at all. VibeRant Metal to Software: the OpenGL window goes into a Space (0.6 s), and then the
  Metal window leaves its own as it is destroyed (0.7 to 1.1 s). So two transitions that way, but one after the
  other, because SDL waits for each to end. After every change the pictures of the runner's screen show the game
  on the whole screen with the renderer that was asked for, no frame was withheld from a window out of sight, and
  the game went on.

  A person at a MacBook Pro (macOS 15.8, SDL 2.30.9) then saw what the runner hadn't shown. VibeRant Metal to
  Software was fine. Software to VibeRant Metal left fullscreen, went back and forth, and ended with the game on a
  Space other than the one on the display. The log had the reason: hiding the OpenGL window (`SDL_HideWindow`) while
  it is fullscreen makes SDL take it out of its Space (0.7 s), show it again as that ends, put it back into a Space
  for being fullscreen and shown (0.6 s), and only then hide it, which takes it out once more (1.7 s). Each of those
  takes the display along, away from the Metal window's Space. So the presenter now takes a fullscreen OpenGL window
  out of its Space and hides it before it makes the Metal window: the OpenGL window leaves its Space (0.56 s), then
  the Metal window goes into one (0.6 s), and the Metal window is on the Space that shows. Two transitions, one
  after the other, as in the other direction. `capture.py` fails a run in whose log the OpenGL window leaves a Space
  while the Metal window is in one. On a Mac whose screen is locked there are no Spaces to try any of this with.
- **A window nobody sees.** A layer's drawables only come back from the display, so asking the layer of a window
  that is minimized, hidden, on another Space, or covered for its next drawable waits a second and gives nothing.
  The presenter asks AppKit whether any of the window is on screen (`NSWindow`'s occlusion state) and doesn't present
  every frame while none is; the frame is still drawn and submitted, so the game runs on. A locked screen and a
  sleeping display count as out of sight too.
- **In case the system is wrong about that.** If AppKit ever called a window out of sight that a player is looking
  at, presenting nothing would freeze the picture while the race goes on. So a window the system calls out of sight
  still gets frames, as long as asking for a drawable can't be expected to wait (`mtl_present_seen.h`, plain C++ so
  that a test can run it). Such a frame is a probe, and there are two things that hold one back:

  - *The count of drawables out.* Metal reports for each presented drawable when the system is done with it
    (`addPresentedHandler`, macOS 10.15.4), and the layer has three drawables: with one on screen and at most one
    more unaccounted for, a third is free. So a probe goes out while at most one earlier drawable is unreported.
    While the system takes what it is given, a probe follows each report, and a window that is in fact on screen
    keeps its picture at up to a frame per refresh. When the system takes nothing, two probes go out and no more,
    and the game never waits. That is how it goes where reports are prompt, which they were on both Macs' own GPUs
    (every one within a quarter of a second, behind a locked screen).
  - *A pause after a slow drawable.* A probe that waited more than a quarter of a second for its drawable, or got
    none, is followed by a pause of a second, then two, doubling to five minutes, until thirty probes in a row are
    quick or the window is in sight.

  Where reports come late too often (three at least, and more than one in twenty: `ReportsLate`), the count is not
  asked and only the pause holds probes back. That is for a virtual machine's display (GitHub's runners), where
  reports came about a second after their drawable was presented, in one run nearly all of them and in others a
  quarter, for a window in plain sight too, while the layer went on giving drawables at once: going by the count
  there left the picture standing for a second at every late report. The price is that a window that really is out
  of sight on such a system makes the game wait a second for a drawable, at intervals that double to five minutes.

  A window the game itself minimized or hid, or one without a size, gets nothing. A new window's first frames go
  out as probes, since a window doesn't count as visible until the system has put it on screen. On a system older
  than 10.15.4, which has no reports, only a window's first frame goes out regardless, as before.

  It took five tries, and the runner's display decided each, being the only screen there was to try it on that
  wasn't locked. The first waited a second after a probe that Metal reported without a time shown, taking that for
  a dropped frame: but on the runner every report of every frame has no time. The second presented a probe only
  when nothing was unreported, and the third when at most one thing was: but the runner's reports can be a second
  late, so both left a picture that two pictures of the screen, two seconds apart, showed standing still. The
  fourth left the count aside where most reports had been late: but in the next run a quarter were, and the
  picture stood still for that quarter's seconds.
  `-mtlblind` acts a wrong report out (the presenter takes its window for out of sight whatever AppKit says), for
  `capture.py`'s `blind` scenes, and the test `metal_present_seen` runs the decision against a model of the layer
  and the display with prompt and late reports (`tests/README.md`). What the scenes showed where is under "What was
  tested, and what wasn't".
- **A layer without a drawable.** If the layer of a window in sight gives no drawable, that frame isn't shown and
  the layer isn't asked again for a quarter of a second, doubling up to four seconds while it keeps giving none; if
  it has none for a probe, probes pause as above. The log says when presenting stops
  and starts again, and, when the window is given back or closed, how many frames were presented, skipped, and left
  without a drawable, how many of those presented were probes, shown or dropped, and how long the layer took to
  give a drawable, on average and at worst.
- **`-mtlunseen`** presents every frame regardless of what AppKit says, for tests on a Mac nobody sits at: on both
  Macs this was tried on, the layer went on giving drawables with the screen locked (and, on the MacBook, the
  display asleep).
- **`-mtlcheck`** has the presenter read drawables back: a window's first three and every sixtieth after, each with
  the frame that was placed in it, compared once the copies are done (`mtl_present_check.h`, plain C++ with a test of
  its own). The frame must be at the rectangle it was placed at, pixel for pixel where it is at its own size and by
  the mean colors of 8 by 8 blocks where it is scaled, and the rest of the drawable must be black; the log has a line
  per drawable, and "FAILED" in it where one differs. It is there because the game's screenshots and the capture
  mode's frames are read from the driver's screen, before the presenter, and so can't tell a window that shows the
  frame from one that shows black, or the frame with red and blue swapped. It is a test's path, not a player's: a
  layer's drawables can only be read with `framebufferOnly` off. And it reads the texture that was presented, not the
  screen: what the display did with it is still something only a look at the screen can tell.
- **The game's headers.** `mtl_present.mm` is Objective-C++, and the game's headers don't go into one file with
  Apple's, so what the presenter needs of the game (the window, the icon, the Screen Scaling setting, the log, and
  `I_Error`) comes through `mtl_present_game.h`, which a C++ file implements.

What the presenter uses of mtl12 (`mtl12.h`):

- `void *Device()`: the `id<MTLDevice>`, not retained, for the `CAMetalLayer`.
- `HRESULT WrapTexture(void *texture, ID3D12Resource **resource)`: a drawable's `id<MTLTexture>`
  (`BGRA8Unorm` or `RGBA8Unorm`) as a resource in `D3D12_RESOURCE_STATE_PRESENT` that the driver can draw into and
  copy to. The resource retains the texture. The presenter wraps each frame's drawable and retires the wrapper
  with the frame's commands.
- `void PresentWithNextSubmit(void *drawable)`: the next `ExecuteCommandLists` presents this
  `id<CAMetalDrawable>` with its last command buffer. Applies to that one submission.

## Validation

Metal's validation is turned on from outside the program, with environment variables that have to be set before the
device is made (`man MetalValidation`): `MTL_DEBUG_LAYER=1` (API validation, which stops the program at the first
misuse; with `MTL_DEBUG_LAYER_WARNING_MODE=assert`, at the first warning too) and `MTL_SHADER_VALIDATION=1` (which
checks what the shaders read and write as they run). The log's device line says which of them the device was made
with, by the classes Metal wrapped it in: `MTLDebugDevice` for the first, and `MTLGPUDebugDevice` or
`MTLLegacySVDevice` for the second. With `DeviceOptions::validation` (`Core_VulkanValidation`; the game's `-mtldebug`,
the counterpart of `-vkdebug`), each command buffer also says which of its passes failed. `rr_mtl12::ValidationErrors()` counts failed command buffers and the faults
shader validation logs with them, such as a function reading a texture that was never bound. Completion handlers
run on Metal's threads, so what they have to say is kept and written to the log from the driver's thread.

## Autorelease pools

Objective-C's frameworks hand out objects that the caller doesn't own by putting them in the thread's innermost
autorelease pool, which releases them when it is drained. A Cocoa program's main thread has one per turn of its event
loop. The game's main loop is C++ and has none (SDL makes one only inside its own calls), so an object autoreleased
there with no pool open is kept for as long as the thread lives. mtl12 and the presenter therefore open a pool in
every function that calls into Metal, AppKit, or Core Animation.

Whether that covered everything was measured on the two Macs with the Objective-C runtime's own report
(`OBJC_DEBUG_MISSING_POOLS=YES`, which logs each object autoreleased with no pool in place, by thread). It didn't:
a replay left about a thousand reports on the driver's thread, all of them the device, autoreleased by
`-[IOGPUMetalResource dealloc]` each time the driver released a texture or a buffer outside a pool (found with a
library loaded for the purpose that printed where; mostly the thousand textures freed at shutdown). Each kept eight
bytes and a reference to the device that was never given back. The destructors of mtl12's resources, pipeline
states, and lists now open a pool too, as does the completion handler, and the same replay has no report on the
driver's thread: `capture.py hardware`'s `autorelease` scene checks that (`tests/README.md`, "On a Mac").

The other reports, four to eight per presented frame, are on Metal's and Core Animation's own threads, from their own
code (`CAMetalLayer`, the arrays and numbers of a presented drawable, a frame-pacing record), on macOS 15 and 27
alike; a pool around the driver's completion handler doesn't change their number. They don't accumulate: without the
debug variable (with it the runtime leaks what it reports), the game presented 39,614 frames in eleven minutes on
the M4 Pro with its memory between 272,912 and 273,024 KB from the first minute on.

## A command buffer that fails

Metal reports what went wrong on the GPU per command buffer (`MTLCommandBufferError`): a timeout, a page fault, no
memory left, an invalid resource, the device removed. Direct3D 12 has one way for the GPU's work to fail, the device
being removed, and that is what any of them is to the driver: a command buffer that failed did some part of its
uploads, draws, and copies and not the rest, nothing says which, and the driver's bookkeeping already counts the
textures as uploaded. From the first failure on, mtl12's fences read as `UINT64_MAX`, waits fail, `Signal` fails, and
`GetDeviceRemovedReason` gives a reason by Metal's code: `DXGI_ERROR_DEVICE_REMOVED` for the device removed,
`DXGI_ERROR_DEVICE_HUNG` for a timeout or a device the system took away after too many of them,
`DXGI_ERROR_DRIVER_INTERNAL_ERROR` for an internal error, and `DXGI_ERROR_DEVICE_RESET` for the rest. The driver
then ends the frame as it does for a removed Direct3D 12 device, by stopping the game with an error that names the
reason; the log has Metal's own description and code. There is no recovery short of starting the renderer again,
which makes a new device.

Before, only the device removed counted. Any other failure was logged and its fence completed as if the work had
been done, so a readback could return pixels that were never written. No command buffer has failed on any GPU this
ran on; the driver test has mtl12 treat a command buffer as failed (`FailNextSubmissionForTest`) to check the path
(`tests/README.md`, "Metal driver harness").

## Apple's paravirtual GPU

A macOS virtual machine's GPU ("Apple Paravirtual device": GitHub's runners, and any VM made with Apple's
Virtualization framework) has a driver that passes Metal's commands to the host, and that driver has a bug the game
runs into. It writes each encoder's commands into chunks of 131,072 bytes. When an encoder ends with its last chunk
within four bytes of full, the first command of the next encoder made on the same command buffer is tested against
the old chunk's fill, found not to fit the new, empty chunk, and the driver stops the program at an assertion of its
own (`-[AppleParavirtCommandBuffer endCurrentChunk]`, "`_commandCurrentStorage.currentOffset`"). A race's 3D view is
one pass of about 600 draws and 350,000 bytes, and a draw's size varies, so by the arithmetic of it the pass ends on
such a fill about once in 16,000 frames: the first time it happened was 80 frames into Aerial Highlands, in the copy
of the screen that follows the 3D view. Found by running the failing frame under `lldb` on a runner and reading the driver's code around
the assertion; the sizes were measured there (macOS 15.8, with shader validation: a draw 350 to 620 bytes with the
buffers it binds, a pipeline state 68, a texture 20, a new pass 850, a copy up to 200).

An encoder that never fills a chunk can't end on a full one. So on this device (`CreateDevice` knows it by the class
of the device, `AppleParavirt...`) a list ends a pass after 48 draws and a blit encoder after 96 copies, and the
next draw or copy begins another, which is the same as far as the result goes: mtl12's passes load and store
everything. Even at twice the measured sizes that stays under a chunk. Other devices are not affected and get no
limit. With the limit, 213 replays (436,000 frames) ran without the assertion, where the estimate without it is
one stop in every eight replays. `-mtldebug` made the same bug show sooner, because Metal then ends every pass with
a small blit encoder of its own; it runs with the limit too.

## What can differ from the other backends

As on Vulkan, the driver's logic, shaders, textures, and states are the same, and what is left is arithmetic: another
shader compiler rounds differently in the last bit, and depth is 32-bit float where Direct3D's is 24-bit. Besides:

- **Depth bias** on a float depth buffer is in units of the depth value's own precision rather than of 1/2^24, as on
  Vulkan devices without 24-bit depth.
- **Strips** always restart at the index 0xFFFF (or 0xFFFFFFFF) in Metal. Direct3D 12 only does when the pipeline
  state says so, and the driver's never do; it would take a strip of 65,536 vertices to tell.
- **`SV_VertexID`** counts from the draw's first vertex in Metal, as in Vulkan, and from zero in Direct3D. The
  driver's only use draws from vertex zero.

### What the M4 Pro's validation found

Three things, none of them Metal's, all in code that every hardware renderer of the game runs:

- **The sky dome's caps had no texture coordinates.** `HWR_SkyDomeVertex` never wrote them, so the two fans that
  close the dome sampled the sky texture at whatever `malloc` had left in the vertex array: infinities and
  not-a-numbers in 21 maps' replays with that build, zeros with another. That was the frame that had changed between
  two runs on the runner: Neon Resort at level time 700, where the camera is pitched up on a slope, had 198 dim
  pixels in the top 43 rows of the black sky in one run of four. Giving the caps random coordinates on the M4 Pro
  (temporary instrumentation) changes 202 pixels in the top 41 rows of that frame, over the same columns, and none
  of the frame at 650. The caps now get the middle of the texture's first texel. Ten more replays of Neon Resort to
  700 on the M4 Pro gave ten identical frames, and seven on the Intel GPU seven.
- **A sprite two near planes from the camera** has a clip-space z of exactly zero, where the sprite shader's
  clipping hack (`80 / z`) is infinite. One replay had one for a frame (Gust Planet), another one too (Malign Egg
  Shrine). The shader now divides zero like a tiny positive number.
- **A sprite without height**, in a sector whose light changes at 3D floors, got texture coordinates divided by its
  height. Seven maps' replays have one. It isn't drawn any more.

None of the three changed a pixel of the 1,002 frames on the M4 Pro: a sprite at the pole or without height shows
nothing either way, and no captured frame of that build had a cap in view with anything but zeros behind it.

### What a person at a Mac should look at

Ten minutes at a Mac with its screen unlocked would settle most of what the logs can't. Start the game from a

2. **Sharpness on a Retina display.** Options → Video → Advanced → Renderer: look at the same scene in Software and
   in VibeRant Metal. Right: equally sharp (neither is pixel-sharp on a scaled Retina mode). Wrong: one clearly
   softer or blockier than the other.
3. **Colors on a MacBook's own display.** The same scene in both renderers again, or the title screen. Right: the
   same colors. Wrong: VibeRant Metal more saturated (reds and greens above all). The log's line "colors are matched
   to the display" should name the window's color space and "(the system gave it)" or "(set here)".
4. **Change the renderer in fullscreen**, Software and back, twice. Right: after a second or two of the system's
   animation the game is on the whole screen again and the keys work without a click; Mission Control (Control-Up)
   shows one Space for the game and no empty one. Wrong: the desktop, a black Space, the game in a window, or keys
   that do nothing. The log has a line for each window's way into and out of a Space.
5. **Quit from fullscreen and from a window**, through the menu. Right: the game is gone. Wrong: an empty window
   that flashes or flies into a Space as it goes.
6. **Hide it and bring it back** while a race or a replay runs: minimize to the Dock and restore, Command-H and
   back, another Space and back (Control-Left and Right), a window dragged over it and away, lock the screen and
   unlock it, close the lid and open it. Right: the picture is moving again at once each time. Wrong: a picture
   that stands still while the sound goes on. Afterwards the presenter's last line in the log says how many frames
   "went to a window the system called out of sight": if that is a large number although the window was in plain
   sight, the system's report was wrong and the safeguard was what kept the picture going, which is worth telling.
7. **`vid_wait` on and off** (the console, or Options → Video): on, the motion is even and nothing tears; off, the
   frame rate is higher and tearing is possible.
8. **Options → Video → Advanced with Software selected**: the lines above the Renderer row should describe VibeRant
   Metal, not VibeRant D3D and Direct3D 12.
9. **A second display, if there is one**: drag the window across, and go fullscreen on each. Right: the picture
   fits each display. Wrong: a stretched or offset picture after the move.
