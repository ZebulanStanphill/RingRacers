# Changes from Ring Racers v2.4

Changes from vanilla [Ring Racers v2.4](https://github.com/KartKrewDev/RingRacers/releases/tag/v2.4). This repository adds engine commits to upstream's `maintenance-2.4`. SDL changes live in `uwp/patches/sdl-angle.patch`, `uwp/patches/sdl-controller-duplicates.patch`, and `uwp/patches/sdl-egl-surface-handoff.patch`. `uwp/` holds the Xbox app's launcher and `uwp/build.ps1` builds it. The app was a separate repository, [ringracers-uwp](https://github.com/ZebulanStanphill/ringracers-uwp), until its history was merged here. Earlier entries say "the fork" for the engine.

Unless stated otherwise, changes apply only to UWP builds (`SRB2_CONFIG_UWP`, which defines `_UWP`). The GL2 RHI's general call reductions and OpenGL ES support, colormap caching, most Software optimizations, UDP error handling, Lua userdata set, state bookkeeping, and interpolation-list changes apply to every platform built from the fork. Legacy GL entries identify other shared changes.

Game logic results are unchanged. Optimizations do the same work in less time, preserving replay, netplay, and ghost behavior. The *(works on Xbox)* and *(untested on Xbox)* markers include qualifiers for partial coverage. Confirmation refers to Xbox One X, including features confirmed before the driver replacement and carried forward unchanged. Build, CI, and tools have no Xbox marker.

## Platform and build

- **UWP library and launcher.** `SRB2_CONFIG_UWP` and the `ninja-x64_windows_uwp_vcpkg-release` preset build a static game library without a Git revision suffix in its executable name. The launcher starts it through `SDL_WinRTRunApp`, caches the CoreWindow on the UI thread, and reports the process memory budget; the launcher builds on [worleydl's port](https://github.com/worleydl/ringracers-uwp), rebased onto v2.4.
- **Dependencies and CPU.** SDL2 and libuwp come from [worleydl/uwp-dep](https://github.com/worleydl/uwp-dep). The game targets Xbox One's Jaguar CPU with `-march=btver2`, also supported by Xbox Series X|S; Jaguar has no FMA, preserving the floating-point behavior of other x64 builds.
- **Direct3D 12 option.** The CMake option `SRB2_CONFIG_VIBERANT_D3D` builds VibeRant D3D (`src/hardware/r_viberant`) and defines `HAVE_VIBERANT`, which guards every engine call into it. The option is available on Windows. Linux builds use the Vulkan backend (see **VibeRant Vulkan**), and macOS builds use the Metal backend (see **VibeRant Metal**). Renderer code the driver depends on (portals, water surfaces, shader fog, per-pixel distortion, and palette rendering) is under `HAVE_VIBERANT` as well and compiles without `_UWP`, which the Linux CI job checked before Linux built the driver itself. This prepares the driver for Windows desktop without changing UWP behavior. Driver-dependent rendering (the level walk, portals, sky claims, void walls, wall light slices, fog, water states, post-processing, and rolled sprites) checks `HWR_VibeRant()` at runtime so both drivers can ship in one build. UWP uses a constant and behaves as before *(works on Xbox, walls crossed by 3D floors included)*.
- **VibeRant D3D on Windows desktop.** The driver can draw the finished frame scaled to fit a window-sized swap chain, with linear filtering and black bars (`screen_scaling::FitRect`), when the system leaves scaling to the presenter. UWP builds never ask for it; their frame placement only gains a second sampler *(Screen Scaling still works on Xbox)*. The driver presents on ordinary Windows windows too *(tested under Wine only)*: the presenter (`d3d_present_win32.cpp`) puts its swap chain on a child window of the game's window, which never takes input or focus and goes away when Software takes over, so the game window's OpenGL contexts are untouched. The UWP presenter is unchanged. A desktop build with the driver also keeps OpenGL: Video Options > Advanced > Renderer offers Software, VibeRant D3D, and Legacy GL, and `-d3d12` starts with VibeRant D3D as `-opengl` starts with Legacy GL. One hardware driver is used per run of the game: switching between Software and it is immediate, and choosing the other hardware renderer is saved and takes effect at the next start, as the popup and console report. UWP builds keep their two choices *(works on Xbox)*. Windows desktop builds made with MSVC or clang-cl include the driver by default; MinGW builds don't, as its shaders are compiled with the Windows SDK's `fxc`.
- **Fork version** *(works on Xbox)*. On every platform, the title screen, the `version` command, and one line of the startup log show the fork version alongside Ring Racers', as `v2.4_z1`. A development build shows a version like `v2.4_z0-dev (1a2b3c4d)`, using `FORKVERSION` from `src/fork_version.h` (`z0` before the first release) and the commit. To build a release, Git must be available, the checkout must be clean, and the commit must have a tag matching its nonzero fork version, such as `2.4_z1` (an optional leading `v` is accepted). A release commit raises the fork version, and the Build workflow fetches tags so it can recognize the release commit. Netplay, replays, and Lua's `VERSIONSTRING` keep the vanilla version. The letter was a capital `Z` when this was confirmed on Xbox; the lowercase `z` is untested there.
- **Package.** The package version appends the Build workflow's run number to Ring Racers' version (for example, 2.4.0.123), so later Build workflow runs always have newer versions. Local builds end in 0. Windows treats installing an older build over a newer one as a downgrade. The project, executable, linker map, and package are named `ring-racers-ze` (the package file is `ring-racers-ze_<version>_x64.msix`), and the `uwp/tools/` scripts read the module name of earlier `ringracers-uwp` builds too, so their logs and profiles still work. The Build workflow checks the version in the finished package. The app is shown as "Ring Racers ZE" (in the app list and in the launch-time message about Dev Home's App type), with the package identity `ZebulanStanphill.RingRacersZE`, publisher `CN=ZebulanStanphill` (the CI certificate's subject), and publisher name "Zebulan Stanphill". Windows installs it as a separate app alongside the earlier "Ring Racers" package. Uninstalling the earlier app keeps the config and saves on the USB drive (`E:\ringracers\ringracers`) and deletes that app's internal copy of the game data. The new app makes its own copy. The manifest requests file system, removable storage, network, expanded resources, and microphone access for voice chat. The `expandedResources` capability is documented by Microsoft as granting Game Mode resources on Xbox: CPU cores reserved for the app and a memory partition of at least 4 GB, where plain apps get a share of the cores, 1 GB, and, on Xbox One, no Direct3D 12. On an Xbox One X the game got Direct3D 12, the same 5 GB memory budget, and the same race speed with Dev Home's App type set to App or to Game, so the type doesn't need changing; in Game mode, the SDL patch handles the console reporting each controller twice. Runtime DLLs are not copied beside the static library. The small logo (`Square44x44Logo`, the icon shown at small sizes) is Dr. Robotnik's face *(untested on Xbox)*, taken from the game's own icons. The 88-pixel version is the macOS icon's detailed face over a night sky: that icon is 64×64 pixel art, and its middle 44×44 pixels, which lie inside the icon's rounded shape, are doubled without smoothing to fill the square. The 24-pixel version is the simpler 16×16 face of the Windows desktop icon on a transparent background. The small logo was a shrunken copy of the box art, which is unreadable at that size; the medium tile keeps the box art.
- **Audio** *(works on Xbox)*. The audio driver is WASAPI instead of DirectSound.
- **Build script.** `uwp/build.ps1` builds the engine and SDL2 with the SDL patches in `uwp/patches/`, verifies ANGLE's download with SHA-256, and generates the launcher solution.
- **CI.** The Build workflow builds the Xbox app; the Tests workflow checks for retired driver names (`tests/check-retired-names.py`) and for changes inside upstream files without a `[ZE]` or `[UWP]` comment (`tests/check-change-markers.py`, against upstream's `maintenance-2.4`), and runs the native regression tests with ASan/UBSan, a `warp` job that compiles the 98 translated add-on shader stages for Shader Model 5.1 and runs the Direct3D 12 WARP harness with the debug layer and GPU-based validation, a `vulkan` job that runs the same driver test on Vulkan (see **VibeRant Vulkan**), a `metal` job that runs it on Metal on a macOS runner (see **VibeRant Metal**), a Linux build with the driver's Vulkan backend, a macOS build with its Metal backend, and a Windows desktop build with both backends beside OpenGL; the Windows desktop build (not UWP, `clang-cl` and vcpkg) is uploaded as `windows-desktop` and the macOS app as `macos-app`, and the `warp` job also runs the desktop presenter on a hidden window. Each test was checked by mutating the production code it covers. Tests that ran identical code, duplicated a WARP pixel check, or only parsed a debug command were removed. Negative controls assert their specific rejection in-process instead of passing on any failure; WARP keeps six shader and feature mutants as separate processes and checks every other oracle with a self-test and a registry of the scenes that ran. The WARP job caches its glslang and SPIRV-Cross build per runner image. [tests/README.md](tests/README.md) describes coverage and limits.
- **Build artifacts.** The `build` job uploads the `ring-racers-ze-uwp` artifact. The `-uwp` distinguishes it from the Tests workflow's `windows-desktop` and `macos-app` builds. The artifact contains a sideloadable `.msix` signed with a throwaway certificate, that certificate (an Xbox in Developer Mode doesn't need it; a Windows PC does), and the linker map (`ring-racers-ze-uwp-symbols`). Actions use Node.js 24 releases, and Visual Studio's Developer PowerShell exports the x64 environment to later steps.
- **Profile-guided optimization** *(works on Xbox)*. Run the Build workflow manually with `pgo_generate` to make an instrumented package (`ring-racers-ze-uwp-pgo-instrumented`). It records which engine code runs and saves the recording to `E:\ringracers\pgo\` at a clean quit, before the app is suspended, and on the `pgo_dump` console command. Recordings committed to `uwp/pgo/` are merged with the `llvm-profdata` matching the compiler and used by every later build to lay out and inline the engine's hottest code; without any, builds are unchanged. It doesn't change what the code does, so netplay and replays stay compatible. [docs/uwp-pgo.md](docs/uwp-pgo.md) describes collecting them. `uwp/pgo/` holds one recording from the instrumented build of 6b2cff1d2 on Xbox One X: about 67 minutes in VibeRant D3D at 1920x1080, with offline races against 15 bots (Joypolis, Metropolis, and others), online races, Time Attack, and menus. With it, a 16-racer Joypolis race on Xbox One X took 16.2 instead of 18.5 ms of game logic per tic and 12.2 instead of 16.8 ms per 3D frame at the median, and ran at 23.2 instead of 15.1 frames per second (same engine code built with the November 8 recordings; five races against three).
- **Shader smoke test.** The [installable PK3](tests/addons/shader-smoke/README.md), uploaded by the Tests workflow as `shader-smoke-test`, supplies shader-only checker and water-ripple effects without gameplay scripts or replacement assets.
- **Renderer test map** *(works on Xbox)*. The [installable PK3](tests/addons/renderer-test/README.md), lets you drive freely around a generated UDMF map (`map RR_RENDERTEST`). The Tests workflow uploads it as `renderer-test-map`. It has a room each for fog, overlapping water and heat haze, polyobject ripples, wall light slices, translucent ordering, and brightmaps, a rainy hall whose sky shows a separate, brightly lit skybox room where rain must not be drawn (judged from a covered sky pit off the hall's east end, which has no rain of its own), and item boxes that become a sprite-textured model when its `models/` folder is installed beside `ringconfig.cfg`. It has no finish line, checkpoint, or waypoints *(their removal is untested on Xbox)*, so the round never ends, the item boxes show from the start, and the hand that points out the wrong way never appears; the engine logs three errors about the missing waypoints and finish line each time the map loads, as expected. The add-on removes AI racers from this map, including bots added after loading. Local split-screen players, other maps, and bot settings are unaffected. Its scenery objects replace any game object that already uses their editor numbers when the map loads, logging which object it was. Its Encore remap swaps red and blue. Without the remap, Encore only mirrors the screen. A wing of nine numbered rooms off the Brightmaps room *(works on Xbox)* covers the Software-matching fixes that no base-game map exercises: a fog-style line beside an ordinary translucent one, two rooms of fullbright sprites with and without `colormapfadesprites`, `RF_SHADOWDRAW` objects on flat ground and a ramp, translucent overlay sprites beside a plainly translucent one, a pad (and the `rendertest_darkness` console command) that triggers level darkening beside areas at three light levels, a tree-line texture between two skies as at Municipal Meadow's skybox edge, a wall of numbered bands with a marked standing spot for comparing the renderers' view width in two-player split-screen, two bays of ordinary, semibright, and fullbright posts at sector light 128 and 96 (the darker one doubles as a dark-sector check), and the tree line again under a sky ceiling lower than its tips. Enable `cheats on` before using the map command. The water room has a long descent into a 608-unit-deep pool, a large flat bottom for submerged chase-camera views, and a far ramp back to the dry heat-haze ledge. `build.py` generates every texture, sprite, and the map from code and runs ZDBSP, which CI builds from source to verify the committed PK3; it ships the sign's brightmap as a Doom patch and gives the orb's brightmap the orb's exact transparency, since vanilla Software can't read a PNG texture brightmap and walks a sprite's and its brightmap's columns together.

## VibeRant renderer

- **Small-texture atlas** *(works on Xbox)*. Less slowdown when many color-changing sprites appear, such as multiplayer invincibility: VibeRant shares texture pages instead of creating a resource for every sprite translation. In online races on an Xbox One X, resource creations fell from about 150 to about 6 every five seconds. The atlas frees empty pages, such as after a level change, and keeps one ready *(untested on Xbox)*. Previously, pages only accumulated, reaching 35 (560 MB) in a two-hour session. `gr_textureatlas` (On by default) flushes textures when toggled for comparison. See [the atlas notes](docs/viberant-texture-atlas.md).

### VibeRant D3D

- **Renderer and default** *(works on Xbox)*. VibeRant D3D is the default for new configs. Valid saved renderer choices still apply. It draws upstream Legacy GL through `src/hardware/r_viberant/`. Startup logs `VibeRant backend: D3D12`, and a failed driver start falls back to Software.
- **Shaders** *(works on Xbox)*. `fxc` compiles the built-in HLSL at build time for Shader Model 5.1 with an embedded root signature. Xbox One X exposes feature level 12_0 and Shader Model 5.1; Xbox One has no Shader Model 6. The shader compile commands define no `_UWP` or Direct3D macro, since the HLSL reads none; its one conditional, `RR_VULKAN`, is set only when compiling to SPIR-V for the Vulkan and Metal backends.
- **Presentation** *(works on Xbox)*. Starting VibeRant D3D takes the window from ANGLE (with the first drawn frame instead if no ANGLE context exists yet, as with `-opengl`), and each frame is then copied into the driver's own three-buffer flip-model swap chain and shown at once, with `vid_wait` as the sync interval and a frame latency of 2. The presenter letterboxes the frame if its aspect ratio differs from the window's. A CoreWindow takes one swap chain at a time, so `uwp/patches/sdl-egl-surface-handoff.patch` lets the driver destroy ANGLE's window surface, and recreate it when Software is chosen. If taking the window fails at startup, the game falls back to Software; a failure to take it with the first frame, resize the swap chain, or give the window back stops the game with an error. [Diagnostics notes](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/viberant-diagnostics.md) describe the logs.
- **GPU synchronization** *(works on Xbox)*. The swap chain shares the driver's queue, so frames need no synchronization with ANGLE. The 2026-10-16 Xbox logs confirm the swap chain taking the window, giving it back for Software, taking it again, resizing, and letterboxing.
- **Resources and constants** *(works on Xbox, including 3D models and mipmaps)*. Drawing constants use a root-CBV ring, and fence completion controls resource and descriptor reuse, resizing, and shutdown. Models, indices, and sky buffers use persistently mapped 4 MB upload arenas; the driver generates RGBA8 mip chains on the CPU and skips redundant topology, stencil-reference, and viewport changes.
- **Texture heaps** *(works on Xbox)*. Textures use shared 16 MB heaps with 4 KB or 64 KB alignment, quarter-octave size classes, and a 4 KB guard after each reported allocation; textures exceeding the 4 MB class limit including the guard, or failing placement, get a dedicated heap with a spare 64 KB page. The guards protect neighboring or final texels from corruption by Xbox One's resource-state word. Committed textures remain a logged last resort. The 2026-10-16 Xbox log shows dedicated heaps with zero committed textures. See [texture placement](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/viberant-texture-placement.md).
- **Pipeline prewarming** *(works on Xbox)*. One worker prewarms 36 built-in shader pairings without blocking draws. `VibeRant D3D: prewarmed` and the first 64 main-thread `PSO #` cache misses report creation cost.
- **Add-on shaders** *(works on Xbox)*. Pinned glslang and SPIRV-Cross translate `SHADERS` GLSL into Shader Model 5.1 HLSL for polygon, sky, and model layouts; `D3DCompile` compiles it, and load-time pipeline validation rejects invalid programs in favor of built-ins. Missing stages use shared built-in GLSL, Ignore custom shaders keeps built-ins, and custom sprite stages also cover clipped sprites. Compiler notices ship in `Licenses`.
- **Custom water and shader limits** *(works on Xbox)*. Custom water color keeps built-in refraction through a composite variant; a custom vertex stage requires a whole-viewport capture, while capture/variant failure or Reduce VFX uses normal blending without refraction. Underwater/heat postprocessing stays built-in, arbitrary uniforms use their initializer or zero without engine setters, and uninitialized uniform arrays and extra vertex attributes remain unsupported; see [add-on shader notes](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/viberant-custom-shaders.md).
- **Division by zero in sprite clipping** *(seen and fixed on a Mac with an M4 Pro; untested on Xbox)*. The shared sprite shader now handles zero clip-space z on every backend. To keep sprites from poking through floors, the shader pulls each vertex's clip-space z in by `80 / z`, as OpenGL's does. The quotient is infinite at exactly zero, about two near planes from the camera. One replay in 213 had a sprite there for one frame (Gust Planet). The sprite is invisible on either side of zero, so the picture is unchanged. GPUs need not handle infinite vertex positions, and Metal's shader validation reports them. The division now uses a tiny positive value at zero, placing the vertex in front of the near plane like its neighbors on that side.

### VibeRant Vulkan

Not on Xbox: these entries are for Linux and Windows PCs, and say what they were tested on.

- **VibeRant Vulkan** *(works on Linux with an AMD Radeon (RADV); the Windows build is tested under Wine only; other GPUs untested)*. VibeRant Vulkan is the hardware renderer for platforms without Direct3D 12, and a second choice on Windows. It shares the VibeRant driver. `src/hardware/r_viberant/vulkan` implements the dozen Direct3D 12 interfaces the driver uses (about 70 methods) on Vulkan 1.1. Both backends share drawing code, shaders (`shaders.hlsl`, compiled to SPIR-V by glslang), textures, and states, so driver fixes apply to both. Everything listed for VibeRant D3D applies: palette rendering, portals, fog, water, wipes, brightmaps, add-on shaders, screen effects, Screen Scaling, and the rest. [docs/vulkan-backend.md](docs/vulkan-backend.md) describes the mapping. Vulkan is loaded when the renderer starts, so a system without it, or without a usable device, falls back to Software with a console message. `-vulkan` starts with it, and `-vkdebug` adds Vulkan's validation layers, whose messages go to the log.
- **Same picture as VibeRant D3D** *(measured on one PC: Radeon Vega 10, RADV, with VibeRant D3D running under Wine on the same GPU)*. The Windows build drew the same 1,002 frames with each backend (five moments of the first staff ghost of each of the 213 maps, taken with the frame capture mode), and they were compared pixel by pixel. In the median frame 0.08% of the pixels differ, in 95% of the frames fewer than 0.18%, and in the worst 1.4%. What differs is arithmetic in the last bit: the two backends' shader compilers don't round identically, so a pixel whose texture coordinate falls on the edge between two texels can take the other texel. Setting those pixels aside, 958 of the frames differ in at most 0.02% of their pixels and four in more than 0.1%: two of Daytona Speedway, where a fine texture is far away, and two where surfaces lie in the same plane and depth rounding decides which one shows (a wall in Ice Paradise that Software doesn't show and Legacy GL shows whole, which VibeRant has since stopped drawing (see **Walls of sectors whose ceiling is below their floor**), and an effect in Haunted Ship that lasts one tic). The Linux build's frames against the same VibeRant D3D frames give the same figures. Vulkan's validation layers reported nothing in races on 43 of the maps, in the menus, or while the window was resized, floated, tiled, and made fullscreen. Direct3D 12 under Wine is itself translated to Vulkan, so this compares the two backends on one GPU, not against Microsoft's Direct3D 12 or the Xbox. Devices without 24-bit depth (AMD's) use 32-bit float depth here.
- **Vulkan window** *(works on Linux under Hyprland; the Windows build under Wine)*. The game's window is OpenGL's, for Software's frames, and a window can't be both OpenGL's and Vulkan's, so VibeRant Vulkan presents on a second window that takes the first one's place, size, fullscreen state, title, icon, and input, and gives them back when Software takes over. Where VibeRant Vulkan is the default, the OpenGL window stays hidden until a renderer that needs it is the one running, so starting the game shows one window. The swap chain is the window's size and the frame is placed in it as on Windows desktop: Screen Scaling's Integer and 1:1, or scaled with linear filtering to fit.
- **Renderer setting** *(works on Linux)*. Options → Video → Advanced → Renderer lists **VibeRant Vulkan** where the build has it: Software, VibeRant Vulkan, and Legacy GL on Linux, and Software, VibeRant D3D, VibeRant Vulkan, and Legacy GL on Windows. The description and options header use the same name. Switching between Software and the running hardware renderer is immediate; another hardware renderer, including VibeRant's other backend, takes effect at the next start, as before. The saved value is `renderer "VibeRant Vulkan"`.
- **Default renderer on PCs** *(works on Linux)*. A new config starts with VibeRant Vulkan on Linux and with VibeRant D3D on Windows desktop builds that have it, instead of Software. Saved renderer choices still apply.
- **Driver test on Vulkan** *(passes on the Radeon and on lavapipe in CI)*. The driver's pixel test (`tests/viberant-driver.cpp`, the one the `warp` job runs on Windows) also builds on Linux against the Vulkan backend (`tests/run-vulkan.sh`): the same 114 scenes and six negative controls, with any Vulkan validation error failing the run in place of Direct3D's debug layer. CI runs it on lavapipe, Mesa's CPU device. One scene starts from a different color on Vulkan. AMD's hardware rounds down when the exact value is just below the next level, putting the grouped water scene's expected green one step outside its tolerance on the Radeon. A starting color away from that boundary tests the same behavior on every device. The test found that the backend reported Vulkan's own (smaller) alignment for textures where the driver expects Direct3D's 4 KB and 64 KB placement classes, which made the driver give 18 of 376 small textures a heap each; it now reports the classes.
- **Build options.** `SRB2_CONFIG_VIBERANT_VULKAN` builds the backend and defines `HAVE_VIBERANT_VULKAN`. It defaults to on for Linux and for Windows desktop builds made with MSVC or clang-cl. Those Windows builds include both backends (`HAVE_VIBERANT_D3D` marks Direct3D 12 itself). UWP never builds the Vulkan backend. `HAVE_VIBERANT` now means the driver is built, with either backend. Configuring downloads pinned Vulkan-Headers, volk, and, off Windows, Microsoft's MIT-licensed DirectX-Headers, beside the glslang and SPIRV-Cross the driver already used; `-DSRB2_CONFIG_VIBERANT_VULKAN=OFF` builds without any of it.

### VibeRant Metal

Not on Xbox: these entries are for Macs. It has run on three GPUs: the virtual one of GitHub's macOS runners ("Apple Paravirtual device", macOS 15 on Apple silicon), an Apple M4 Pro (a Mac mini, macOS 27), and an Intel Iris Plus Graphics 645 (a MacBook Pro with a Retina display, macOS 15). The two Macs were tested over the network with nobody at them, by automated replays under Metal's validation, so "works" below means that the log and the frames read back from the driver say so. The owner has since played it by hand on the MacBook Pro (2026-11-16), as the tags below say where that covered an entry. [docs/metal-backend.md](docs/metal-backend.md) says what was tested and what wasn't.

- **VibeRant Metal** *(runs on GitHub's macOS runners, an M4 Pro, and an Intel Iris Plus 645; played by hand on the Intel MacBook Pro)*. VibeRant Metal runs directly on Apple's Metal. `src/hardware/r_viberant/metal` ("mtl12") implements the same dozen Direct3D 12 interfaces in Objective-C++, so it shares drawing code, shaders, textures, and states with VibeRant D3D and VibeRant Vulkan. It does not use MoltenVK. The shaders are the SPIR-V the Vulkan backend is built with, which mtl12 turns into Metal Shading Language with SPIRV-Cross when a pipeline state first needs them; the code that makes and patches that SPIR-V moved out of the Vulkan backend into a file both share, without changing what VibeRant Vulkan does. Metal's clip space, viewport, depth range, and winding are Direct3D's, so nothing is flipped. Depth is 32-bit float with 8-bit stencil, since Apple's GPUs have no 24-bit depth. Heaps hold no memory (every texture is its own), timestamp queries read as zero, and a sampler's level-of-detail bias isn't implemented (the driver never sets one). [docs/metal-backend.md](docs/metal-backend.md) describes the mapping. `HAVE_VIBERANT_METAL` is the build define, and `Core_Metal()` identifies the backend to the driver. `-metal` starts the game with it, and `-mtldebug` has each failed command buffer say which of its passes failed (Metal's own validation is turned on with its environment variables, `MTL_DEBUG_LAYER` and `MTL_SHADER_VALIDATION`). If Metal has no device, the game falls back to Software with a console message. If the presenter cannot create its window on the first frame, the game stops with an error.
- **Driver test on Metal** *(passes on GitHub's macOS runner, an M4 Pro, and an Intel Iris Plus 645)*. The driver's pixel test (`tests/viberant-driver.cpp`) builds on macOS against the Metal backend (`tests/run-metal.sh`): the same 118 scenes with the same expected colors as on Direct3D 12 and Vulkan, none skipped or adjusted, and the same six negative controls, each rejected by its named oracle. Metal's API validation and shader validation are both required, and the debug layer's warnings stop the run as its errors do. After the scenes, the test wraps a texture like a drawable's, clears it, and reads it back, and presents a drawable of a layer that is on no window, which checks the presenter's hooks without a window. Metal code can't be built off macOS, so CI runs the test in the `metal` job.
- **Metal window** *(works on the runner: a window, fullscreen, a window larger than the display, the keyboard; on the Intel MacBook, by its log: a window, fullscreen and back, another video mode, `vid_wait` at the display's 60 Hz, and a Retina display's point-sized drawables; on the M4 Pro's locked screen: the same without fullscreen in a Space and without `vid_wait`; by hand on the Intel MacBook: fullscreen, minimizing, Command-H, Spaces, locking, the lid, and `vid_wait`; untested with more than one display)*. As with VibeRant Vulkan, the game's window is OpenGL's, for Software's frames, so VibeRant Metal presents on a second window (`SDL_WINDOW_METAL`, a `CAMetalLayer`) that takes the first one's place, size, fullscreen state, title, icon, and input, and gives them back when Software takes over (`src/hardware/r_viberant/metal/mtl_present.mm`). The layer's drawables are the window's size in points, not the display's pixels, because the game's window isn't a high-resolution one: on a Retina display the system upscales both Metal and Software frames. The frame is placed in the drawable as on the other desktop presenters: Screen Scaling's Integer and 1:1, or scaled with linear filtering to fit. `vid_wait` is the layer's display sync. A window that is minimized, hidden, on another Space, or covered isn't presented to, since its layer would make every frame wait a second for a drawable that doesn't come; the game runs on meanwhile.
- **No empty window at quit** *(by the log on both Macs, their screens locked, and on the runner; quitting through the menu worked by hand on the Intel MacBook)*. Quitting VibeRant Metal closes its window and leaves the OpenGL window hidden. Previously, quitting restored OpenGL as if switching to Software, briefly showing a blank window that could start moving to its own Space when quitting from fullscreen. The presenter logs the OpenGL window's state as reported by SDL. `capture.py` fails a run that ends with VibeRant Metal unless that is "hidden". With the old behavior put back, the same run failed with "the game's OpenGL window was shown as the game quit".
- **The same colors as Software on a wide-gamut display** *(by the log on both Macs, the MacBook's display being the wide-gamut one; not compared on any screen)*. The Metal presenter uses the same color space as its window, so the system can match colors to the display as it does for Software. SDL gives its windows the sRGB color space, and the system converts the OpenGL output used by Software for the display. A Metal layer without a color space is not matched, Apple's documentation says, which on a MacBook's P3 panel would show VibeRant Metal's colors more saturated than Software's. The presenter logs both the layer's and the display's color spaces. On both Macs, the system already gave the layer that color space. The presenter restored it when deliberately removed. With the restoration disabled, `capture.py` failed the run.
- **A picture that can't freeze on a wrong "hidden" report** *(the decision passes its test; on a runner's screen and behind both Macs' locked screens the log shows frames going out with nothing held up; no wrong report has been seen, so the case itself is acted out with `-mtlblind`; hiding and restoring the window during a race worked by hand on the Intel MacBook)*. VibeRant Metal doesn't present every frame to a window the system calls out of sight, because the layer of such a window gives no drawables and asking it waits a second per frame. An incorrect visibility report could leave the picture frozen while the race continued. A window called out of sight now still gets frames for as long as asking the layer isn't expected to wait: Metal reports when the system is done with each presented frame, the layer has three drawables, and a frame is presented while at most one earlier one is unaccounted for. While the system takes frames the picture keeps moving; when it takes none, two go out and no more; and if it hands drawables back slowly, frames go to that window less and less often. Where Metal's reports come late, as on a virtual machine's display, only that last rule applies. `-mtlblind` makes the presenter act as if its window were out of sight, for `capture.py`'s `blind` scenes, and `metal_present_seen` runs the decision against a model of the layer and the display. Needs macOS 10.15.4 for the reports; older systems behave as before.
- **A replay sweep fails if its frames weren't presented** *(works on an M4 Pro Mac mini behind its locked screen, where the first version of this failed a sweep without `-mtlunseen` and passed one with it)*. `capture.py sweep` printed how many frames the presenter said it had presented and passed whatever the number was, although `tests/README.md` said a run failed without any; and the frames a sweep collects are read from the driver's screen, so they can't tell either. In every mode, a run fails if no frames were presented or if it missed more than a few frames and more than a twentieth of the total. The frames a new window skips before the system calls it visible (six at most on the runners) pass.
- **`-mtlcheck`: is the frame in the drawable?** *(works on an M4 Pro, where 7,816 drawables of 213 replays held their frames and one blanked on purpose failed; on an Intel Iris Plus 645; and on the runner)*. With `-mtlcheck`, the presenter reads back a window's first three drawables and every sixtieth after placing their frames. It logs whether each frame matches Screen Scaling's rectangle with black around it, comparing pixels at native size and block means when scaled. Several `capture.py` scenes use the check and fail if a drawable differs. Sweeps can use it too. It tells a window that gets the frame from one that gets black or swapped colors, which screenshots read from the driver's screen never could; it does not tell what the display showed. `metal_present_check` tests the comparison and `metal_capture_judging` tests how `capture.py` reads a log.
- **Drawable wait times in the log** *(read on an M4 Pro Mac mini behind its locked screen)*. The presenter logs each window's average and worst drawable wait times on its last line. `capture.py hardware` reports those times for the timed scenes. The driver's periodic performance lines, which had the figure, are only logged on Xbox.
- **Metal window creation error** *(a wording fix; the case has not occurred anywhere)*. The README now distinguishes a missing Metal device, which falls back to Software, from a failure to create the presenter's window. When the device is there and only the presenter's window can't be made, the game stops with an error at its first frame, as it does on Vulkan, and the error now names `-software` before the setting in the menu the game never reaches.
- **Changing the renderer in fullscreen, by the log** *(works on GitHub's macOS runners, by the log and by pictures of the screen; on a Mac, see the next entry)*. A fullscreen game window is in a Space of its own on macOS, and a change of renderer trades two windows. The presenter now logs each window entering and leaving a Space, and `capture.py` has scenes that change the renderer in fullscreen in both directions (`fullscreen-switch`, `fullscreen-switch-software`). On a runner the transitions come one after the other, never two at once: one for Software to VibeRant Metal, two for the way back, and the game is on the whole screen after each. Nothing in the handover was changed. `capture.py hardware` no longer runs its Space scenes behind a locked screen, where the system makes no Spaces, and says so instead of failing them.
- **Changing to VibeRant Metal in fullscreen no longer leaves the game on another Space** *(works on an Intel MacBook Pro, by the log and by hand: its owner saw the fault, and then the fix work)*. Switching from fullscreen Software to VibeRant Metal could leave the game on a Space the display wasn't showing. Hiding the fullscreen OpenGL window made SDL take it out of its Space, show it, put it back into a Space, and take it out again. The presenter now takes that window out of its Space and hides it before it makes the Metal window, so there are two transitions, one after the other, and the game is on the display at the end. `capture.py` fails a run in which the OpenGL window leaves a Space while the Metal window is in one.
- **A window for a resolution larger than the screen** *(works on an Intel MacBook Pro with VibeRant Metal, by the log; with Software by reading the code)*. macOS gives no window that is taller than the screen has room for: it cuts the height and leaves the width. On a screen of 1440x900 points, a resolution of 1920x1200 in a window got a window of 1920x804, wider than the screen, with the picture in the middle and bars at its sides. On macOS, every renderer now fits an oversized window to the available screen space while preserving its aspect ratio (1286x804 in this example). Resolutions that fit and manual window resizing are unchanged.
- **Test for quitting through the menu** *(works on GitHub's macOS runners)*. `docs/metal-backend.md` said that quitting through the menu had been tried, but the scene canceled the Exit Program prompt and then used the `quit` command. `menu-quit` answers the question with yes and has nothing else that could end the game in time: the game exits with 0 in 37 seconds, with its OpenGL window still hidden.
- **`-mtlunseen`** *(works on an M4 Pro Mac mini and an Intel MacBook Pro, each with its screen locked)*. VibeRant Metal doesn't present to a window nobody can see, and a locked screen or a sleeping display counts as that, so on a Mac that nobody sits at, a test of the game presented one frame and no more. With `-mtlunseen` the presenter presents whatever AppKit says of the window. This flag is for tests.
- **Renderer setting** *(works on the runner and on both Macs, as far as console commands go: the menu's own Renderer row was not operated)*. A build with the Metal backend lists **VibeRant Metal** in Options → Video → Advanced → Renderer, between Software and Legacy GL, with a description and an options header that name it; the saved value is `renderer "VibeRant Metal"`, a new config starts with it, and `-metal` selects it for one run. Switching between Software and VibeRant Metal is immediate, and Legacy GL after VibeRant Metal (or the reverse) takes effect at the next start, as between the other hardware renderers. The game's OpenGL window stays hidden until a renderer that presents on it is the one running, as where VibeRant Vulkan is the default. `renderer_setting_metal` checks the list, the default, the command line, and that the driver that starts is the one the setting names; every variant of the test now also checks that the name of a renderer the build doesn't have selects nothing.
- **Build options.** `SRB2_CONFIG_VIBERANT_METAL` builds the backend and defines `HAVE_VIBERANT_METAL`; it is on by default on macOS, where it is the driver's only backend (not Direct3D 12, and not Vulkan through MoltenVK: asking for either beside it stops the configuration). The game links Metal, QuartzCore, AppKit, Foundation, and CoreGraphics, and builds glslang and SPIRV-Cross with its Metal target, as the Linux build builds them for Vulkan; `-DSRB2_CONFIG_VIBERANT_METAL=OFF` builds without the driver, as before. The `macos` CI job checks the defines and that the backend's files are compiled with automatic reference counting (without it nothing keeps Metal's objects alive, which the first build showed by crashing in its first texture upload), builds the game, and uploads the app as `macos-app`: for Apple silicon, not signed, and loading Homebrew's SDL2, libpng, and Opus instead of carrying them.
- **Automatic reference counting with any CMake that can build it** *(checked with CMake 3.16.9 and 3.31.6 on a Mac)*. The backend's five Objective-C++ files were given `-fobjc-arc` as a source file property that names the target's directory (`TARGET_DIRECTORY`), available since CMake 3.18. CMake 3.16 and 3.17 read that word as one more file name and configured without complaint, leaving the option out: the build that crashes in its first texture upload. The option is now the game target's own, for its Objective-C++ files, which works from 3.16 on (a project of two targets made for the purpose showed the old way losing the option with 3.16.9 and the new way keeping it). CMake 3.16 is also the first that knows Objective-C++ as a language, so a configuration with `SRB2_CONFIG_VIBERANT_METAL` and an older CMake now stops and says so; the rest of the project still states 3.14, and `-DSRB2_CONFIG_VIBERANT_METAL=OFF` builds with it as before.
- **Add-on shaders leave the Metal shader cache** *(driver test passes on the runner, an M4 Pro, and an Intel Iris Plus 645)*. mtl12 kept every compiled Metal function, and a copy of its SPIR-V, until the device was released, so each add-on shader that was loaded, replaced, or unloaded stayed in memory for the rest of the session. The pipeline states made of a function now own it, and the cache only finds it while one of them exists: an add-on shader's functions go when the driver retires its pipeline states. The driver test compiles, draws with, and cleans sixteen add-on shaders and checks that the cache ends as it began. Code review found the leak.
- **A failed Metal command buffer stops the game** *(driver test passes on the runner, an M4 Pro, and an Intel Iris Plus 645; no command buffer has failed on its own on any GPU)*. When Metal failed a command buffer for reasons other than device removal (a timeout, a page fault, no memory), mtl12 logged it and completed its fence as if the work had been done, so the driver went on with textures it believed uploaded and readbacks that were never written. Every failed command buffer now makes the device report itself removed, with a reason by Metal's error code, and the driver ends the frame with the error it shows for a removed Direct3D 12 device. Four runs of the driver test fail a command buffer on purpose, with four of Metal's codes, and check the wait, the fence, the reason, the log, and that the game stops. Code review found the bug.
- **Metal null-view initialization** *(driver test passes on the runner, an M4 Pro, and an Intel Iris Plus 645)*. The one-texel texture that stands in for a null view was written as zero by a command buffer outside mtl12's bookkeeping: nothing waited for it, a failure of it on the GPU went unseen, and if it couldn't be set up at all the texture was kept anyway, with whatever its memory held, for every later null view of that kind. Its command buffer is now a submission like the driver's, and a texture that couldn't be set up is dropped, so the view stays empty and the next one tries again. Code review found the bug.
- **Autorelease pools on the driver's thread** *(measured on an M4 Pro and an Intel Iris Plus 645)*. The game's main loop has no autorelease pool, so whatever Metal autoreleases there outside a pool of mtl12's own is never released. A Metal texture or buffer autoreleases its device as it is deallocated, and mtl12 released them outside a pool: each freed texture left eight bytes and a reference to the device behind (about a thousand per replay, most at shutdown). Its destructors now open a pool, and with the Objective-C runtime reporting every object autoreleased without one, a replay has none on the driver's thread. The reports that remain are from Metal's and Core Animation's own threads; the game's memory stayed within 112 KB over eleven minutes and 39,614 presented frames. Code review prompted the measurement.
- **Apple's paravirtual GPU** *(works on the runner; the limit is off on both Macs' GPUs)*. The GPU of a macOS virtual machine, GitHub's runners among them, has a driver that stops the program at an assertion of its own (`-[AppleParavirtCommandBuffer endCurrentChunk]`) when an encoder ends with its last 131,072-byte chunk of commands within four bytes of full and another encoder follows on the same command buffer, which a race's 3D view does about once in 16,000 frames. On that device mtl12 ends a pass after 48 draws and a blit encoder after 96 copies and goes on in a new one, so no encoder fills a chunk; the picture is the same, since a pass loads what the one before stored. Found in the first replay the game played on a runner (80 frames into Aerial Highlands) and traced with `lldb` there; with the limit, 213 replays ran without it. The limit applies only to the virtual GPU.
- **Same picture as VibeRant Vulkan** *(measured on the runner's virtual GPU, an M4 Pro, and an Intel Iris Plus 645, against a Linux PC with a Radeon)*. The macOS game played the first staff ghost of each of the 213 maps with VibeRant Metal under Metal's API and shader validation, and its 1,002 captured frames were compared with VibeRant Vulkan's: on a runner, on a Mac mini with an M4 Pro, and, for 89 of the maps (424 frames), on a MacBook Pro with an Intel Iris Plus 645. Every run exited cleanly with nothing reported by the validation or the driver (on the M4 Pro, after three faults that only its validation reports were fixed: the sky dome's caps, the sprite shader's pole, and sprites without height, each with its own entry). The M4 Pro's frames are the runner's almost to the pixel (0.002% of the pixels differ in the median frame, 0.1% in the worst), and the Intel GPU's differ from both in about 0.09% of the pixels, at texel edges. The figures that follow are the runner's against the Radeon, and the two Macs' are the same to within a few frames. In the median frame 0.14% of the pixels differ, in 95% of the frames fewer than 0.76%, and in the worst 20%; nearly all of it is one level of one color channel on blended surfaces, water above all, and there it is the Radeon that rounds differently from the rest: the same frames drawn by the Vulkan backend on a CPU device (lavapipe) agree with Metal's. Counting only pixels more than one level apart, the median is 0.02%, 95% of the frames are under 0.17%, and the worst is 3.3%. Setting texel edges aside, 936 frames differ in at most 0.02% of their pixels and 11 in more than 0.1%: five where the Linux build's game itself differs from the Windows and macOS builds' at the start of a race (as it did in the Vulkan comparison), one puff of dust that each system places differently, Haunted Ship's one-tic effect, and four frames of fine distant textures in Daytona Speedway and Blizzard Peaks Classic. One difference is in neither list: in Vermilion Vessel a distant wall lies in the plane of a sky wall, and the runner's GPU and the M4 Pro show the sky through it in a stipple of about 900 pixels where the Radeon and the Intel GPU show the wall whole (Software shows only sky there). One frame had changed between two runs on the runner, Neon Resort at 700, with 198 dim pixels in its black sky; that was the sky dome's cap, drawn with texture coordinates nothing had set (see **The sky dome's caps**). Also run on the runner, with pictures of the screen: the title screen and a menu by keyboard, 3D models on and off, the three Screen Scaling modes in fullscreen, changing the renderer back and forth while a replay plays, and quitting. On the Macs, judged by the log alone: fullscreen and back, another video mode and back, `vid_wait`, and every change of renderer. A replay's frame takes 2.3 ms on the M4 Pro and 7.5 ms on the Intel GPU at 1280x720, against 4.0 and 9.3 ms with Software. [docs/metal-backend.md](docs/metal-backend.md) has the details and the list of what could not be tested without a person at the Mac. On `master`'s later renderer changes (2026-11-16) the M4 Pro's 1,002 frames were taken again: 453 are the earlier ones to the pixel, 165 changed exactly as VibeRant Vulkan's did (the same frames and the same pixels), and 384 differ by one pixel in the median frame and twelve at most, which is the texture atlas moving a sprite's edge texel on Apple's GPU (with the atlas off they are the earlier frames to the pixel, on the nine maps tried). Against the Radeon the figures are unchanged.
- **The game on a macOS runner.** The `Metal frames` workflow (`.github/workflows/metal-frames.yml`, `tests/metal-frames/capture.py`) builds the macOS game, fetches the official assets, and runs the replays in parallel jobs and the other scenes in one, with Metal's validation on, failing on any validation message, driver error, missing frame, or exit status, and uploading frames, pictures of the screen, and logs. - **The Metal frames workflow checks what it downloads.** The 752 MB assets archive was fetched from the release's page and unpacked unchecked, then cached under a fixed key, so a replaced or cut-off file would have been kept for every later run. ### Matching Software

- **Palette rendering** *(works on Xbox)*. Ported from SRB2, palette rendering lights surfaces through colormaps, limits colors to the palette, and applies palette flashes and the color profile to the whole frame. It rebuilds cached textures when Encore's remap changes, so colors from the previous normal or Encore race don't carry over. With palette rendering off, flashes remain white or pink overlays.
- **Brightmaps** *(works on Xbox, including Encore)*. Brightmapped pixels use the base colormap's full-bright row rather than a sector's tint/fade, in palette and smooth rendering, while retaining Encore's texel remap. SPRTINFO sprite brightmaps include roll rotation with the base patch's transform, pivot, flip, and origin. Missing or differently sized maps fall back to ordinary lighting. Reloading or purging the cache releases rotated companions. Sprite brightmap selection and rotated companions apply to every platform.
- **Springs** *(works on Xbox)*. Springs use Software's origin and sprite-height sorting against solid walls, two-sided upper/lower walls, and opaque 3D floor sides and planes, including nearer faces drawn over them. Clipping removes rounding slivers and clamps crossed sprite light slices to prevent bow-ties, hiding Metropolis's springs inside bumpers without dashes; ordinary sprites and translucent or see-through sides retain per-pixel depth behavior. Flat silhouettes (all within a tenth of a pixel's angle of one plane through the camera), such as the seam between two sloped floors on one plane that Software leaves undrawn, no longer clip springs *(untested on Xbox)*; one beside the camera in Green Hills Zone had cut a whole row of springs out.
  - **Springs beside a 3D floor plane** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. Software sorts a spring behind a 3D floor's plane only if the plane is nearer than the spring somewhere in the spring's own screen columns. The hardware rule looked at the plane's nearest corner anywhere, so a plane that passes beside a spring on its way toward the camera counted: in Endless Mine, the springs on the side of a diagonal beam, whose tops are under the beam's top, were cut away almost entirely where Software shows them whole. The hardware rule now tests only the part of the plane in the spring's columns. A sweep of all 213 maps found the bug. Metropolis's bumpers are unaffected.
  - **Spring 3D models** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. With **3D Models** on, a spring was drawn as a model with ordinary depth testing, so the tips of the springs inside Metropolis's yellow bumpers poked through the bumpers' faces. A spring's model now follows its sprite: it isn't drawn when Software's rule leaves nothing of the sprite, and when part of the sprite is left, VibeRant hides the model behind the same silhouettes that cut the sprite (marked in the stencil buffer's top bit while the model is drawn, within twice the sprite's size since a model can be larger than its sprite). Legacy GL hides a fully hidden spring's model too and draws a partly hidden one whole. In a Metropolis replay the spring tips no longer show through the bumpers. Of 1,002 frames from the 213 maps, nine changed, all of them spring models that no longer show through a wall or a floor: springs set into walls in Obsidian Oasis and Mega Collision Chaos, which Software hides too, and a few distant ones that now show exactly as much as their sprites do.
  - **Clipping bounds** *(works on Xbox)*. Capacity checks prevent buffer overruns during spring and near-plane clipping. Skipping an oversized silhouette or keeping its affected triangle whole can leave a rare spring sliver visible.
- **Water** *(works on Xbox, including split-screen and overlapping volumes)*. Translucent ripple surfaces refract the scene behind them, including visible submerged geometry. Software distorts only the background. It uses Software's wave timing, distance attenuation, and signed pixel rounding with viewport clamps and six blend modes. Coplanar pieces share an immutable, bounded capture expanded by disjoint strips and a 16-pixel ripple margin; intervening draws, different layers/slopes, or polyobjects start fresh captures, and the shared-platform `FOF_CUTEXTRA` rule removes hidden internal water/fog boundaries as Software does, retaining touching or different-kind boundaries.
  - **Water fallbacks** *(works on Xbox)*. Offscreen faces need no copy, near-plane crossings use conservative full-view bounds, and standalone polyobjects use bounded per-face captures. Reduce VFX disables distortion, opaque ripple surfaces keep texture-only ripples, and capture failure retains ordinary rendering. Controlled Xbox performance comparisons remain pending.
- **Underwater and heat distortion** *(works on Xbox, including split-screen)*. Per-pixel sampling follows Software's wave shapes and tic timing rather than Legacy GL's coarse grid; underwater displacement reaches 1% of the full frame width, and sampling clamps to each viewport without affecting the HUD. Reduce VFX disables both effects, and desktop OpenGL retains its coarse grid and single-view limit.
- **Fog** *(works on Xbox)*. With Shaders on, fog walls and planes remap the captured scene inside colored, inward, outward, and overlapping boundaries, using Software's integer light rows and control colormaps in palette mode or tint/fade equations in smooth mode. Each visible face copies its projected bounds into one retained RGBA texture, preserving portal/viewport clipping without depth writes; custom fog shaders own their output, and allocation failure uses the old shader.
  - **Fog approximation** *(works on Xbox)*. Shaders Off and desktop OpenGL retain one cached inward neutral camera-fog approximation: cap surface light, apply the colormap and sky attenuation once, and omit that block's boundary polygons. This shared-platform path needs no scene copies but can differ from Software in color, brightness, and boundary placement; colored, outward, and overlapping fog retain older paths.
  - **Overlapping fog order** *(works on Xbox)*. Every hardware renderer keeps fog planes at the same height in the order their fog blocks were created, so overlapping fog no longer switches color with the viewing angle. The first block wins in both renderers. Software also draws the second block's plane in the first block's colors. Looking out from inside the overlap, the shared boundary wall also shows the first block's color, where Software shows the second's; hardware keeps the first, matching the fog you're standing in.
- **Palette fades and wipes** *(works on Xbox)*. Palette Rendering uses Software's fade-map rows before the HUD, clamps strength to the available rows, and leaves flashes/color correction to the final palette pass; missing resources or Palette Rendering Off use the overlay (`path=exact` or `path=overlay`). Transitions support black/white Mega Drive-style fades, inversion, Encore wiggle, and reversed fades, with the final current frame shown immediately; an unavailable full wipe falls back to two passes.
- **Encore inversion flag** *(works on Xbox)*. `PF_Invert` has a separate bit from depth writes so blend selection recognizes screen inversion instead of drawing a white quad.
- **Portals** *(works on Xbox, including split-screen)*. Special-40 linedefs show their paired destination through stencil openings and exit-plane clipping, using Software's tag pairing, rotation, and floor-height offset. The implementation credits [SRB2Kart Saturn](https://github.com/Indev450/SRB2Kart-Saturn). `maxportals` defaults to 2, with 0 disabling portals; recursive views use the regular sky, maps without portals skip the search, and the player model can disappear near an opening as in Software.
- **Sky alignment and horizon boundaries** *(works on Xbox)*. Sky domes and the flat fallback honor single-patch header offsets, and empty two-sided sky boundaries no longer extend opaque floors over the background, fixing Water Palace's sky position and cutoff. The horizon check applies on every platform; real boundaries still extend, and signed sky offsets use multiplication instead of undefined negative left shifts.
- **Skybox visibility** *(precipitation works on Xbox; `RF_HIDEINSKYBOX` untested)*. Precipitation and things marked `RF_HIDEINSKYBOX` are excluded from skybox views on every platform. Upstream's Legacy GL draws rain in the skybox.
- **Black void** *(works on Xbox: no stray black walls, Green Hills Zone's skies and Municipal Meadow's skybox buildings show; the black under a step with the camera underground hasn't been seen there)*. Screen areas the level doesn't cover, such as gaps with nothing behind them, views out of the map, or the camera clipped into a wall, are black, as in Software, instead of showing the sky that was drawn behind everything. The sky shows only through sky surfaces: sky-flat floors and ceilings, from the side they face (including opaque 3D floors with the sky flat) and the existing sky walls, which write depth without color. One full-screen pass per view fills undrawn pixels with black before sprites and translucent surfaces blend over them. It applies inside skybox views, portals, and split-screen views. The far clipping plane moves from 32768 to 131072 units so distant geometry isn't clipped into the void. From the other side Software only shows sky beyond the edges of the sky flat's sector, which the sky walls already give; claiming the plane there as well hid the buildings in the first prison map's skybox whenever the chase camera dipped below the ground. Sky planes also claim their extension past horizon lines, as Software extends them, so the skies above Green Hills Zone's horizons aren't black. Translucent 3D floors with the sky flat and Boom fake-flat sky conditions don't claim sky. When the chase camera is pushed underground (below the floor in front of a raised step), the screen columns Software leaves empty there are black too *(not seen on Xbox yet)*: Software treats a step whose top is above the screen as filling its columns, so VibeRant draws black along the line below the wall (or above an upper wall), meeting the wall's edge without overlapping it, instead of showing the level behind. It doesn't treat the line as a closed door as well, which an earlier version did: looking up or down, VibeRant's true-perspective view reaches past the wall's far edge where Software's sheared view stops, and with nothing drawn behind such walls, black stood above Green Hills Zone's blocks instead of their sky *(fix works on Xbox)*. To judge whether a step's top is above the screen, VibeRant uses Software's freelook tilt (independent of field of view), 80° pitch limit, and wider view when the screen tilts. An earlier version scaled the tilt by the field of view and ignored the other two, so at a field of view other than 90° or with screen tilting it blackened sky that Software shows, as in Green Hills Zone with the camera low beside a raised block.
- **Walls of sectors whose ceiling is below their floor** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. VibeRant draws only the part of a one-sided wall whose top is above its bottom. Ice Paradise is bordered by a strip of sky sectors whose ceiling (−256) is below their floor (680), and the strip's outer walls carry a placeholder texture that isn't meant to be seen. Software draws a column of a wall only where the wall's top is above its bottom, so it draws nothing there and the sky shows. Legacy GL draws the wall whichever way up it is, so a brown "Why?" wall 936 units tall stood behind the track, flickering against the sky drawn in the same plane. A wall that is upside down from end to end is invisible in VibeRant. Where slopes make the top and bottom cross, VibeRant draws the triangle up to the crossing. Legacy GL is unchanged. `upright_wall` tests it.
- **Wall and sprite brightness by distance** *(works on Xbox)*. VibeRant D3D now uses Software's two light tables, including their steps. Software lights floors and ceilings by distance and walls and sprites by their size on screen, which works out as if they stood at half their distance, so in a dim sector a wall or sprite is brighter than the floor under it. VibeRant D3D lit everything with the floors' curve: sprites and walls in dim sectors came out several light levels darker than Software's, and in a room with a short colored fade the kart was almost fully faded where Software shows it lit. Floors and ceilings also change slightly, up to four levels darker at some sector light levels and brighter within 16 units of the camera. The OpenGL renderer on other platforms keeps the old curve.
- **Brightness steps of walls and slopes** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. A map's light contrast brightens the walls and slopes that face its light and darkens those that face away. Software has 32 light levels and rounds that change to whole levels. Legacy GL has a change eight times finer, for its smooth lighting. VibeRant lights every surface by Software's 32 levels (see **Wall and sprite brightness by distance**), so there the fine change was no smoother, only rounded another way: about half of all such walls and slopes came out one level brighter or darker than Software's. A sector light of 192 with a change of -1 fell a whole level, and with +7 it stayed where it was. With shaders on, VibeRant now adds Software's own rounded change, and leaves the darkest and the brightest level alone as Software does. It also leaves the change out where Software does: on an upper, lower, or one-sided wall under a 3D floor's light that has a colormap, and on a middle texture or a 3D floor's side under a fog colormap or in fog. The finer change was often lost in the rounding there, so those walls used to match by accident. With shaders off, and in the OpenGL renderer on other platforms, light isn't cut into those levels, and the fine change stays. Sprites' light contrast is a separate approximation and hasn't changed.
- **Translucent wall textures at full brightness** *(works on Xbox)*. Every hardware renderer now follows Software's rule. Software draws a translucent wall texture on a two-sided line at full brightness, with only the sector's tint, unless the sector's colormap is fog, and does the same for the translucent side of a 3D floor (water, glass) seen from a sector with no 3D floors of its own. Legacy GL lit them like opaque walls, so in a dim or tinted sector a window darkened with distance and changed the color of what was behind it along its length.
- **Drop shadow strength** *(works on Xbox)*. Every hardware renderer now subtracts the object's shadow color or adds it for a white shadow. Software darkens the floor under an object by its shadow color, a mid gray by default, wherever the round shadow image has a pixel, and ignores that image's own color and the sector's tint. Legacy GL subtracted the image's own color, a much darker gray, so its shadows were less than half as strong: a faint darkening where Software's is nearly black.
- **Wall textures above a sky ceiling** *(works on Xbox)*. Every hardware renderer now draws masked wall textures between sky ceilings before drawing the sky surfaces, so the textures can extend above the ceilings as in Software. Software shows the line's masked wall texture against the sky even above the ceilings' height, as it has nothing to clip it with. Legacy GL's invisible sky ceilings are drawn first and hid that part, so a tree line taller than its sky ceiling was cut off flat. Nearer walls still cover these textures. This needs Batching on (the default), and translucent textures there are still clipped.
- **Semibright sprites** *(works on Xbox)*. With shaders on, VibeRant D3D now lights semibright sprites like Software. For item capsules, dash rings, and a few pickups, Software keeps the sector's light and treats the sprites as nearer than they are, so they stay fairly dark in a dim sector. Legacy GL raised their light level instead, so in dim and dark areas they stood out almost fullbright (at sector light 64, the brightest quarter of the light table where Software uses the darkest third). Bright areas look the same as before, and the OpenGL renderer on other platforms keeps the raised level.
- **Wall textures between two skies** *(works on Xbox)*. Every hardware renderer now lets a two-sided line's middle texture extend past the opening where both sides have sky ceilings or both have sky floors. Legacy GL previously clipped the texture to the opening. Software has no such clip where both ceilings are sky (it draws no upper wall there, so nothing cuts the texture's top), or at the bottom where both floors are sky. Municipal Meadow's skybox ends in lines whose far side is a zero-height sky sector, so the row of pine trees and the distant skyline on them were clipped to nothing. They now show on every platform.
- **Level darkening** *(works on Xbox)*. Every hardware renderer now applies Software's level darkening. It dims walls, floors, and ceilings (bright areas more than dark ones) while Shrink is active, when a Battle power-up is picked up, during the Duel margin boost, and for the end-of-race camera, and leaves sprites bright. Legacy GL never applied it. At Battle's strength, a local render of Municipal Meadow matches Software's brightness to within a few levels out of 255. At full strength (the Duel margin boost) Software's floor is black where hardware's is very dark, and a strip of grass and railing stayed bright in Software but not in hardware; neither difference has been traced. The `debugrender_contrast` cheat now affects these surfaces too, and fog volumes no longer apply the dimming a second time.
- **Fog-style lines** *(works on Xbox; no base-game map has one)*. Every hardware renderer now tints the scene behind a two-sided line with the fog render style (or the old special 909). Like the sides of fog volumes, it tints the middle texture's rectangle using the front sector's light and colormap. The middle texture itself is invisible. Legacy GL drew it as an ordinary wall. Software mixes up world heights and screen positions, producing inconsistent results the hardware renderers do not copy exactly. Software also shapes the fog by the texture's opaque columns, while hardware fills the rectangle.
- **Software perspective's shift** *(works on Xbox, including two-player)*. With Software perspective on, every hardware renderer now shifts the picture vertically by Software's amount for the view's shape. Legacy GL already shifted the picture without pitching the camera, but its shift was correct only at 16:10. At 16:9 the picture sat a tenth of the shift lower than Software's, about 25 pixels at 1080p with the chase camera's usual pitch, and in two-player split-screen over half of it.
- **Two-player view width** *(works on Xbox)*. In two-player split-screen, VibeRant D3D widens each view to 1.7 times the single-player width, matching Software. It previously used 1.6 and showed about 6% less in both directions at the same field of view. Every hardware renderer's visibility clipper covers the wider view.
- **Translucent overlay sprites** *(works on Xbox; no base-game object is known to use the combination)*. Every hardware renderer now blends translucent overlay sprites, walls, and 3D floors like ordinary translucent surfaces. Software does the same because it has no separate blend table for the overlay style. Legacy GL kept its cut-out blend for those, which ignores the background, so their partly transparent pixels darkened instead of showing it. Opaque overlay surfaces are unchanged.
- **`RF_SHADOWDRAW` sprites** *(works on Xbox, apart from the tilt on slopes; nothing in the base game sets the flag)*. Software draws a sprite with this flag as a ground shadow: as wide as the sprite itself, as tall as the object's radius allows, flattened according to how high the camera is above the ground, and sheared on slopes. Legacy GL drew it as an ordinary upright sprite. Every hardware renderer now applies the same size, flattening, slope shear, and position (the first version sized the width by the radius too, which drew the renderer test map's posts 1.5 times too wide). On a slope the shape tilts by the slope's real angle here, where Software's tilt depends on the resolution and the distance and is nearly flat at 1080p; paper sprites, floor sprites, and 3D models are unaffected. Hardware's true perspective means the shape isn't pixel-identical to Software's.
- **`colormapfadesprites`** *(works on Xbox; no base-game map sets it)*. With this colormap setting, every hardware renderer now matches Software. Software dims the part of a fullbright sprite that lies below a 3D floor's lighting boundary by that boundary's light level and by distance, without the colormap's tint; whole sprites and the part above the boundary stay fullbright. Legacy GL kept every part fullbright.

### Intended differences from Software

VibeRant aims to match Software. The following differences are intentional and carry no status markers.

- **True perspective.** Looking up or down pitches the camera, so vertical lines converge, and sprites turn to face the pitched camera (**Sprite Billboarding**). Software shifts the picture up or down instead and keeps vertical lines upright. **Software Perspective** in the VibeRant D3D options gives Software's shift.
- **Water.** Seen from above, a rippling water surface also distorts the level under it, (see **Water**). Software distorts only the background.
- **Drop shadows.** A drop shadow lies on the floor as a real circle. Software draws an upright ellipse on the screen, so here a shadow away from the middle of the screen looks slightly turned. Its strength is Software's (see **Drop shadow strength**).
- **Sprites against the level.** Each pixel of a sprite is hidden by whatever level geometry is nearer, so a sprite that pokes into a wall or floor is cut where it enters. Software decides from where the sprite stands and can show such a sprite whole. Only springs follow Software's rule (see **Springs**), and the floor under a floor sprite doesn't hide it (see **Floor sprites under the floor**).
- **Shadow-drawn sprites on slopes.** A `RF_SHADOWDRAW` sprite tilts by the slope's real angle; Software's tilt depends on the resolution and the distance (see **`RF_SHADOWDRAW` sprites**).
- **Camera underground.** When the chase camera is pushed below the floor in front of a raised step, Software draws the step's wall, leaves the screen under it black, and draws nothing that lies behind the step. VibeRant draws the same black under the wall but still draws what lies behind the step. Software's shifted view never reaches past the top of such a wall, so hiding what is behind it costs nothing there; a pitched camera sees over the wall's far edge, and hiding it left black shapes where the sky belongs (see **Black void**).
- **Translucent colors.** With Palette Rendering on, a see-through surface is blended in full color and the finished pixel then takes the nearest palette color. Software looks the result up in the game's translucency tables (`TRANS10` to `TRANS90`). Both stay within the palette and are on average equally close to the true blend, but they pick a different palette color for 10 to 14% of color pairs, and more often the fainter the surface is.
- **Hardware-only options.** **3D Models**, **Texture Filter** modes other than Nearest, and anisotropic filtering are options.
- **Palette Rendering off.** Colors are no longer limited to the palette: lighting is smooth, translucent surfaces show true blends, palette flashes are overlays, and level fades darken or whiten the picture evenly. Software's fade table is Mega Drive style instead: red drops out first, then green, then blue (see **Palette fades and wipes**).
- **Shaders off.** Fog volumes use one neutral approximation that can differ from Software in color, brightness, and edges (see **Fog approximation**).

### Fixes to Legacy GL

- **Sprites without height where 3D floors change the light** *(seen and fixed on a Mac with an M4 Pro; untested on Xbox)*. The hardware renderer skips sprites squashed to zero height when drawing sectors whose light changes at 3D floors. In these sectors it draws sprites in pieces, each with texture coordinates (and, for a billboard, a position) divided by the sprite's height. A sprite squashed to no height at all, which the replays of seven of the 213 maps have for a frame or more (Carnival Night and Chrome Gadget among them), gave every piece coordinates that weren't numbers. It has no pixel to draw, so nothing showed, but what a GPU does with such a polygon isn't defined, and Metal's shader validation reports it. The bug also affected upstream's OpenGL renderer.
- **The sky dome's caps** *(seen on a Mac with an M4 Pro, where Metal's shader validation reported it; untested on Xbox)*. The sky dome's top and bottom caps now sample the middle of the sky texture's first texel, as they did with freshly allocated (zeroed) memory. Their coordinates were previously left unset, so the caps sampled the sky texture using whatever the vertex memory from `malloc` held. Looking steeply up, the top of the sky could have another color from one run of the game to the next, or stray texels of the sky texture scattered over it, and where the memory held an infinity or not-a-number, nothing defined. It is the upstream renderer's code, so OpenGL's Legacy GL had it too. On an M4 Pro, the replays of 21 of the 213 maps drew caps with such values in every frame (Astral Dimension and Marble Foyer among them). This was also the one frame that differed between two identical runs on GitHub's macOS runner: Neon Resort at level time 700, where the camera is pitched up on a slope, had 198 dim pixels in the top 43 rows of the black sky, and giving the caps random coordinates on the M4 Pro changes 202 pixels in the top 41 rows of that frame, over the same columns.
- **Untextured steps** *(untested on Xbox)*. Where a floor steps up, or a ceiling steps down, and the wall between has no texture, the farther floor's (or ceiling's) flat continues across the step with that flat's lighting, as Software lets it bleed, instead of leaving a gap that shows what is behind. Neighboring sloped floors in Green Hills Zone meet a few thousandths of a unit apart, which showed as thin crack lines across the grass. It applies only while that flat faces the camera; sky flats and polyobjects are unchanged.
- **Textures also used as brightmaps** *(works on Xbox)*. Every hardware renderer now sets a texture's role on each use, so using it as a brightmap no longer replaces its image on surfaces. This applies to every platform. The fullbright color textures `~B000` to `~B255` all use plain white `~000` as their brightmap; once one had been drawn, Legacy GL treated `~000` as a brightmap for the rest of the session, so a floor or wall textured with `~000` showed the previous surface's texture, or black. Test Run's bowl showed black and gray wedges on its white floor after the map's `~B000` ceilings had been seen.
- **Seams between floor polygons** *(works on Xbox)*. On every platform, each subsector's floor and ceiling polygons now use its outline in the map's GL nodes, sharing corners exactly with their neighbors. Legacy GL previously cut each subsector's floor and ceiling polygon out of the map's BSP lines with floating-point math and merged points closer than 0.45 units, so where several BSP lines cross within that distance, neighboring polygons got different corners and the void showed between them. Test Run's bowl showed four black lines to its center, where the wedges of its floor meet. Outlines that are dented or not closed keep the old cut: 10 of the 556,203 subsectors in the shipped maps, besides 451 with too few edges for an outline.
- **Floors beside a moved polyobject** *(works on Linux with VibeRant Vulkan and Legacy GL; untested on Xbox)*. On every platform, floor polygons now use the polyobject vertices from the map as the node builder saw them, including when the renderer changes mid-level. Previously, the renderer read the outlines after moving each polyobject to its spawn point, so a floor polygon with a polyobject's line on its edge reached from where the map has the polyobject to where it now is. In Balloon Park, the dark gray floor of the sliding elephant blocks' control sector stretched across the funnel behind them and hid it, and the blocks' own peach floor and ceiling stayed where the blocks started.
- **Hidden areas behind horizon lines** *(works on Xbox)*. UWP now skips hidden branches of the BSP tree on the camera's side of a split. Legacy GL checked for nearer walls only on the far side of each split and always drew the branch on the camera's side. Software visits those too but draws nothing in a hidden one, because all its lines are clipped; Legacy GL draws its floors and ceilings whole and counts on the nearer walls to cover them. A horizon line (special 41) draws no wall, so the ceiling of a 3D-floor control sector behind Green Hills Zone's horizon showed as a small dark-green triangle in the sky. UWP draws slightly fewer map sections, 385 instead of 411 in that Green Hills view.
- **Walls cut by solid 3D floors** *(untested on Xbox)*. VibeRant D3D now fills the part of an upper, lower, or one-sided wall inside a solid 3D floor's thickness with black. Software leaves the part of an upper, lower, or one-sided wall inside a solid 3D floor's thickness undrawn and draws nothing behind it, so through a see-through 3D floor, such as Green Hills Zone's tube grates, that part is black (or the HOM flash). VibeRant previously showed the level behind the wall, such as the sky or grass outside the tube. The 3D floor and anything nearer still draw in front.
- **Lower-unpegged walls on slopes** *(untested on Xbox)*. A one-sided wall whose texture is lower unpegged now has the texture's bottom on its floor along the floor's slope, as in Software, on every platform; Legacy GL measured it from the sector's unsloped floor height, so Green Hills Zone's pit walls between the tubes showed the grass at the top of their texture at their foot instead of brick.
- **Slope shading on 3D floors and ceilings** *(works on Linux with VibeRant Vulkan and Legacy GL; untested on Xbox)*. Every hardware renderer now matches Software's slope shading, including on flats that continue across untextured steps. A map's light contrast brightens slopes that face its light and darkens those that face away. Software turns that around for a surface that faces down, a sloped ceiling or the underside of a sloped 3D floor, because a slope's direction is worked out as for a floor. Legacy GL turned it around for both planes of a 3D floor and for no ceiling, so the top of a sloped 3D floor was dark where Software has it light and light where Software has it dark, and a sloped ceiling likewise. Balloon Park's funnel is made of 3D floor tops under a contrast of 48, three times the usual: its far side was navy instead of light blue.
- **Floor sprites under the floor** *(works on Linux with VibeRant Vulkan and Legacy GL; untested on Xbox)*. Every hardware renderer now adjusts depth to keep floor sprites such as sneaker panels visible where the floor rises over them by up to a step's height. A floor sprite lies on one plane: its own height, or the slope its object stands on. Software draws it after every floor and never hides it behind one. Legacy GL tests each of its pixels against the level's depth, so wherever the floor rises over that plane the sprite was hidden. Robotnik Coaster's track is a different slope every few units, so one of its three green sneaker panels wasn't drawn at all on the way up to it, and another was cut down to a strip. Every hardware renderer now measures how far the floor under the sprite rises over it, at 25 points and up to a step's height, and gives the sprite the depth it would have that much higher, without moving its picture from where Software draws it. A floor sprite on a floor that doesn't rise over it is drawn exactly as before. What stands on such a sprite can lose up to that rise from its foot where the two overlap.
- **Wall light slices** *(works on Xbox, including split-screen)*. UWP clips each lighting band to its original wall and splits crossing slopes, preserving UVs, lighting, alpha, and solid-floor holes. This removes inverted slices that covered Water Palace scenery with brown wall pixels, without new GPU resources or copies.
- **Missing floors and ceilings** *(works on Xbox)*. BSP cuts send unsplit polygons to their actual side, and a closed GL-seg loop supplies a fallback for subsectors missing a polygon. This fixes reported holes on Green Hills Zone and Storm Rig on every platform; some inherited oversized subsector polygons remain possible.
- **Sprite-textured models** *(works on Xbox, including after video changes)*. Every platform prepares a model's selected sprite patch before reading hardware data and compares sprite dimensions when refitting UVs, preventing crashes with models such as item boxes after video changes.
- **Title background lighting** *(works on Xbox)*. Preparing neighboring 3D-floor lighting before use prevents a briefly lit title-map background during fade-in on every platform.
- **First frame after a map load** *(works on Xbox)*. View interpolation stays off after a reset until a frame of the new map is drawn, on every platform. A slow load used to run tics without drawing, so the first frame blended from the previous map's last view: after a race, EXIT GAME's fade-in showed only sky in hardware renderers and a wrong view in Software.
- **Fill transparency** *(works on Xbox)*. Every hardware renderer honors fill translucency and HUD fades, including the spectator Watching underline over the finish-grade icon. Opaque fullscreen fills retain the clear shortcut; translucent fills blend over the full surface.
- **Polyobject ripples** *(works on Xbox)*. Moving floors and ceilings use their control sector's ripple flag, including translucent planes, on every platform. Regular and polyobject planes honor Reduce VFX when selecting ripples.
- **Raw pictures** *(untested on Xbox)*. Every platform supports opaque intensity/grayscale and RGB24 pictures alongside palette, intensity/alpha, and RGBA modes, including nearest-neighbor resizing. Conversion validates headers, dimensions, modes, and lengths, ignores trailing bytes, and prevents RGBA destination overruns.

### Settings

- **Advanced menu** *(works on Xbox; the new wording is untested there)*. The renderer list says **VibeRant D3D**. Options → Video → Advanced describes it as a Direct3D 12 port of Legacy GL with 3D models, true perspective, and high parity with Software, and asks for visual bugs to be reported to GitHub.com/ZebulanStanphill/RingRacers, the engine fork (it said "more parity" and named this repository before). Switching to it shows no confirmation or loading warning, and its **VibeRant D3D Options...** section has no blank rows.
- **Renderer description with Software selected** *(not on Xbox; checked by a test, not on a screen)*. With Software selected, Options → Video → Advanced described VibeRant D3D as a port to Direct3D 12 in every desktop build, including Linux and macOS builds, which have neither. It now describes the VibeRant renderer the build lists first, which is the one a new config uses: VibeRant D3D on Windows, VibeRant Vulkan on Linux, and VibeRant Metal on macOS. `renderer_description_both`, `_vulkan`, `_metal`, and `_all` run the menu's own refresh function for every setting in each kind of build.
- **Software saved as the renderer** *(works on Xbox)*. The game starts in Software when Software is the saved renderer. VibeRant D3D is the default, so startup queued a switch to it before the saved setting was read, and reading Software didn't cancel that switch: the game ran VibeRant D3D with the menu showing Software until the option was changed and changed back. The same stale switch was possible on every platform when the setting was changed and restored before the next frame, and is dropped there too.
- **Palette control** *(works on Xbox)*. `gr_paletterendering` defaults to On and requires Shaders on.
- **Better transparency ordering** *(works on Xbox)*. On every hardware-renderer platform, blended sprites, models, linkdraw attachments, and always-on-top sprites are inserted into the transparent surface pass using overlap, depth, and plane-side checks, instead of being drawn in a separate pass afterwards. It adds per-view CPU sorting and storage without scene copies, preserves opaque depth drawing and water-capture runs, and works with Shaders on or off; proxy model bounds, unsplit face crossings, cyclic intersections, and triangles within translucent models limit accuracy. This was the saved option `gr_bettertransparency`, Off by default. In a 16-bot race on Chemical Facility on Xbox it cost about 0.2 ms more sorting per frame, with the whole 3D view at 7.0 ms either way, so it is now always on and the option and its menu row are gone, along with the code only Off used (Legacy GL's delayed z-buffer pass for linkdraw sprites). A `gr_bettertransparency` line left in an old `ringconfig.cfg` is ignored. Under Wine, VibeRant D3D and Legacy GL on OpenGL both draw Chemical Facility's start with it; one Legacy GL run out of seven had a black 3D view in its screenshot, which didn't happen again in 42 further frames and isn't explained.
- **Batching** *(works on Xbox)*. `gr_batching` defaults to On, resets at launch, and appears last in VibeRant D3D's options.
- **Texture Filter** *(untested on Xbox)*. VibeRant D3D's options show **Texture Filter** (`gr_filtermode`: Nearest, Bilinear, Trilinear, Linear_Nearest, Nearest_Linear, Nearest_Mipmap) in place of **Texture Quality**. That setting only chooses Legacy GL's OpenGL texture format. VibeRant always uses 32-bit textures. A new mode applies at once, and **Anisotropic** takes effect with Bilinear, Trilinear, Nearest_Linear, and Nearest_Mipmap, which filter distant texels.
- **Screen effects** *(works on Xbox)*. Options → Video → **Screen Effect**'s SalCRT and SalCRT Sharp apply in VibeRant after Palette Rendering as the final pass. Screenshots and recordings omit the effect. The game's own CRT shaders are read from its shader data and translated to Direct3D when first chosen; if that fails, the log says `screen effect ... failed:` with the reason and the frame is shown without the effect. Nearest and Sharp Bilinear only choose how Software scales its picture up, which VibeRant doesn't need.
- **Fullscreen row on Xbox** *(works on Xbox; other UWP devices untested)*. Options → Video no longer shows **Fullscreen** on an Xbox console, because the app always fills the screen there. Screen Scaling takes its place. The row is hidden only when Windows reports the Xbox device family, so PCs, tablets, and other devices that can run the UWP app keep it, as does every other platform. The `fullscreen` console variable is unchanged.
- **Screen Scaling** *(works on Xbox)*. Options → Video → **Screen Scaling**, under Fullscreen (or in its place on Xbox), places the game's frame on the screen in every renderer: **Fit** (the default, as before) scales it to fit, keeping its aspect ratio; **Integer** scales it by the largest whole number that fits; **1:1** shows it unscaled. Integer and 1:1 center the frame with black around it and fall back to Fit when the frame is bigger than the screen. VibeRant D3D then sizes its swap chain to the screen and draws the frame into place after the screen effect; if it can't, the log says `couldn't place the frame` and Fit is used from then on.

- **ANGLE/OpenGL ES 2** *(works on Xbox)*. ANGLE runs the RHI and presents Software's frames through its Direct3D 11 device (VibeRant D3D presents with its own swap chain), replacing worleydl's desktop OpenGL/Mesa path. The GL2 RHI supports ES 2 contexts, GLSL ES 1.00, core framebuffer entry points, `glClearDepthf`, unsized texture formats, RGBA screenshot readback, and no `glReadBuffer`. `uwp/patches/sdl-angle.patch` builds SDL with EGL/ES 2.

## Network

- **Unreachable UDP routes** *(untested on Xbox)*. Host-unreachable and network-unreachable sends, including Winsock 10065, count as dropped packets on every platform. Existing retries and timeouts govern recovery. Other unexpected send errors remain fatal.
- **Online loading** *(works on Xbox)*. UWP VibeRant clients send basic keepalives during geometry/resource loading and vanilla tic acknowledgments at most once per clock tic while connected in-game, excluding demos and savegame redownloads. This prevents loading-related delay kicks without changing server delay rules or the receive limit. A kick logs the last reported delay/limit and local simulated, received, and level tics.
- **Track title timing** *(works on Xbox)*. Pre-race titles start with a fresh clock after loading and retain upstream animation steps and HUD timer clamps. Online VibeRant clients animate the title in the normal HUD while simulation catches up; hosts, Software, offline play, and demos retain the pre-level animation.

## Files and startup

- **Data and logs** *(works on Xbox)*. Assets use `E:\ringracers`. Config and saves use `E:\ringracers\ringracers`, ignoring `-home` and `RINGRACERSWADDIR`. The save folder exists before the writability check. The log uses `E:\ringracers\latest-log.txt` because the package directory is read-only.
- **Missing game data** *(untested on Xbox)*. When `bios.pk3` isn't in `E:\ringracers`, the error first asks whether the USB drive with the `ringracers` folder is connected. It says to put that folder at the top of the drive with the v2.4 assets, points to the README, and lists the drives the app can see.
- **Game data in internal storage** *(untested on Xbox)*. The game copies files it reads when loading tracks and characters (about 300 MB) from `E:\ringracers\data` to the app's folder on internal storage and loads them from there. Windows deletes that folder when the app is uninstalled. That storage is a volume of about 3 GB shared by the data of every sideloaded app, so music, alternative music, and sound effects (about 430 MB) and staff ghosts (48 MB, read only for Time Attack staff ghosts) stay on the USB drive, and copies of them made by earlier builds, like any other file the game no longer keeps there, are deleted at startup. When startup checks a USB file, it copies the file as it reads and keeps the copy only if the MD5 matches. Later launches load a copy without checking it again while its source keeps the size and last-write time it was copied from and the game expects the same MD5; otherwise the file loads from the USB drive and is checked and copied again. Staff ghosts are likewise checked once and then trusted while unchanged, from a small record of the check. Running out of space or failing to write stops copying for that launch without affecting the check. The log lists where each file loads from and why (`UWP: data:`), anything deleted, the internal storage's free space (for this app and on the drive) and size, which volume the internal storage, the install, and `E:\ringracers` are each on (serial number and NT path), and each file copied.
- **Sound effects in memory** *(untested on Xbox)*. Startup reads all sounds from the USB drive's `sounds.pk3` into memory (about 43 MB, in file order), avoiding the race stalls that could occur when a sound first played. The game still decodes each sound on first playback. Sounds from other files, such as characters' voices and add-ons, load as before. The log reports how many sounds were read, their size, and the time it took.
- **Background file check** *(untested on Xbox)*. Main files load with expected MD5s while a below-normal-priority worker verifies contents in 1 MB reads. The game reads zip local headers when it uses the entry. The check can no longer be skipped (B used to skip it, before startup got faster). Startup waits before network setup if needed. Mismatches raise the usual error at the next loading step or final wait. Logs record each file's check time, speed, outcome, and wait.
- **Music and sound hashes** *(untested on Xbox)*. Files without expected MD5s hash their names rather than contents for duplicate detection. They are not transferred to netgames or recorded in replays.
- **Direct3D 12 launch check** *(works on Xbox)*. Launch requires a hardware adapter that creates a feature-level-11_0 Direct3D 12 device and command queue, excluding software adapters and Basic Render Driver. Failure shows a Dev Home Game-type pop-up, flushes logs, and exits; the launcher links `d3d12.lib`/`dxgi.lib`.
- **Earlier loading text** *(untested on Xbox)*. **Loading maps...** redraws up to ten times a second. Graphics, fonts, and the console initialize before map thumbnails and minimaps.
- **Map cache** *(works on Xbox)*. Startup no longer inflates every map WAD (305 MB) and staff ghost (76 MB) to find each map's thumbnail and minimap and each ghost's time and name. `mapcache.bin` in the app's folder on internal storage keeps them between launches, keyed by each zip entry's path, CRC32, and sizes, so a new or changed game file or add-on is read as before and added. The first launch after an install or a data change builds the cache (about 17 MB). A save keeps only the entries in use, a file from another demo version or a damaged one is rebuilt, and a cache that can't be read or written is logged and skipped. Thumbnails still all load at startup, so menus are unchanged. A cache left in `E:\ringracers\ringracers` by earlier builds is deleted. The cache is read with one unbuffered read, and the log reports how long reading and saving it took and how many maps and ghosts came from it.
- **Header cache** *(untested on Xbox)*. Startup caches reads of up to 256 bytes from PK3 entries in `lumpheaders.bin` in the app's folder on internal storage, keyed by each entry's path, CRC32, and sizes, and the read's offset and size, and serves the same bytes from the cache on later launches. Startup reads the first few bytes of thousands of textures and sprites to size them, each a separate seek and often a decompression. On Xbox that was about 8 s of a 13 s startup. The cache keeps only entries used, and reads after startup go to the files as before. The log reports hits, misses, and how long reading and saving the cache took.
- **Lump lookups** *(startup works on Xbox; long names untested)*. On every platform, finding a lump by name in a file checks only the lumps whose stored name hash matches, from an index built when the file is added, instead of every lump in the file. Results are identical. On Xbox, these searches (mostly for HUD graphics) took about 4.5 s of a 26 s startup. Long-name lookups use the same index. Sprite brightmaps look up a long name for every visible sprite every frame. Previously, a missing name meant scanning every lump of every file (0.8% of race time).
- **Folder lookups** *(untested on Xbox)*. On every platform, PK3 folder lookups return the same starting entry using a folder-path index built when the file is added. Previously, the lookup compared every entry's path. On Xbox, looking up each map's staff ghost folder in every file took about 4 s of startup.
- **Texture lookups** *(untested on Xbox)*. On every platform, finding a texture by name uses an index of the loaded textures and a hashed cache of earlier answers instead of scanning both. Results are identical, including newer textures taking precedence over older ones with the same name. On Xbox, the brightmap definitions' lookups took about 5.5 s of startup.
- **Loading-to-intro transition** *(works on Xbox)*. The intro starts with the credits card instead of six blue tics, without changing timing. VibeRant D3D skips clear-only presentation before its first drawn frame, keeping the loading screen visible instead of flashing black.
- **Skipping the intro** *(untested on Xbox)*. A press skips an intro logo as soon as it's on screen, without the previous half-second wait in each scene. The opening credits card, previously unskippable, skips to the disclaimer. The disclaimer still has to slide in and finish fading in its text before it can be dismissed. Controllers already connected at startup are opened while the game loads, rather than once the intro's first frames have been drawn.

## Performance

### Rendering

- **Driver thread** *(works on Xbox)*. VibeRant D3D can record and present frames on a second CPU thread while the game builds the next frame, with the same drawing commands and settings. On Xbox One X, in 16-racer Joypolis races (four with it on, four with it off), it raised the average from 17.9 to 24.0 frames per second: the main thread's 3D time fell from 16.5 to 11.8 ms per frame at the median, and the worker was busy about 5 ms per frame without the main thread ever waiting for it. It is always on; the console command `gr_driverthread Off` (Xbox and Windows desktop) turns it off until the next launch, for troubleshooting, and switches at the next frame boundary. Vulkan and Metal continue rendering on the main thread. [docs/viberant-driver-thread.md](docs/viberant-driver-thread.md) describes the queue and perf counters.
- **Level precaching** *(works on Xbox)*. During loading, the hardware renderer precaches walls, flats, brightmaps, FOF control sectors, existing models, and current player models and colors. It precaches player models and colors again after spawning and hooks. Dedicated servers, reloads, snapshots, and rewind skip it; sprite-textured models, future animation frames, later objects, and view-dependent remaps remain lazy, and Models must be enabled for model warming.
- **Rolled sprites** *(untested on Xbox)*. VibeRant draws sprites tilted by roll (karts on slopes, spinning objects) from the unrotated sprite texture, with the pixel shader applying Software's exact integer rotation, instead of rotating each new angle on the CPU and uploading it as a new texture. Races on Xbox created 20-60 such textures a second (about 1.8% of 3D time rotating and 3% of race CPU creating them, plus hitches). Sizes, offsets, and cropping still come from the CPU, cached per frame and angle, so sorting and clipping are unchanged; brightmaps use the same mapping. Floor and paper sprites, linked sprites, custom sprite shaders, Shaders off, filtering other than nearest, mipmaps, and very large art keep CPU rotation. The perf log reports how many rolled sprites each path drew.
- **Batch sorting** *(untested on Xbox)*. On every platform, Legacy GL batches sort an index array by compact keys copied out once per frame, instead of comparing large polygon entries and their texture pointers on every comparison, which cost about 7% of 3D drawing time on Xbox. Sorting the keys themselves was tried first and doubled the sort time, since qsort moves whole elements. Submission order breaks ties and makes the ordering total. Polygons with different colors may draw in a different order where the old comparison was inconsistent.
- **Batch sorting by group** *(works on Xbox)*. The hardware renderer groups polygons with equal sort keys before sorting a batch. It keeps submission order within each group, so it draws the polygons in exactly the same order and cuts the work of sorting when many keys match. On Xbox One X, in a 16-racer Joypolis race, batch sorting fell from 0.6 to 0.3 ms per frame at the median (three races on each build).
- **Horizon lines** *(untested on Xbox)*. VibeRant caches which parts of the map have a horizon line (special 41) instead of checking every edge of every floor, ceiling, and sky surface it draws for one, every frame, which took 4.6% of 3D time on Xbox. The record is rebuilt whenever a line becomes or stops being a horizon line, so the result is identical.
- **Drop shadows** *(untested on Xbox)*. On every platform, Legacy GL looks up the `DSHADOW` lump once and repeats the lookup only when a file is added. Previously it searched by name for each shadow in every frame.
- **Rotated flats** *(untested on Xbox)*. On every platform, Legacy GL computes a rotated floor or ceiling texture's cosine and sine once per plane instead of four times per vertex, with identical results.
- **3D floor light lists** *(untested on Xbox)*. UWP keeps a sector's 3D floor light list when its allocation is large enough. Previously, preparing a sector with moving 3D floors freed and reallocated its list each time because a shorter-than-counted list never matched the count again. The contents are identical.
- **Device-removal checks** *(untested on Xbox)*. Upload rings read a removal flag set by failed calls or fences instead of making a kernel query on every allocation. A full device check still runs once per frame.
- **Video memory safeguard** *(untested on Xbox)*. Exceeding the local budget schedules a texture-cache flush for the next frame, at most once every five seconds. Model buffers remain, but reloading textures can hitch.
- **GL2 call reduction** *(works on Xbox)*. Every platform skips redundant state/texture/buffer binds, disables only enabled vertex arrays, caches uniform locations, changes sampler uniforms only when needed, and retains framebuffers. Colormap/lighttable textures upload only after changes and expire after 300 unused frames; palettes upload only when changed and the default colormap once, while UWP uses `GL_RED` with `EXT_texture_rg` where available to avoid ANGLE's luminance conversion.
- **Spring silhouettes** *(works on Xbox)*. On every platform, hiding springs behind walls and 3D floors (see **Springs**) now computes each recorded wall or plane's near-plane-clipped outline, whether Software draws it over a spring, and its silhouette planes once per camera. Previously, it repeated these calculations for every spring. A wall that misses every piece left of a spring no longer copies the pieces. On a Joypolis staff-ghost replay on Linux with VibeRant Vulkan (about 1,900 recorded walls and planes at most), this fell from 16.5% of the game's main-loop time to 6.0% with **3D Models** on, and from 13.5% to 5.4% with them off; sprite and model drawing as a whole fell from 24.0% to 14.1% of it. The cache takes at most 0.6 MB there. The optimization leaves spring rendering unchanged. A test compares thousands of random scenes against the earlier code bit for bit. All 80 VibeRant Vulkan frames from six staff ghosts matched, with models on and off. After recapturing three maps on an idle machine, the 80 Legacy GL frames matched except for four in Metropolis that vary from run to run in both versions. A map sweep (1,065 frames per renderer) matched in every VibeRant Vulkan and Legacy GL frame; two VibeRant D3D frames differed by one pixel inside a sprite that is not a spring. On Xbox One X, a 16-racer Joypolis race spent 5.3 ms per frame drawing sprites and models at the median and 10.6 ms in its worst five seconds, against 7.3 and 22.7 ms in an online Joypolis race on the build before (not the same race, so the comparison is rough).
  - **Spring clipping scans** *(works on Xbox)*. On every platform, the hardware renderer checks a smaller table before testing whether walls and 3D floors sort in front of a spring. It searches backward for the farthest 3D floor entry that applies and stops as soon as it finds one. Sprite clipping and model masks produce the same results. On Xbox One X, in a 16-racer Joypolis race, spring clipping took about 1.7 ms per frame instead of 1.85 (profile share, three races on each build).

### Software renderer

- **Planes and sorting** *(works on Xbox)*. Every platform clears only visible visplane columns, skips draw nodes outside a sprite's columns before reading them, and computes 3D-floor plane bounds once during sorting.
- **Columns** *(works on Xbox)*. Every platform leaves unused thick-side slots alone, copies wall-column data only for remapping, computes masked clipping limits once, and passes read-only column data directly to drawers. UWP also inlines `R_GetTextureNum`.
- **Screen tilting** *(works on Xbox)*. Every platform steps along source rows instead of rebuilding a full-screen pixel map, preserving float stepping, clipping, zoom, and mirrored sampling. Large views share work across Software workers.

### Game logic

- **Waypoint pathfinding** *(works on Xbox)*. The game reuses memory between searches and looks up waypoints it has already found without scanning the whole list. Racers and bots follow the same paths. On Xbox One X, in a 16-racer Joypolis race, pathfinding fell from about 1.5 to 1.0 ms per tic (profile share, three races on each build).

- **Blockmap line walks** *(works on Xbox)*. Every platform uses a compact table of linedef bounds and visit stamps to skip distant lines before calling movement and sector-list callbacks. The table is the only storage for each live linedef's bounds and stamp. The walk and its callbacks read the same bounds, so they cannot disagree. In a 16-racer Joypolis race, 96% of about 55,000 such calls per tic returned at the bounds test. The walk preserves visit stamps, callback order, and game logic results. Five staff ghosts play to the same state on every tic as before (every thinking object's position, momentum, floor and ceiling heights, and flags, each racer, and every random seed). On Xbox One X, in that race with level 6 bots, the line walk fell from about 3.5 to 2.5 ms per tic, and game logic per position check from 7.0 to 6.45 microseconds. A first comparison of one race on each build showed 19.8 against 16.8 ms per tic of game logic, but three later races with the table also took 19.8 ms, so that race was lighter than average.
- **Thing collision checks** *(works on Xbox)*. On every platform, a new distance check skips distant things before checking for spectators, hitlag, collision flags, and respawning. If the early check cannot safely rule out a collision, the original checks run in their usual order. On Xbox One X, in a 16-racer Joypolis race, thing collision checks fell from about 2.9 to 2.2 ms per tic (profile share). Together with **Waypoint pathfinding**, game logic fell from 19.8 to 18.5 ms per tic at the median and the frame rate rose from 12.6 to 15.1 frames per second (three races on each build; every race on the new build was faster than every race on the old one).
- **Arithmetic and references** *(works on Xbox)*. UWP inlines `FixedMul`, release-build `P_SetTarget`, and `P_MobjWasRemoved`, preserving collision callback reference order and `PARANOIA` checks.
- **Subsector cache** *(works on Xbox; the larger cache is untested)*. UWP caches `R_PointInSubsector` results for 4096 recent points (2048 sets of two; 512 before, which answered only about 60% of lookups in races) and clears them when the BSP loads or is freed.
- **Lua userdata** *(works on Xbox)*. Every platform tracks pointers with Lua userdata, so freeing a pointer without userdata skips Lua.
- **State bookkeeping** *(works on Xbox)*. Every platform gives each `P_SetMobjState`/`P_SetPlayerMobjState` nesting depth its own table and clears only recorded states. Calls that remove an mobj balance the nesting count instead of making later calls look nested.
- **Interpolation list** *(works on Xbox)*. Every platform records each mobj's interpolation-list slot so removal needs no search.

### Frame pacing and threads

- **Pacing** *(skipped frames work on Xbox; the schedule is untested)*. On UWP the frame cap sleeps to a running schedule instead of padding every loop to a whole frame on its own. A quick frame after a slow one that ran game tics draws immediately until the schedule catches up. A delay of more than four frames, for example after a load, is dropped. Scenes faster than the cap still run at an even rate. On tracks below 60 FPS, the old padding left the game idle 5–12% of the time on Xbox. Frames skipped to catch up on simulation never sleep, Unlimited never sleeps, and V-Sync with a cap matching the refresh rate still sleeps, following worleydl's Xbox timing fix.
- **Thread pool** *(works on Xbox)*. The pool uses Xbox's allocated processor count, falling back to upstream's hardware count when no processors are marked.

## Diagnostics

- **Startup and performance logs** *(works on Xbox)*. Startup records graphics/device capabilities, surface size, shader compilation, first-frame steps, loading/asset times, and logging cost, memory budgets, CPU sets, and thread-pool size. Every five seconds `UWP perf:` reports FPS, frame/tic, and HUD/present times, draws/uploads/resources, mobj/collision/Lua activity, subsector-cache hits, main-thread CPUs, profiler pauses, and renderer/portal CPU and GPU costs. In a level it also reports the map, gametype, game speed, active modes, racer, bot, spectator, and local player counts, the bots' level, and 3D model, drop shadow, and first-player FOV settings (the bots' level is untested on Xbox).
- **Driver counters** *(works on Xbox)*. `VibeRant perf:` includes `per frame` constant updates (`root CBV ring`), `pipeline:`, `rings:`, `textures:`, `models`, `texture heaps:`, `palette:`, `screens:`, `water:`, `portals:`, and `present:` statistics. These identify pipeline creation, upload peaks/wraps/stalls, storage, lazy models/mips, screen/fog/water copies, and synchronization, including the swap chain's copy, latency-wait, `Present`, and failure counts. Driver log lines start with their backend (`VibeRant D3D:`, `VibeRant Vulkan:`, or `VibeRant Metal:`), and its counters are `VibeRant perf:` lines, which only UWP builds log; builds before this change wrote `UWP D3D12:` and `UWP perf:   D3D12:` on Direct3D 12 (`uwp/tools/perf-summary.py` reads both). The precache line is `VibeRant: precache`.
- **ANGLE cost** *(works on Xbox)*. With the Software renderer, `UWP perf:   ANGLE GPU:` adds per-frame GPU time (timestamp queries on ANGLE's Direct3D 11 device) for the screen upload, 2D/upscale/ImGui, and total, with worst frame, idle until the next frame, and timed/not-ready/disjoint counts. Idle is not cost: the GPU reaches the end of the present only with the next frame's commands, so it's excluded from total. A stage the CPU feeds slowly reads as an upper bound. The profiler splits level samples by renderer (`Software: 3D view`, `VibeRant D3D: 3D view`), and `uwp/tools/profile-report.py` shows each phase's and renderer's share inside ANGLE (`libGLESv2.dll`/`libEGL.dll`); `perf-summary.py` averages the new line. On Xbox One X at 1920x1080, a Software race spends about 1.4 ms of GPU and 8% of its main-thread time in ANGLE, so a Direct3D 12 RHI for Software is deferred.
- **Spring probe** *(works on Xbox)*. `gr_springprobe` waits for the console to close, then logs one main-world view, excluding skybox/portal passes. `Spring probe camera:`, `Spring probe:`, `Spring entry:`, `Spring result:`, and `Spring probe end:` record camera/settings, sprite heights/quad/depth, wall/plane tests and cuts, remaining area, and piece limits without changing drawing.
- **Pixel history** *(untested on Xbox)*. `gr_surfaceprobe [x_percent y_percent]` defaults to `15 35` from the top-left and requires a level, hardware rendering, split-screen off, and Batching off. Capture starts after the console closes. `surface probe:` logs `begin`, changed-color `sample=` rows with source/texture/flags/shader/depth/alpha and up to eight vertices, and `end`; one 4 MB readback buffer holds up to 8,192 samples with 256 color-change reports and explicit overflow/omission counts, is released after the frame, and does no work while inactive. The captured frame stalls for readback, making it unsuitable for benchmarking. See [Direct3D 12 diagnostics](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/viberant-diagnostics.md) for row formats and timeout logs.
- **Screenshot camera position** *(untested on Xbox)*. Each screenshot taken in a level also logs `UWP screenshot camera:` with the file name, map, level time, renderer, the last drawn view's position, yaw, pitch, roll, FOV, and sector, so the view can be drawn again on a PC without holding still for the console.
- **Frame, title, and fade traces** *(works on Xbox)*. `UWP frame:` records positions, camera, elapsed time, tics, interpolation, title timers, and copied/shown slot IDs (the swap chain's back buffer) during titles and level seconds 10–20, capped at 300 frames per window. `UWP: track title:` summarizes animation timing; `UWP fade:` records state/load/wipe/palette changes in ten-second, 200-event windows and caps title-map/light-fade samples at 20 each.
- **Memory and stalls** *(works on Xbox)*. Perf summaries include DXGI local budget/usage and tracked texture, buffer, ring, render-target, and swap chain storage. `GPU frame exceeded 250 ms` logs once, while abandoned fence waits log at most once per second with suppressed warnings counted.
- **GPU failure details** *(untested on Xbox)*. Device removal and the first GPU-wait timeout dump DRED breadcrumbs when available, with page-fault details on removal. Search for `GPU wait for <what> timed out after N ms; breadcrumbs:` and `DRED:`.
- **Profiler and crashes** *(works on Xbox)*. `src/sdl/i_uwpprofile.cpp` samples the main thread about 50 times a second from the start of startup, writing stacks/activity to `E:\ringracers\uwp-profile.txt`. `uwp/tools/profile-report.py` reports activity by phase, separating play from startup, menus and the title screen, a paused or loading level, intermission, voting, the podium, and cutscenes. A vectored exception handler logs crashes and stacks because the app runtime bypasses the game's signal handler; it cannot catch stack-cookie termination.
- **Driver thread profiling** *(works on Xbox)*. During play, the profiler also samples the VibeRant D3D worker when it is running. The profile report lists its functions under the driver thread phase, separately from the main thread totals.
- **Error dialog** *(works on Xbox)*. The short Xbox dialog lists the error, visible drives, and their `ringracers` folders. It saves the text to `E:\ringracers\error.txt`.
- **Frame capture and comparison.** `-shottics 70,350,700` with a replay (`-shotghost RR_GREENHILLS-sonic-Name` plays a staff ghost straight from `staffghosts.pk3`, which `-playdemo` can't) draws exactly one frame per tic without interpolation, saves a screenshot of the finished frame at each listed level time as `<MAP>_<tic>.png` in the game folder's `framecapture` (or `-shotdir`), and quits. While capturing, the unsynced random numbers and the clock-driven HUD animations depend on the level time alone, and what animates by the time between two frames gets one tic per frame (Legacy GL's underwater and heat waves went by how long the machine took over each frame, so its frames with them differed from run to run), so two runs of the same replay give identical files with any renderer, on Linux and on Windows. `tests/frame-compare` runs a list of replays on two builds or renderers (native, or a Windows build under Wine) and reports, per frame, how many pixels differ and by how much, with side-by-side images and an HTML summary. Its baseline: VibeRant D3D against itself, 90 of 90 frames identical.
- **`-warp` and `-d3ddebug`: VibeRant on a machine without a GPU.** On a desktop build, `-warp` makes VibeRant D3D use Windows' WARP adapter and VibeRant Vulkan a CPU device (lavapipe), and `-d3ddebug` turns on the Direct3D 12 debug layer and copies its error messages to the log as `D3D12 debug ERROR` (with VibeRant Vulkan it means `-vkdebug`). CI runners can use these flags to play the game with a renderer and log errors. Neither flag appears in a menu. Both are opt-in, and UWP ignores them. See [docs/viberant-diagnostics.md](docs/viberant-diagnostics.md).
- **Automated map sweeps.** The Map sweep workflow runs on demand and nightly when `master` has moved. It plays each of the 213 maps' staff ghost with Software, Legacy GL, and VibeRant Vulkan on Ubuntu hosted runners (Xvfb, Mesa llvmpipe and lavapipe, Vulkan validation on) and with VibeRant D3D on Windows (WARP, Direct3D debug layer on), takes five frames per map at 640x400 (320x200 or 1280x720 on request), and fails on a crash, a hang, a missing or wrongly sized frame, `I_Error`, a "not implemented" line, a fallback to Software, or a validation or debug layer error. Each renderer's frames are compared with its last complete sweep of `master` (a plain measure and a texel-edge-insensitive one, before, after, and difference crops of the worst frames, and any runner image or driver change). Each sweep of `master` provides the next baseline. The report also compares VibeRant Vulkan and VibeRant D3D for reference. Maps known to differ from run to run can be listed (`tests/map-sweep/unstable.json`) so that they are reported without making a sweep red; Legacy GL had 23 there until its waves and the sky dome's caps were made repeatable, and the list is empty now: two sweeps of code that draws alike give the same 1,065 frames with Legacy GL and with both VibeRant backends, and all but three pixels of one frame with Software. Python unit tests (CTest `map_sweep`) cover the ghost list, sharding, comparison, and report generation. `AGENTS.md` asks for a sweep of any branch that changes rendering. See [tests/README.md](tests/README.md), "Automated map sweeps".
- **Tools.** `uwp/tools/` summarizes performance logs, resolves profile/crash addresses to functions, and annotates instructions with samples.

## Other fixes

- **Overflowing math matches the PC game** *(works on Xbox)*. The Xbox build compiles the engine with `-fwrapv`, so signed integer overflow wraps around as it does in the official Windows build, which MSVC compiles. Without it, clang assumed overflow can't happen and sometimes kept a wider result instead: deciding which side of a map partition a point is on (`R_PointOnSide` and `R_PointInSubsector`), it multiplied the unwrapped 64-bit difference of two coordinates, while the PC game multiplies the wrapped 32-bit one. The two could disagree when a point was 32,768 or more map units from the start of a partition line, which changes which part of the map an object is found in. The disassembly of both builds shows the difference; other overflowing arithmetic gets the same treatment. In the build with it, `R_PointOnSide` and `R_PointInSubsector` subtract in 32 bits, as the PC game does.
- **Switching to Software after starting in a hardware renderer** *(not on Xbox, which always starts in Software; works on Linux)*. Switching to Software now creates the state it needs to show frames. A game started in a hardware renderer (`-opengl`, `-d3d12`, `-vulkan`, or the Vulkan default) previously crashed on the switch. Software normally creates that state on its first frame, but the switch occurs mid-frame after the other renderer has already begun drawing. Upstream has the same crash after `-opengl`.
- **Quitting when asked by a signal** *(not on Xbox; works on Linux)*. The game now handles a quit signal from its event loop, as it does when the window closes. Ctrl+C in the terminal that launched the game, `kill`, and the end of a desktop session send a signal. The old handler ran the entire shutdown wherever the signal interrupted the game. When that was inside a memory allocation or a graphics driver call, the shutdown hung or crashed, and the frozen window stayed until the desktop offered to end it. The handler now only records the request. A second signal ends the process at once, for a game that isn't getting back to its event loop. Seen with Software and with VibeRant Vulkan, and upstream has the same handler. In a test that kept changing the window with Vulkan's validation layers on, three of four runs ended hung or crashed before, and none of four after. `quit_signal` tests the handler.
- **Options button slide** *(works on Xbox)*. Submenu title buttons start their slide once and finish at or after the final tic, preventing repeated bouncing when low frame rates skip a menu tic.
- **Console slide** *(works on Xbox)*. On every platform, opening and closing use elapsed time since the last movement, keeping the intended speed through skipped frames and stalls.
- **Controller ignored after loading** *(works on Xbox)*. Controller input during loading no longer causes a full queue to erase controller registration. Previously, moving a stick or pressing buttons a lot during loading could leave the controller dead for the session. The title screen reacted to a press, then every menu ignored it. The input queue has 128 slots and holds up to 127 pending events. Previously, filling the last slot lost every queued event, including the one that registers the controller, and nothing reads the queue while the game loads. A full queue now drops only its oldest event, and still registers or removes a controller when it does. The same loss was possible on every platform during any long load.
- **Duplicate controllers** *(works on Xbox)*. `uwp/patches/sdl-controller-duplicates.patch` prevents duplicate controllers and double-counted presses in Game mode.
- **Camera Position** *(untested on Xbox)*. Options → Video → **Camera Position...**, between Color Profile and Advanced, gives each of the four local players a **3rd Person** (the default) or **1st Person** view. It sets the game's own `chasecam`, `chasecam2`, `chasecam3`, and `chasecam4`, which had no menu entry and weren't saved; they are now saved in `ringconfig.cfg` and still take `on` and `off` in the console. The view is local, so netplay and replays are unaffected, and the menu is there on every platform. An unmodified game given the same config file starts in first person too; `chasecam on` in its console switches it back.
- **Title screen in first person** *(untested on Xbox)*. The title screen and any other view of a player without a kart now use the ordinary camera on every platform. Returning to the title screen with a player set to 1st Person previously crashed (`access violation` in `R_SetupFrame`) because the first-person view needs a kart and the title map has none. Upstream has the same crash after `chasecam off`; it mattered more here because Camera Position saves the setting.
- **First-person view on slopes** *(works on Linux with VibeRant Vulkan and Software; untested on Xbox)*. The first-person view now pitches by the ground's slope in the direction the view faces, uphill or downhill, and returns to level in the air. It eases over a few tics (a quarter of the way each tic) so slope changes don't snap the view. Previously the view stayed level whatever the kart stood on, so on a steep slope, as in Marble Garden, it stared into the ground on the way up and over the track into the sky on the way down. Third person doesn't have this, because its camera sits behind the kart and looks at it. Only the view changes: nothing of the game's state, a netgame, or a replay depends on it, and third person is pixel for pixel what it was. **Screen Tilting** (the sideways roll on inclines) is separate and unchanged.
- **First-person view after the finish** *(works on Xbox)*. In first person, the view keeps turning with the kart once the game takes over its steering after the finish line; it used to stay pointing where the player last steered while the kart drove on. The chase camera already followed the kart there, and first person now does the same on every platform, so netplay and replays are unaffected. The first version of this did nothing *(confirmed on Xbox)*: it sat in the chase camera's code, which doesn't run for a first-person view. The view's angle is now updated in the camera pass that runs every tic for every view *(checked under Wine with a script that makes the game steer the kart)*.
