# Changes from Ring Racers v2.4

Changes from vanilla [Ring Racers v2.4](https://github.com/KartKrewDev/RingRacers/releases/tag/v2.4). Engine changes are commits in this repository, on top of upstream's `maintenance-2.4`; SDL changes live in `uwp/patches/sdl-angle.patch`, `uwp/patches/sdl-controller-duplicates.patch`, and `uwp/patches/sdl-egl-surface-handoff.patch`; `uwp/` holds the Xbox app's launcher and `uwp/build.ps1` builds it. The app was a separate repository, [ringracers-uwp](https://github.com/ZebulanStanphill/ringracers-uwp), until its history was merged into this one; entries written before that say "the fork" for the engine.

Unless stated otherwise, changes apply only to UWP builds (`SRB2_CONFIG_UWP`, which defines `_UWP`). The GL2 RHI's general call reductions and OpenGL ES support, colormap caching, most Software optimizations, UDP error handling, Lua userdata set, state bookkeeping, and interpolation-list changes apply to every platform built from the fork. Individual Legacy GL entries identify other shared changes.

Game logic results are unchanged. Optimizations do the same work in less time, preserving replay, netplay, and ghost behavior. Status markers mean *(works on Xbox)* or *(untested on Xbox)*; qualifiers identify partial coverage. Confirmation refers to Xbox One X, including features confirmed before the driver replacement and carried forward unchanged. Build, CI, and tools have no Xbox marker.

## Platform and build

- **UWP library and launcher.** `SRB2_CONFIG_UWP` and the `ninja-x64_windows_uwp_vcpkg-release` preset build a static game library without a Git revision suffix in its executable name. The launcher starts it through `SDL_WinRTRunApp`, caches the CoreWindow on the UI thread, and reports the process memory budget; this builds on [worleydl's port](https://github.com/worleydl/ringracers-uwp), rebased onto v2.4.
- **Dependencies and CPU.** SDL2 and libuwp come from [worleydl/uwp-dep](https://github.com/worleydl/uwp-dep). The game targets Xbox One's Jaguar CPU with `-march=btver2`, also supported by Xbox Series X|S; Jaguar has no FMA, preserving the floating-point behavior of other x64 builds.
- **Direct3D 12 option.** The CMake option `SRB2_CONFIG_D3D12` builds VibeRant D3D (`src/hardware/r_d3d12`) and defines `HAVE_D3D12`, which guards every engine call into it; it is available for Windows builds; Linux builds have the driver with its Vulkan backend instead (see **VibeRant Vulkan**), and macOS builds leave the driver out. Renderer code the driver depends on (portals, water surfaces, shader fog, per-pixel distortion, palette rendering) is under `HAVE_D3D12` as well and compiles without `_UWP`, which the Linux CI job checked before Linux built the driver itself; this prepares the driver for Windows desktop builds and changes nothing in a UWP build. What depends on which driver draws (the level walk, portals, sky claims, void walls, wall light slices, fog, water states, post-processing, rolled sprites) asks `HWR_D3D12()` when the game runs instead of being chosen when it is compiled, so that one build can hold both this driver and OpenGL; a UWP build answers with a constant and behaves as before *(works on Xbox, walls crossed by 3D floors included)*.
- **VibeRant D3D on Windows desktop.** The driver can draw the finished frame scaled to fit a window-sized swap chain, with linear filtering and black bars (`screen_scaling::FitRect`), for a presenter whose system doesn't scale the swap chain. UWP builds never ask for it; their frame placement only gains a second sampler *(Screen Scaling still works on Xbox)*. The driver presents on ordinary Windows windows too *(tested under Wine only)*: a new presenter (`d3d12_present_win32.cpp`) puts its swap chain on a child window of the game's window, which never takes input or focus and goes away when Software takes over, so the game window's OpenGL contexts are untouched. The UWP presenter is unchanged. A desktop build with the driver also keeps OpenGL: Video Options > Advanced > Renderer offers Software, VibeRant D3D, and Legacy GL, and `-d3d12` starts with VibeRant D3D as `-opengl` starts with Legacy GL. One hardware driver is used per run of the game: switching between Software and it is immediate, and choosing the other hardware renderer is saved and takes effect at the next start, which a popup and a console line say. UWP builds keep their two choices *(works on Xbox)*. Windows desktop builds made with MSVC or clang-cl include the driver by default; MinGW builds don't, as its shaders are compiled with the Windows SDK's `fxc`.
- **Fork version** *(works on Xbox)*. On every platform, the title screen, the `version` command, and one line of the startup log show the fork's own version on top of Ring Racers', as `v2.4_z1`. A build from a commit that isn't a release tag is a development build and reads `v2.4_z0-dev (1a2b3c4d)`: the number of the last release (`z0` before the first) and the commit. A release is an engine commit that raises `FORKVERSION` in `src/fork_version.h` and is tagged `2.4_z1`; the Build workflow fetches the tags of the engine commit, so a tagged engine commit builds as a release. Netplay, replays, and Lua's `VERSIONSTRING` keep the vanilla version. The letter was a capital `Z` when this was confirmed on Xbox; the lowercase `z` is untested there.
- **Package.** Each build's package version is Ring Racers' version followed by the Build workflow's run number, such as 2.4.0.123, so a later build is always a newer version; a local build ends in 0. Windows treats installing an older build over a newer one as a downgrade. The project, executable, linker map, and package are named `ring-racers-ze` (the package file is `ring-racers-ze_<version>_x64.msix`), and the `uwp/tools/` scripts read the module name of earlier `ringracers-uwp` builds too, so their logs and profiles still work. The Build workflow checks the version in the finished package. The app is shown as "Ring Racers ZE" (in the app list and in the launch-time message about Dev Home's App type), with the package identity `ZebulanStanphill.RingRacersZE`, publisher `CN=ZebulanStanphill` (the CI certificate's subject), and publisher name "Zebulan Stanphill". This is a new app to Windows, so it installs beside the earlier "Ring Racers" package instead of updating it, and the earlier one can be uninstalled: the config and saves are on the USB drive (`E:\ringracers\ringracers`) and stay, while the game data the earlier app copied to its internal storage goes with it, and the new app makes its own copy. The manifest requests file system, removable storage, network, expanded resources, and microphone access for voice chat. The `expandedResources` capability is what Microsoft documents as granting Game Mode resources on Xbox: CPU cores reserved for the app and a memory partition of at least 4 GB, where plain apps get a share of the cores, 1 GB, and, on Xbox One, no Direct3D 12. On an Xbox One X the game got Direct3D 12, the same 5 GB memory budget, and the same race speed with Dev Home's App type set to App or to Game, so the type doesn't need changing; with Game, the console reports each controller twice, which the SDL patch handles. Runtime DLLs are not copied beside the static library. The small logo (`Square44x44Logo`, the icon shown at small sizes) is Dr. Robotnik's face *(untested on Xbox)*, taken from the game's own icons. The 88-pixel version is the macOS icon's detailed face over a night sky: that icon is 64×64 pixel art, and its middle 44×44 pixels, which lie inside the icon's rounded shape, are doubled without smoothing to fill the square. The 24-pixel version is the simpler 16×16 face of the Windows desktop icon on a transparent background. The small logo was a shrunken copy of the box art, which is unreadable at that size; the medium tile keeps the box art.
- **Audio** *(works on Xbox)*. The audio driver is WASAPI instead of DirectSound.
- **Build script.** `uwp/build.ps1` builds the engine and SDL2 with the SDL patches in `uwp/patches/`, verifies ANGLE's download with SHA-256, and generates the launcher solution.
- **CI.** The Build workflow builds the Xbox app; the Tests workflow runs 36 native regression tests with ASan/UBSan, a `warp` job that compiles 97 translated add-on shader stages for Shader Model 5.1 and runs the Direct3D 12 WARP harness with the debug layer and GPU-based validation, a `vulkan` job that runs the same driver test on Vulkan (see **VibeRant Vulkan**), a Linux build with the driver's Vulkan backend, a macOS build without the driver, and a Windows desktop build with both backends beside OpenGL; the Windows desktop build (not UWP, `clang-cl` and vcpkg) is uploaded as `windows-desktop`, and the `warp` job also runs the desktop presenter on a hidden window. Each test was checked by mutating the production code it covers. Tests that ran identical code, duplicated a WARP pixel check, or only parsed a debug command were removed. Negative controls assert their specific rejection in-process instead of passing on any failure; WARP keeps four shader and feature mutants as separate processes and checks every other oracle with a self-test and a registry of the scenes that ran. The WARP job caches its glslang and SPIRV-Cross build per runner image. [tests/README.md](tests/README.md) describes coverage and limits.
- **Build artifacts.** The `build` job uploads a sideloadable `.msix` signed with a throwaway certificate, that certificate (an Xbox in Developer Mode doesn't need it; a Windows PC does), and the linker map (`ring-racers-ze-symbols`). Actions use Node.js 24 releases, and Visual Studio's Developer PowerShell exports the x64 environment to later steps.
- **Profile-guided optimisation** *(recording works on Xbox; optimised build untested)*. Running the Build workflow by hand with `pgo_generate` makes an instrumented package (`ring-racers-ze-pgo-instrumented`) that records which engine code runs, saving it to `E:\ringracers\pgo\` at a clean quit, before the app is suspended, and on the `pgo_dump` console command. Recordings committed to `uwp/pgo/` are merged with the `llvm-profdata` matching the compiler and used by every later build to lay out and inline the engine's hottest code; without any, builds are unchanged. It doesn't change what the code does, so netplay and replays stay compatible. [docs/uwp-pgo.md](docs/uwp-pgo.md) describes collecting them. `uwp/pgo/` holds two recordings from the instrumented build of dc41df4 on Xbox One X: about 28 minutes of local races in VibeRant D3D at 1920x1080, plus menus.
- **Shader smoke test.** The [installable PK3](tests/addons/shader-smoke/README.md), which the Tests workflow uploads as `shader-smoke-test`, supplies shader-only checker and water-ripple effects without gameplay scripts or replacement assets.
- **Renderer test map** *(works on Xbox)*. The [installable PK3](tests/addons/renderer-test/README.md), which the Tests workflow uploads as `renderer-test-map`, is a generated UDMF map (`map RR_RENDERTEST`) for driving around freely, with a room each for fog, overlapping water and heat haze, polyobject ripples, wall light slices, translucent ordering, and brightmaps, a rainy hall whose sky shows a separate, brightly lit skybox room where rain must not be drawn (judged from a covered sky pit off the hall's east end, which has no rain of its own), and item boxes that become a sprite-textured model when its `models/` folder is installed beside `ringconfig.cfg`. It has no finish line, checkpoint, or waypoints *(their removal is untested on Xbox)*, so the round never ends, the item boxes show from the start, and the hand that points out the wrong way never appears; the engine logs three errors about the missing waypoints and finish line each time the map loads, which are expected. The add-on removes AI racers on this map, including bots added after loading, while keeping local split-screen players and leaving other maps and bot settings alone. Its scenery objects replace any game object that already uses their editor numbers when the map loads, logging which object it was. It carries an Encore remap that swaps red and blue, since without one Encore only mirrors the screen. A wing of nine numbered rooms off the Brightmaps room *(works on Xbox)* covers the Software-matching fixes that no base-game map exercises: a fog-style line beside an ordinary translucent one, two rooms of fullbright sprites with and without `colormapfadesprites`, `RF_SHADOWDRAW` objects on flat ground and a ramp, translucent overlay sprites beside a plainly translucent one, a pad (and the `rendertest_darkness` console command) that triggers level darkening beside areas at three light levels, a tree-line texture between two skies as at Municipal Meadow's skybox edge, a wall of numbered bands with a marked standing spot for comparing the renderers' view width in two-player split-screen, two bays of ordinary, semibright, and fullbright posts at sector light 128 and 96 (the darker one doubles as a dark-sector check), and the tree line again under a sky ceiling lower than its tips. Enable `cheats on` before using the map command. The water room has a long descent into a 608-unit-deep pool, a large flat bottom for submerged chase-camera views, and a far ramp back to the dry heat-haze ledge. `build.py` generates every texture, sprite, and the map from code and runs ZDBSP, which CI builds from source to verify the committed PK3; it ships the sign's brightmap as a Doom patch and gives the orb's brightmap the orb's exact transparency, since vanilla Software can't read a PNG texture brightmap and walks a sprite's and its brightmap's columns together.

## VibeRant D3D renderer

- **Small-texture atlas** *(works on Xbox)*. Less slowdown when many color-changing sprites appear, such as multiplayer invincibility: VibeRant shares texture pages instead of creating a resource for every sprite translation. In online races on an Xbox One X, resource creations fell from about 150 to about 6 every five seconds. Pages left empty, as after a level change, give their memory back, except one kept ready *(untested on Xbox)*; before, a session's pages only ever grew, to 35 (560 MB) in a two-hour one. `gr_textureatlas` (On by default) flushes textures when toggled for comparison. See [the atlas notes](docs/d3d12-texture-atlas.md).

### Direct3D 12 driver

- **Renderer and default** *(works on Xbox)*. VibeRant D3D draws upstream Legacy GL through `src/hardware/r_d3d12/` and is the default for new configs; valid saved renderer choices remain effective. Startup logs `UWP: VibeRant backend: D3D12`, and a failed driver start falls back to Software.
- **Shaders** *(works on Xbox)*. `fxc` compiles the built-in HLSL at build time for Shader Model 5.1 with an embedded root signature. Xbox One X exposes feature level 12_0 and Shader Model 5.1; Xbox One has no Shader Model 6.
- **Presentation** *(works on Xbox)*. Starting Legacy GL takes the window from ANGLE (with the first drawn frame instead if no ANGLE context exists yet, as with `-opengl`), and each frame is then copied into the driver's own three-buffer flip-model swap chain and shown at once, with `vid_wait` as the sync interval and a frame latency of 2. A screen whose aspect ratio differs from the window's is letterboxed. A CoreWindow takes one swap chain at a time, so `patches/sdl-egl-surface-handoff.patch` lets the driver destroy ANGLE's window surface, and recreate it when Software is chosen. If taking the window fails at startup, the game falls back to Software; a failure to take it with the first frame, resize the swap chain, or give the window back stops the game with an error. [Diagnostics notes](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/d3d12-diagnostics.md) describe the logs.
- **GPU synchronization** *(works on Xbox)*. The swap chain shares the driver's queue, so frames need no synchronization with ANGLE. The 2026-10-16 Xbox logs confirm the swap chain taking the window, giving it back for Software, taking it again, resizing, and letterboxing.
- **Resources and constants** *(works on Xbox, including 3D models and mipmaps)*. Drawing constants use a root-CBV ring, and fence completion controls resource and descriptor reuse, resizing, and shutdown. Models, indices, and sky buffers use persistently mapped 4 MB upload arenas; the driver generates RGBA8 mip chains on the CPU and skips redundant topology, stencil-reference, and viewport changes.
- **Texture heaps** *(works on Xbox)*. Textures use shared 16 MB heaps with 4 KB or 64 KB alignment, quarter-octave size classes, and a 4 KB guard after each reported allocation; textures exceeding the 4 MB class limit including the guard, or failing placement, get a dedicated heap with a spare 64 KB page. Committed textures remain a logged last resort: the guards protect against Xbox One's resource-state word corrupting neighboring or final texels, and the 2026-10-16 Xbox log shows dedicated heaps with zero committed textures; see [texture placement](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/d3d12-texture-placement.md).
- **Pipeline prewarming** *(works on Xbox)*. One worker prewarms 36 built-in shader pairings without blocking draws. `UWP D3D12: prewarmed` and the first 64 main-thread `PSO #` cache misses report creation cost.
- **Add-on shaders** *(works on Xbox)*. Pinned glslang and SPIRV-Cross translate `SHADERS` GLSL into Shader Model 5.1 HLSL for polygon, sky, and model layouts; `D3DCompile` compiles it, and load-time pipeline validation rejects invalid programs in favor of built-ins. Missing stages use shared built-in GLSL, Ignore custom shaders keeps built-ins, and custom sprite stages also cover clipped sprites; compiler notices ship in `Licenses`.
- **Custom water and shader limits** *(works on Xbox)*. Custom water color keeps built-in refraction through a composite variant; a custom vertex stage requires a whole-viewport capture, while capture/variant failure or Reduce VFX uses normal blending without refraction. Underwater/heat postprocessing stays built-in, arbitrary uniforms use their initializer or zero without engine setters, and uninitialized uniform arrays and extra vertex attributes remain unsupported; see [add-on shader notes](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/d3d12-custom-shaders.md).

### VibeRant Vulkan

Not on Xbox: these entries are for Linux and Windows PCs, and say what they were tested on.

- **VibeRant Vulkan** *(works on Linux with an AMD Radeon (RADV); the Windows build is tested under Wine only; other GPUs untested)*. The VibeRant driver also runs on Vulkan, as a renderer of its own name: the hardware renderer for platforms without Direct3D 12, and a second choice on Windows. It is the same driver, not a port of it: `src/hardware/r_d3d12/vulkan` implements the dozen Direct3D 12 interfaces the driver uses (about 70 methods) on Vulkan 1.1, and the driver's drawing code, shaders (`shaders.hlsl`, compiled to SPIR-V by glslang), textures, and states are shared, so a fix to one renderer is a fix to both. Everything listed for VibeRant D3D applies: palette rendering, portals, fog, water, wipes, brightmaps, add-on shaders, screen effects, Screen Scaling, and the rest. [docs/vulkan-backend.md](docs/vulkan-backend.md) describes the mapping. Vulkan is loaded when the renderer starts, so a system without it, or without a usable device, falls back to Software with a console message. `-vulkan` starts with it, and `-vkdebug` adds Vulkan's validation layers, whose messages go to the log.
- **Same picture as VibeRant D3D** *(measured on one PC: Radeon Vega 10, RADV, with VibeRant D3D running under Wine on the same GPU)*. The Windows build drew the same 1,002 frames with each backend (five moments of the first staff ghost of each of the 213 maps, taken with the frame capture mode), and they were compared pixel by pixel. In the median frame 0.08% of the pixels differ, in 95% of the frames fewer than 0.18%, and in the worst 1.4%. What differs is arithmetic in the last bit: the two backends' shader compilers don't round identically, so a pixel whose texture coordinate falls on the edge between two texels can take the other texel. Setting those pixels aside, 958 of the frames differ in at most 0.02% of their pixels and four in more than 0.1%: two of Daytona Speedway, where a fine texture is far away, and two where surfaces lie in the same plane and depth rounding decides which one shows (a wall in Ice Paradise that Software doesn't show and Legacy GL shows whole, which VibeRant has since stopped drawing (see **Walls of sectors whose ceiling is below their floor**), and an effect in Haunted Ship that lasts one tic). The Linux build's frames against the same VibeRant D3D frames give the same figures. Vulkan's validation layers reported nothing in races on 43 of the maps, in the menus, or while the window was resized, floated, tiled, and made fullscreen. Direct3D 12 under Wine is itself translated to Vulkan, so this compares the two backends on one GPU, not against Microsoft's Direct3D 12 or the Xbox. Devices without 24-bit depth (AMD's) use 32-bit float depth here.
- **Its window** *(works on Linux under Hyprland; the Windows build under Wine)*. The game's window is OpenGL's, for Software's frames, and a window can't be both OpenGL's and Vulkan's, so VibeRant Vulkan presents on a second window that takes the first one's place, size, fullscreen state, title, icon, and input, and gives them back when Software takes over. Where VibeRant Vulkan is the default, the OpenGL window stays hidden until a renderer that needs it is the one running, so starting the game shows one window. The swap chain is the window's size and the frame is placed in it as on Windows desktop: Screen Scaling's Integer and 1:1, or scaled with linear filtering to fit.
- **Renderer setting** *(works on Linux)*. Options → Video → Advanced → Renderer lists **VibeRant Vulkan** where the build has it: Software, VibeRant Vulkan, and Legacy GL on Linux, and Software, VibeRant D3D, VibeRant Vulkan, and Legacy GL on Windows. Its description and options header name it. Switching between Software and the running hardware renderer is immediate; another hardware renderer, including VibeRant's other backend, takes effect at the next start, as before. The saved value is `renderer "VibeRant Vulkan"`.
- **Default renderer on PCs** *(works on Linux)*. A new config starts with VibeRant Vulkan on Linux and with VibeRant D3D on Windows desktop builds that have it, instead of Software. A saved renderer is kept.
- **Driver test on Vulkan** *(passes on the Radeon and on lavapipe in CI)*. The driver's pixel test (`tests/d3d12-driver.cpp`, the one the `warp` job runs on Windows) also builds on Linux against the Vulkan backend (`tests/run-vulkan.sh`): the same 114 scenes and six negative controls, with any Vulkan validation error failing the run in place of Direct3D's debug layer. CI runs it on lavapipe, Mesa's CPU device. One scene starts from another color on Vulkan: AMD's hardware rounds a color it writes down where the exact value is within a hair of the next level, which put the grouped water scene's expected green one step outside its tolerance on the Radeon, and a starting color away from that edge checks the same thing on every device. The test found that the backend reported Vulkan's own (smaller) alignment for textures where the driver expects Direct3D's 4 KB and 64 KB placement classes, which made the driver give 18 of 376 small textures a heap each; it now reports the classes.
- **Build options.** `SRB2_CONFIG_VULKAN` builds the backend and defines `HAVE_VULKAN`; it is on by default for Linux and for Windows desktop builds made with MSVC or clang-cl, which then hold both backends in one program (`HAVE_D3D12_NATIVE` marks Direct3D 12 itself), and never for UWP, whose build is unchanged. `HAVE_D3D12` now means the driver is built, with either backend. Configuring downloads pinned Vulkan-Headers, volk, and, off Windows, Microsoft's MIT-licensed DirectX-Headers, beside the glslang and SPIRV-Cross the driver already used; `-DSRB2_CONFIG_VULKAN=OFF` builds without any of it.

### Matching Software

- **Palette rendering** *(works on Xbox)*. Ported from SRB2, palette rendering lights surfaces through colormaps, limits colors to the palette, and applies palette flashes and the color profile to the whole frame. It rebuilds cached textures when Encore's remap changes, preventing colors from the previous normal/Encore race from carrying over; without palette rendering, flashes remain white or pink overlays.
- **Brightmaps** *(works on Xbox, including Encore)*. Brightmapped pixels use the base colormap's full-bright row rather than a sector's tint/fade, in palette and smooth rendering, while retaining Encore's texel remap. SPRTINFO sprite brightmaps include roll rotation with the base patch's transform, pivot, flip, and origin; missing or differently sized maps fall back to ordinary lighting, and cache reloads/purges release rotated companions. Sprite brightmap selection and rotated companions apply to every platform.
- **Springs** *(works on Xbox)*. Springs use Software's origin and sprite-height sorting against solid walls, two-sided upper/lower walls, and opaque 3D floor sides and planes, including nearer faces drawn over them. Clipping removes rounding slivers and clamps crossed sprite light slices to prevent bow-ties, hiding Metropolis's springs inside bumpers without dashes; ordinary sprites and translucent or see-through sides retain per-pixel depth behavior. Flat silhouettes (all within a tenth of a pixel's angle of one plane through the camera), such as the seam between two sloped floors on one plane that Software leaves undrawn, no longer clip springs *(untested on Xbox)*; one beside the camera in Green Hills Zone had cut a whole row of springs out.
  - **Springs beside a 3D floor plane** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. Software sorts a spring behind a 3D floor's plane only if the plane is nearer than the spring somewhere in the spring's own screen columns. The hardware rule looked at the plane's nearest corner anywhere, so a plane that passes beside a spring on its way towards the camera counted: in Endless Mine, the springs on the side of a diagonal beam, whose tops are under the beam's top, were cut away almost entirely where Software shows them whole. The rule now cuts the plane to the spring's columns first. Found by a sweep of all 213 maps; Metropolis's bumpers are unaffected.
  - **Spring 3D models** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. With **3D Models** on, a spring was drawn as a model with ordinary depth testing, so the tips of the springs inside Metropolis's yellow bumpers poked through the bumpers' faces. A spring's model now follows its sprite: it isn't drawn when Software's rule leaves nothing of the sprite, and when part of the sprite is left, VibeRant hides the model behind the same silhouettes that cut the sprite (marked in the stencil buffer's top bit while the model is drawn, within twice the sprite's size since a model can be larger than its sprite). Legacy GL hides a fully hidden spring's model too and draws a partly hidden one whole. In a Metropolis replay the bumpers' tips are gone. Of 1,002 frames from the 213 maps, nine changed, all of them spring models that no longer show through a wall or a floor: springs set into walls in Obsidian Oasis and Mega Collision Chaos, which Software hides too, and a few distant ones that now show exactly as much as their sprites do.
  - **Clipping bounds** *(works on Xbox)*. Capacity checks prevent spring and near-plane clipping from overrunning buffers; an oversized silhouette is ignored or its affected triangle remains whole, so a rare spring sliver can remain visible.
- **Water** *(works on Xbox, including split-screen and overlapping volumes)*. Translucent ripple surfaces refract the scene behind them. Unlike Software, which distorts only the background, this also refracts visible submerged geometry. It uses Software's wave timing, distance attenuation, and signed pixel rounding with viewport clamps and six blend modes. Coplanar pieces share an immutable, bounded capture expanded by disjoint strips and a 16-pixel ripple margin; intervening draws, different layers/slopes, or polyobjects start fresh captures, and the shared-platform `FOF_CUTEXTRA` rule removes hidden internal water/fog boundaries as Software does, retaining touching or different-kind boundaries.
  - **Water fallbacks** *(works on Xbox)*. Offscreen faces need no copy, near-plane crossings use conservative full-view bounds, and standalone polyobjects use bounded per-face captures. Reduce VFX disables distortion, opaque ripple surfaces keep texture-only ripples, and capture failure retains ordinary rendering; controlled Xbox performance comparisons remain pending.
- **Underwater and heat distortion** *(works on Xbox, including split-screen)*. Per-pixel sampling follows Software's wave shapes and tic timing rather than Legacy GL's coarse grid; underwater displacement reaches 1% of the full frame width, and sampling clamps to each viewport without affecting the HUD. Reduce VFX disables both effects, and desktop OpenGL retains its grid and single-view limit.
- **Fog** *(works on Xbox)*. With Shaders on, fog walls and planes remap the captured scene inside colored, inward, outward, and overlapping boundaries, using Software's integer light rows and control colormaps in palette mode or tint/fade equations in smooth mode. Each visible face copies its projected bounds into one retained RGBA texture, preserving portal/viewport clipping without depth writes; custom fog shaders own their output, and allocation failure uses the old shader.
  - **Fog approximation** *(works on Xbox)*. Shaders Off and desktop OpenGL retain one cached inward neutral camera-fog approximation: cap surface light, apply the colormap and sky attenuation once, and omit that block's boundary polygons. This shared-platform path needs no scene copies but can differ from Software in color, brightness, and boundary placement; colored, outward, and overlapping fog retain older paths.
  - **Overlapping fog order** *(works on Xbox)*. Every hardware renderer keeps fog planes at the same height in the order their fog blocks were created, so overlapping fog no longer switches color with the viewing angle; the first block wins, as in Software, though Software also draws the second block's plane in the first block's colors. Looking out from inside the overlap, the shared boundary wall also shows the first block's color, where Software shows the second's; hardware keeps the first, matching the fog you're standing in.
- **Palette fades and wipes** *(works on Xbox)*. Palette Rendering uses Software's fade-map rows before the HUD, clamps strength to the available rows, and leaves flashes/color correction to the final palette pass; missing resources or Palette Rendering Off use the overlay (`path=exact` or `path=overlay`). Transitions support black/white Mega Drive-style fades, inversion, Encore wiggle, and reversed fades, with the final current frame shown immediately; an unavailable full wipe falls back to two passes.
- **Encore inversion flag** *(works on Xbox)*. `PF_Invert` has a separate bit from depth writes so blend selection recognizes screen inversion instead of drawing a white quad.
- **Portals** *(works on Xbox, including split-screen)*. Special-40 linedefs show their paired destination through stencil openings and exit-plane clipping, using Software's tag pairing, rotation, and floor-height offset; the approach credits [SRB2Kart Saturn](https://github.com/Indev450/SRB2Kart-Saturn). `maxportals` defaults to 2, with 0 disabling portals; recursive views use the regular sky, maps without portals skip the search, and the player model can disappear near an opening as in Software.
- **Sky alignment and horizon boundaries** *(works on Xbox)*. Sky domes and the flat fallback honor single-patch header offsets, and empty two-sided sky boundaries no longer extend opaque floors over the background, fixing Water Palace's sky position and cutoff. The horizon check applies on every platform; real boundaries still extend, and signed sky offsets use multiplication instead of undefined negative left shifts.
- **Skybox visibility** *(precipitation works on Xbox; `RF_HIDEINSKYBOX` untested)*. Precipitation and things marked `RF_HIDEINSKYBOX` are excluded from skybox views on every platform. Upstream's Legacy GL draws rain in the skybox.
- **Black void** *(works on Xbox: no stray black walls, Green Hills Zone's skies and Municipal Meadow's skybox buildings show; the black under a step with the camera underground hasn't been seen there)*. Screen areas the level doesn't cover, such as gaps with nothing behind them, views out of the map, or the camera clipped into a wall, are black, as in Software, instead of showing the sky that was drawn behind everything. The sky shows only through sky surfaces: sky-flat floors and ceilings, from the side they face (including opaque 3D floors with the sky flat) and the existing sky walls, which write depth without color; one full-screen pass per view then blackens pixels that nothing drew, before sprites and translucent surfaces, which blend over black there. It applies inside skybox views, portals, and split-screen views. The far clipping plane moves from 32768 to 131072 units so distant geometry isn't clipped into the void. From the other side Software only shows sky beyond the edges of the sky flat's sector, which the sky walls already give; claiming the plane there as well hid the buildings in the first prison map's skybox whenever the chase camera dipped below the ground. Sky planes also claim their extension past horizon lines, as Software extends them, so the skies above Green Hills Zone's horizons aren't black. Translucent 3D floors with the sky flat and Boom fake-flat sky conditions don't claim sky. When the chase camera is pushed underground (below the floor in front of a raised step), the screen columns Software leaves empty there are black too *(not seen on Xbox yet)*: Software treats a step whose top is above the screen as filling its columns, so VibeRant draws black along the line below the wall (or above an upper wall), meeting the wall's edge without overlapping it, instead of showing the level behind. It doesn't treat the line as a closed door as well, which an earlier version did: looking up or down, VibeRant's true-perspective view reaches past the wall's far edge where Software's sheared view stops, and with nothing drawn behind such walls, black stood above Green Hills Zone's blocks instead of their sky *(fix works on Xbox)*. Whether a step's top is above the screen is judged with Software's own view: its freelook tilt (which doesn't scale with the field of view), its 80° pitch limit, and the wider view it renders when the screen is tilted. An earlier version scaled the tilt by the field of view and ignored the other two, so at a field of view other than 90° or with screen tilting it blackened sky that Software shows, as in Green Hills Zone with the camera low beside a raised block.
- **Walls of sectors whose ceiling is below their floor** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. Ice Paradise is bordered by a strip of sky sectors whose ceiling (−256) is below their floor (680), and the strip's outer walls carry a placeholder texture that isn't meant to be seen. Software draws a column of a wall only where the wall's top is above its bottom, so it draws nothing there and the sky shows. Legacy GL draws the wall whichever way up it is, so a brown "Why?" wall 936 units tall stood behind the track, flickering against the sky drawn in the same plane. VibeRant now draws only the part of a one-sided wall whose top is above its bottom: nothing of a wall that is upside down from end to end, and the triangle up to the crossing where slopes make the top and the bottom cross. Legacy GL is unchanged. `upright_wall` tests it.
- **Wall and sprite brightness by distance** *(works on Xbox)*. Software lights floors and ceilings by their distance and walls and sprites by their size on screen, which works out as if they stood at half their distance, so in a dim sector a wall or sprite is brighter than the floor under it. VibeRant D3D lit everything with the floors' curve: sprites and walls in dim sectors came out several light levels darker than Software's, and in a room with a short colored fade the kart was almost fully faded where Software shows it lit. It now takes every surface's light level from Software's own two tables, including their steps, so floors and ceilings also change slightly: up to four levels darker at some sector light levels, and brighter within 16 units of the camera. The OpenGL renderer on other platforms keeps the old curve.
- **Brightness steps of walls and slopes** *(works on Linux with VibeRant Vulkan; untested on Xbox)*. A map's light contrast brightens the walls and slopes that face its light and darkens those that face away. Software has 32 light levels and rounds that change to whole levels. Legacy GL has a change eight times finer, for its smooth lighting. VibeRant lights every surface by Software's 32 levels (see **Wall and sprite brightness by distance**), so there the fine change was no smoother, only rounded another way: about half of all such walls and slopes came out one level brighter or darker than Software's. A sector light of 192 with a change of -1 fell a whole level, and with +7 it stayed where it was. With shaders on, VibeRant now adds Software's own rounded change, and leaves the darkest and the brightest level alone as Software does. It also leaves the change out where Software does: on an upper, lower, or one-sided wall under a 3D floor's light that has a colormap, and on a middle texture or a 3D floor's side under a fog colormap or in fog. The finer change was often lost in the rounding there, so those walls used to match by accident. With shaders off, and in the OpenGL renderer on other platforms, light isn't cut into those levels, and the fine change stays. Sprites' light contrast is a separate approximation and hasn't changed.
- **Translucent wall textures at full brightness** *(works on Xbox)*. Software draws a translucent wall texture on a two-sided line at full brightness, with only the sector's tint, unless the sector's colormap is fog, and does the same for the translucent side of a 3D floor (water, glass) seen from a sector with no 3D floors of its own. Legacy GL lit them like opaque walls, so in a dim or tinted sector a window darkened with distance and changed the color of what was behind it along its length. Every hardware renderer now uses Software's rule.
- **Drop shadow strength** *(works on Xbox)*. Software darkens the floor under an object by its shadow color, a mid gray by default, wherever the round shadow image has a pixel, and ignores that image's own color and the sector's tint. Legacy GL subtracted the image's own color, a much darker gray, so its shadows were less than half as strong: a faint darkening where Software's is nearly black. Every hardware renderer now subtracts the shadow color (or adds it, for a white shadow).
- **Wall textures above a sky ceiling** *(works on Xbox)*. Where both sides of a line have sky ceilings, Software shows the line's masked wall texture against the sky even above the ceilings' height, as it has nothing to clip it with. Legacy GL's invisible sky ceilings are drawn first and hid that part, so a tree line taller than its sky ceiling was cut off flat. Such textures are now drawn before the sky surfaces on every hardware renderer; nearer walls still cover them. It needs Batching on (the default), and a translucent texture in that position is still cut.
- **Semibright sprites** *(works on Xbox)*. Item capsules, dash rings, and a few pickups are semibright: Software keeps the sector's light for them but treats them as nearer than they are, which leaves them fairly dark in a dim sector. Legacy GL raised their light level instead, so in dim and dark areas they stood out almost fullbright (at sector light 64, the brightest quarter of the light table where Software uses the darkest third). VibeRant D3D now follows Software's rule when shaders are on. Bright areas look the same as before, and the OpenGL renderer on other platforms keeps the raised level.
- **Wall textures between two skies** *(works on Xbox)*. Legacy GL clips a two-sided line's middle texture to the opening between its two sectors. Software has no such clip where both ceilings are sky (it draws no upper wall there, so nothing cuts the texture's top), or at the bottom where both floors are sky. Municipal Meadow's skybox ends in lines whose far side is a zero-height sky sector, so the row of pine trees and the distant skyline on them were clipped to nothing; they now show, on every platform.
- **Level darkening** *(works on Xbox)*. Software dims the level's walls, floors, and ceilings (bright areas more than dark ones) while Shrink is active, when a Battle power-up is picked up, during the Duel margin boost, and for the end-of-race camera, and leaves sprites bright. Legacy GL never applied it. Every hardware renderer now dims the same surfaces by the same amount; at Battle's strength a local render of Municipal Meadow matches Software's brightness to within a few levels out of 255. At full strength (the Duel margin boost) Software's floor is black where hardware's is very dark, and a strip of grass and railing stayed bright in Software but not in hardware; neither difference has been traced. The `debugrender_contrast` cheat now affects these surfaces too, and fog volumes no longer apply the dimming a second time.
- **Fog-style lines** *(works on Xbox; no base-game map has one)*. A two-sided line with the fog render style (or the old special 909) is meant to tint what is behind it. Legacy GL drew its middle texture as an ordinary wall instead. Every hardware renderer now draws no texture there and tints the scene behind the texture's rectangle, the way the sides of fog volumes are drawn, using the front sector's light and colormap. Software's own code for these lines mixes up world heights and screen positions, so its result is inconsistent and isn't copied exactly; it also shapes the fog by the texture's opaque columns, where this fills the whole rectangle.
- **Software perspective's shift** *(works on Xbox, including two-player)*. With Software perspective on, Legacy GL moves the picture up or down instead of pitching the camera, as Software does, but it moved it by an amount that is only right for a 16:10 picture. At 16:9 the picture sat a tenth of the shift lower than Software's, about 25 pixels at 1080p with the chase camera's usual pitch, and in two-player split-screen over half of it. Every hardware renderer now shifts by Software's amount for the view's shape.
- **Two-player view width** *(works on Xbox)*. In two-player split-screen Software widens each view to 1.7 times the single-player width; VibeRant D3D used 1.6, so it showed about 6% less in both directions at the same field of view. It now uses 1.7, and the visibility clipper covers the wider view on every hardware renderer.
- **Translucent overlay sprites** *(works on Xbox; no base-game object is known to use the combination)*. Software has no separate blend table for the overlay style, so an overlay sprite, wall, or 3D floor that is also translucent blends with what is behind it like ordinary translucency. Legacy GL kept its cut-out blend for those, which ignores the background, so their partly transparent pixels darkened instead of showing it. Every hardware renderer now blends them as translucent; opaque overlay surfaces are unchanged.
- **`RF_SHADOWDRAW` sprites** *(works on Xbox, apart from the tilt on slopes; nothing in the base game sets the flag)*. Software draws a sprite with this flag as a ground shadow: as wide as the sprite itself, as tall as the object's radius allows, flattened according to how high the camera is above the ground, and sheared on slopes. Legacy GL drew it as an ordinary upright sprite. Every hardware renderer now applies the same size, flattening, slope shear, and position (the first version sized the width by the radius too, which drew the renderer test map's posts 1.5 times too wide). On a slope the shape tilts by the slope's real angle here, where Software's tilt depends on the resolution and the distance and is nearly flat at 1080p; paper sprites, floor sprites, and 3D models are unaffected. Hardware's true perspective means the shape isn't pixel-identical to Software's.
- **`colormapfadesprites`** *(works on Xbox; no base-game map sets it)*. In a sector whose colormap has this setting, Software dims the part of a fullbright sprite that lies below a 3D floor's lighting boundary by that boundary's light level and by distance, without the colormap's tint; whole sprites and the part above the boundary stay fullbright. Legacy GL kept every part fullbright. Every hardware renderer now matches Software, and goes no further than it does.

### Intended differences from Software

VibeRant D3D is meant to look like Software except in the ways below, which are kept on purpose. They describe how the renderer is, not changes waiting to be made, so they carry no status marker.

- **True perspective.** Looking up or down pitches the camera, so vertical lines converge as through a real lens, and sprites turn to face the pitched camera (**Sprite Billboarding**). Software shifts the picture up or down instead and keeps vertical lines upright. **Software Perspective** in the VibeRant D3D options gives Software's shift.
- **Water.** Seen from above, a rippling water surface also distorts the level under it, where Software distorts only the background (see **Water**).
- **Drop shadows.** A drop shadow lies on the floor as a real circle. Software draws an upright ellipse on the screen, so here a shadow away from the middle of the screen looks slightly turned. Its strength is Software's (see **Drop shadow strength**).
- **Sprites against the level.** Each pixel of a sprite is hidden by whatever level geometry is nearer, so a sprite that pokes into a wall or floor is cut where it enters. Software decides from where the sprite stands and can show such a sprite whole. Only springs follow Software's rule (see **Springs**), and the floor under a floor sprite doesn't hide it (see **Floor sprites under the floor**).
- **Shadow-drawn sprites on slopes.** A `RF_SHADOWDRAW` sprite tilts by the slope's real angle; Software's tilt depends on the resolution and the distance (see **`RF_SHADOWDRAW` sprites**).
- **Camera underground.** When the chase camera is pushed below the floor in front of a raised step, Software draws the step's wall, leaves the screen under it black, and draws nothing that lies behind the step. VibeRant D3D draws the same black under the wall but still draws what lies behind the step. Software's shifted view never reaches past the top of such a wall, so hiding what is behind it costs nothing there; a pitched camera sees over the wall's far edge, and hiding it left black shapes where the sky belongs (see **Black void**).
- **Translucent colors.** With Palette Rendering on, a see-through surface is blended in full color and the finished pixel then takes the nearest palette color. Software looks the result up in the game's translucency tables (`TRANS10` to `TRANS90`). Both stay within the palette and are on average equally close to the true blend, but they pick a different palette color for 10 to 14% of color pairs, and more often the fainter the surface is.
- **Extras Software doesn't have.** **3D Models**, **Texture Filter** modes other than Nearest, and anisotropic filtering are options.
- **Palette Rendering off.** Colors are no longer limited to the palette: lighting is smooth, translucent surfaces show true blends, palette flashes are overlays, and level fades darken or whiten the picture evenly. Software's fade table is Mega Drive style instead: red drops out first, then green, then blue (see **Palette fades and wipes**).
- **Shaders off.** Fog volumes use one neutral approximation that can differ from Software in color, brightness, and edges (see **Fog approximation**).

### Fixes to Legacy GL

- **Untextured steps** *(untested on Xbox)*. Where a floor steps up, or a ceiling steps down, and the wall between has no texture, the farther floor's (or ceiling's) flat continues across the step with that flat's lighting, as Software lets it bleed, instead of leaving a gap that shows what is behind. Neighboring sloped floors in Green Hills Zone meet a few thousandths of a unit apart, which showed as thin crack lines across the grass. It applies only while that flat faces the camera; sky flats and polyobjects are unchanged.
- **Textures also used as brightmaps** *(works on Xbox)*. A texture that is another texture's brightmap could lose its own image when a surface used it. The fullbright colour textures `~B000` to `~B255` all use plain white `~000` as their brightmap; once one had been drawn, Legacy GL treated `~000` as a brightmap for the rest of the session, so a floor or wall textured with `~000` showed the previous surface's texture, or black. Test Run's bowl showed black and grey wedges on its white floor after the map's `~B000` ceilings had been seen. Every hardware renderer now sets a texture's role each time it is used, on every platform.
- **Seams between floor polygons** *(works on Xbox)*. Legacy GL cut each subsector's floor and ceiling polygon out of the map's BSP lines with float maths and merged points closer than 0.45 units, so where several BSP lines cross within that distance, neighboring polygons got different corners and the void showed between them. Test Run's bowl showed four black lines to its center, where the wedges of its floor meet. A polygon now comes from its subsector's own outline in the map's GL nodes, which neighbors share corner for corner, on every platform. Outlines that are dented or not closed keep the old cut: 10 of the 556,203 subsectors in the shipped maps, besides 451 with too few edges for an outline.
- **Floors beside a moved polyobject** *(works on Linux with VibeRant Vulkan and Legacy GL; untested on Xbox)*. The outlines above were read after each polyobject had gone to its spawn spot, so a floor polygon with a polyobject's line on its edge reached from where the map has the polyobject to where it now is. In Balloon Park, the dark gray floor of the sliding elephant blocks' control sector stretched across the funnel behind them and hid it, and the blocks' own peach floor and ceiling stayed where the blocks started. The polygons are now built with every polyobject's vertices where the map has them, as the node builder saw them, on every platform; this also holds when the renderer is changed in mid-level.
- **Hidden areas behind horizon lines** *(works on Xbox)*. Walking the map's BSP tree, Legacy GL checks whether nearer walls hide a branch only for the branch on the far side of each split, and always draws the one on the camera's side. Software visits those too but draws nothing in a hidden one, because all its lines are clipped; Legacy GL draws its floors and ceilings whole and counts on the nearer walls to cover them. A horizon line (special 41) draws no wall, so the ceiling of a 3D-floor control sector behind Green Hills Zone's horizon showed as a small dark-green triangle in the sky. UWP now skips a hidden branch on the camera's side as well. It also draws slightly fewer map sections: 385 instead of 411 in that Green Hills view.
- **Walls cut by solid 3D floors** *(untested on Xbox)*. Software leaves the part of an upper, lower, or one-sided wall inside a solid 3D floor's thickness undrawn and draws nothing behind it, so through a see-through 3D floor, such as Green Hills Zone's tube grates, that part is black (or the HOM flash). VibeRant D3D now fills it black too, instead of showing the level behind the wall, such as the sky or the grass outside the tube; the 3D floor and anything nearer still draw in front.
- **Lower-unpegged walls on slopes** *(untested on Xbox)*. A one-sided wall whose texture is lower unpegged now has the texture's bottom on its floor along the floor's slope, as in Software, on every platform; Legacy GL measured it from the sector's unsloped floor height, so Green Hills Zone's pit walls between the tubes showed the grass at the top of their texture at their foot instead of brick.
- **Slope shading on 3D floors and ceilings** *(works on Linux with VibeRant Vulkan and Legacy GL; untested on Xbox)*. A map's light contrast brightens slopes that face its light and darkens those that face away. Software turns that around for a surface that faces down, a sloped ceiling or the underside of a sloped 3D floor, because a slope's direction is worked out as for a floor. Legacy GL turned it around for both planes of a 3D floor and for no ceiling, so the top of a sloped 3D floor was dark where Software has it light and light where Software has it dark, and a sloped ceiling likewise. Balloon Park's funnel is made of 3D floor tops under a contrast of 48, three times the usual: its far side was navy instead of light blue. Every hardware renderer now follows Software, including for the flat that continues across an untextured step.
- **Floor sprites under the floor** *(works on Linux with VibeRant Vulkan and Legacy GL; untested on Xbox)*. A floor sprite, such as a sneaker panel, lies on one plane: its own height, or the slope its object stands on. Software draws it after every floor and never hides it behind one. Legacy GL tests each of its pixels against the level's depth, so wherever the floor rises over that plane the sprite was hidden. Robotnik Coaster's track is a different slope every few units, so one of its three green sneaker panels wasn't drawn at all on the way up to it, and another was cut down to a strip. Every hardware renderer now measures how far the floor under the sprite rises over it, at 25 points and up to a step's height, and gives the sprite the depth it would have that much higher, without moving its picture from where Software draws it. A floor sprite on a floor that doesn't rise over it is drawn exactly as before. What stands on such a sprite can lose up to that rise from its foot where the two overlap.
- **Wall light slices** *(works on Xbox, including split-screen)*. UWP clips each lighting band to its original wall and splits crossing slopes, preserving UVs, lighting, alpha, and solid-floor holes. This removes inverted slices that covered Water Palace scenery with brown wall pixels, without new GPU resources or copies.
- **Missing floors and ceilings** *(works on Xbox)*. BSP cuts send unsplit polygons to their actual side, and a closed GL-seg loop supplies a fallback for subsectors missing a polygon. This fixes reported holes on Green Hills Zone and Storm Rig on every platform; some inherited oversized subsector polygons remain possible.
- **Sprite-textured models** *(works on Xbox, including after video changes)*. Every platform prepares a model's selected sprite patch before reading hardware data and compares sprite dimensions when refitting UVs, preventing crashes with models such as item boxes after video changes.
- **Title background lighting** *(works on Xbox)*. Preparing neighboring 3D-floor lighting before use prevents a briefly lit title-map background during fade-in on every platform.
- **First frame after a map load** *(works on Xbox)*. View interpolation stays off after a reset until a frame of the new map is drawn, on every platform. A slow load used to run tics without drawing, so the first frame blended from the previous map's last view: after a race, EXIT GAME's fade-in showed only sky in hardware renderers and a wrong view in Software.
- **Fill transparency** *(works on Xbox)*. Every hardware renderer honors fill translucency and HUD fades, including the spectator Watching underline over the finish-grade icon. Opaque fullscreen fills retain the clear shortcut; translucent fills blend over the full surface.
- **Polyobject ripples** *(works on Xbox)*. Moving floors and ceilings use their control sector's ripple flag, including translucent planes, on every platform. Regular and polyobject planes honor Reduce VFX when selecting ripples.
- **Raw pictures** *(untested on Xbox)*. Every platform supports opaque intensity/grayscale and RGB24 pictures alongside palette, intensity/alpha, and RGBA modes, including nearest-neighbor resizing. Conversion validates headers, dimensions, modes, and lengths, ignores trailing bytes, and prevents RGBA destination overruns.

### Settings

- **Advanced menu** *(works on Xbox; the new wording is untested there)*. The renderer list says **VibeRant D3D**. Options → Video → Advanced describes it as a Direct3D 12 port of Legacy GL with 3D models, true perspective, and high parity with Software, and asks for visual bugs to be reported to GitHub.com/ZebulanStanphill/RingRacers, the engine fork (it said "more parity" and named this repository before). Switching to it shows no confirmation or loading warning, and its **VibeRant D3D Options...** section has no blank rows.
- **Software saved as the renderer** *(works on Xbox)*. The game starts in Software when Software is the saved renderer. VibeRant D3D is the default, so startup queued a switch to it before the saved setting was read, and reading Software didn't cancel that switch: the game ran VibeRant D3D with the menu showing Software until the option was changed and changed back. The same stale switch was possible on every platform when the setting was changed and restored before the next frame, and is dropped there too.
- **Palette control** *(works on Xbox)*. `gr_paletterendering` defaults to On and requires Shaders on.
- **Better transparency ordering** *(works on Xbox)*. On every hardware-renderer platform, blended sprites, models, linkdraw attachments, and always-on-top sprites are inserted into the transparent surface pass using overlap, depth, and plane-side checks, instead of being drawn in a separate pass afterwards. It adds per-view CPU sorting and storage without scene copies, preserves opaque depth drawing and water-capture runs, and works with Shaders on or off; proxy model bounds, unsplit face crossings, cyclic intersections, and triangles within translucent models limit accuracy. This was the saved option `gr_bettertransparency`, Off by default. In a 16-bot race on Chemical Facility on Xbox it cost about 0.2 ms more sorting per frame, with the whole 3D view at 7.0 ms either way, so it is now always on and the option and its menu row are gone, along with the code only Off used (Legacy GL's delayed z-buffer pass for linkdraw sprites). A `gr_bettertransparency` line left in an old `ringconfig.cfg` is ignored. Under Wine, VibeRant D3D and Legacy GL on OpenGL both draw Chemical Facility's start with it; one Legacy GL run out of seven had a black 3D view in its screenshot, which didn't happen again in 42 further frames and isn't explained.
- **Batching** *(works on Xbox)*. `gr_batching` defaults to On, resets at launch, and appears last in VibeRant D3D's options, as the one an average player needs least.
- **Texture Filter** *(untested on Xbox)*. VibeRant D3D's options show **Texture Filter** (`gr_filtermode`: Nearest, Bilinear, Trilinear, Linear_Nearest, Nearest_Linear, Nearest_Mipmap) where **Texture Quality** was; that setting only chooses Legacy GL's OpenGL texture format, while Direct3D 12 always uses 32-bit textures. A new mode applies at once, and **Anisotropic** takes effect with Bilinear, Trilinear, Nearest_Linear, and Nearest_Mipmap, which filter distant texels.
- **Screen effects** *(works on Xbox)*. Options → Video → **Screen Effect**'s SalCRT and SalCRT Sharp apply in VibeRant D3D as a last pass over the frame, after Palette Rendering; screenshots and recordings stay plain. The game's own CRT shaders are read from its shader data and translated to Direct3D when first chosen; if that fails, the log says `screen effect ... failed:` with the reason and the frame is shown without the effect. Nearest and Sharp Bilinear only choose how Software scales its picture up, which VibeRant doesn't need.
- **Fullscreen row on Xbox** *(works on Xbox; other UWP devices untested)*. Options → Video no longer shows **Fullscreen** on an Xbox console, where the app always fills the screen and the setting did nothing; Screen Scaling moves up into its place. The row is hidden only when Windows reports the Xbox device family, so PCs, tablets, and other devices that can run the UWP app keep it, as does every other platform. The `fullscreen` console variable is unchanged.
- **Screen Scaling** *(works on Xbox)*. Options → Video → **Screen Scaling**, under Fullscreen (or in its place on Xbox), places the game's frame on the screen in every renderer: **Fit** (the default, as before) scales it to fit, keeping its aspect ratio; **Integer** scales it by the largest whole number that fits; **1:1** shows it unscaled. Both of those center it with black around it, and fall back to Fit when the frame is bigger than the screen. VibeRant D3D then sizes its swap chain to the screen and draws the frame into place after the screen effect; if it can't, the log says `couldn't place the frame` and Fit is used from then on.

## Software renderer and GL2 RHI

- **ANGLE/OpenGL ES 2** *(works on Xbox)*. ANGLE runs the RHI and presents Software's frames through its Direct3D 11 device (VibeRant D3D presents with its own swap chain), replacing worleydl's desktop OpenGL/Mesa path. The GL2 RHI supports ES 2 contexts, GLSL ES 1.00, core framebuffer entry points, `glClearDepthf`, unsized texture formats, RGBA screenshot readback, and no `glReadBuffer`; `patches/sdl-angle.patch` builds SDL with EGL/ES 2.
- **Display** *(works on Xbox)*. libuwp supplies display size and refresh rate, while rendering uses ANGLE's surface size, which may be smaller than the HDMI mode. The window stays fullscreen, fixing the tiny loading screen.
- **Encore distortion** *(works on Xbox, including split-screen)*. Encore mirroring combines with underwater and heat distortion instead of replacing them in Software and Legacy GL on every platform.

## Network

- **Unreachable UDP routes** *(untested on Xbox)*. Host-unreachable and network-unreachable sends, including Winsock 10065, count as dropped packets on every platform. Existing retries and timeouts decide recovery; other unexpected send errors remain fatal.
- **Online loading** *(works on Xbox)*. UWP VibeRant clients send basic keepalives during geometry/resource loading and vanilla tic acknowledgments at most once per clock tic while connected in-game, excluding demos and savegame redownloads. This prevents loading-related delay kicks without changing server delay rules or the receive limit; a kick logs the last reported delay/limit and local simulated, received, and level tics.
- **Track title timing** *(works on Xbox)*. Pre-race titles start with a fresh clock after loading and retain upstream animation steps and HUD timer clamps. Online VibeRant clients animate the title in the normal HUD while simulation catches up; hosts, Software, offline play, and demos retain the pre-level animation.

## Files and startup

- **Data and logs** *(works on Xbox)*. Assets use `E:\ringracers`; config and saves use `E:\ringracers\ringracers`, ignoring `-home` and `RINGRACERSWADDIR`. The save folder exists before the writability check. The log uses `E:\ringracers\latest-log.txt` because the package directory is read-only.
- **Missing game data** *(untested on Xbox)*. When `bios.pk3` isn't in `E:\ringracers`, the error asks first whether the USB drive with the `ringracers` folder is connected, says the folder must be at the top of the drive and hold the v2.4 assets, and points to the README, before the list of drives the app can see.
- **Game data in internal storage** *(untested on Xbox)*. The game files in `E:\ringracers\data` that are read when tracks and characters load (about 300 MB) are copied to the app's own folder on the console's internal storage, which Windows deletes when the app is uninstalled, and loaded from there. That storage is a volume of about 3 GB shared by the data of every sideloaded app, so music, alternative music, and sound effects (about 430 MB) and staff ghosts (48 MB, read only for Time Attack staff ghosts) stay on the USB drive, and copies of them made by earlier builds, like any other file the game no longer keeps there, are deleted at startup. A launch that checks a file on the USB drive writes the copy as it reads the file, and keeps it only if the MD5 matches. Later launches load a copy without checking it again while its source keeps the size and last-write time it was copied from and the game expects the same MD5; otherwise the file loads from the USB drive and is checked and copied again. Staff ghosts are likewise checked once and then trusted while unchanged, from a small record of the check. Running out of space or failing to write stops copying for that launch without affecting the check. The log lists where each file loads from and why (`UWP: data:`), anything deleted, the internal storage's free space (for this app and on the drive) and size, which volume the internal storage, the install, and `E:\ringracers` are each on (serial number and NT path), and each file copied.
- **Sound effects in memory** *(untested on Xbox)*. `sounds.pk3` stays on the USB drive, so startup reads all of its sounds into memory at once (about 43 MB, in file order) instead of reading each from the drive the first time it plays, which could stall a race. Sounds are still decoded when first played, as before; sounds from other files, such as characters' voices and add-ons, load as before. The log reports how many sounds were read, their size, and the time it took.
- **Background file check** *(untested on Xbox)*. Main files load with expected MD5s while a below-normal-priority worker verifies contents in 1 MB reads; zip local headers wait until an entry is used. The check can no longer be skipped (B used to skip it, before startup got faster); startup waits before network setup if needed, and mismatches raise the usual error at the next loading step or final wait; logs record per-file time/speed, outcome, and wait.
- **Music and sound hashes** *(untested on Xbox)*. Files without expected MD5s hash their names rather than contents for duplicate detection. They are not transferred to netgames or recorded in replays.
- **Direct3D 12 launch check** *(works on Xbox)*. Launch requires a hardware adapter that creates a feature-level-11_0 Direct3D 12 device and command queue, excluding software adapters and Basic Render Driver. Failure shows a Dev Home Game-type pop-up, flushes logs, and exits; the launcher links `d3d12.lib`/`dxgi.lib`.
- **Earlier loading text** *(untested on Xbox)*. Graphics, fonts, and console initialize before map thumbnails/minimaps; **Loading maps...** redraws up to ten times a second, keeping the loading screen live.
- **Map cache** *(works on Xbox)*. Startup no longer inflates every map WAD (305 MB) and staff ghost (76 MB) to find each map's thumbnail and minimap and each ghost's time and name. `mapcache.bin` in the app's folder on internal storage keeps them between launches, keyed by each zip entry's path, CRC32, and sizes, so a new or changed game file or add-on is read as before and added. The first launch after an install or a data change builds the cache (about 17 MB). A save keeps only the entries in use, a file from another demo version or a damaged one is rebuilt, and a cache that can't be read or written is logged and skipped. Thumbnails still all load at startup, so menus are unchanged. A cache left in `E:\ringracers\ringracers` by earlier builds is deleted. The cache is read with one unbuffered read, and the log reports how long reading and saving it took and how many maps and ghosts came from it.
- **Header cache** *(untested on Xbox)*. Startup reads the first few bytes of thousands of textures and sprites to size them, each a separate seek and often a decompression; on Xbox that was about 8 s of a 13 s startup. Reads of up to 256 bytes from PK3 entries made during startup are kept in `lumpheaders.bin` in the app's folder on internal storage, keyed by each entry's path, CRC32, and sizes, and the read's offset and size, and answered from it on later launches with the same bytes. Only entries used are kept; after startup every read goes to the files as before. The log reports hits, misses, and how long reading and saving the cache took.
- **Lump lookups** *(startup works on Xbox; long names untested)*. On every platform, finding a lump by name in a file checks only the lumps whose stored name hash matches, from an index built when the file is added, instead of every lump in the file. Results are identical. On Xbox, these searches (mostly for HUD graphics) took about 4.5 s of a 26 s startup. Lookups by long name use the same index; sprite brightmaps look one up for every visible sprite every frame, which scanned every lump of every file for names that don't exist (0.8% of race time).
- **Folder lookups** *(untested on Xbox)*. On every platform, finding where a folder starts in a PK3 uses an index of the folder paths in each file, built when the file is added, instead of comparing every entry's path. Results are identical. On Xbox, looking up each map's staff ghost folder in every file took about 4 s of startup.
- **Texture lookups** *(untested on Xbox)*. On every platform, finding a texture by name uses an index of the loaded textures and a hashed cache of earlier answers instead of scanning both. Results are identical, including newer textures taking precedence over older ones with the same name. On Xbox, the brightmap definitions' lookups took about 5.5 s of startup.
- **Loading-to-intro transition** *(works on Xbox)*. The intro starts with the credits card instead of six blue tics, without changing timing. VibeRant D3D skips clear-only presentation before its first drawn frame, keeping the loading screen visible instead of flashing black.
- **Skipping the intro** *(untested on Xbox)*. A press skips an intro logo as soon as it's on screen, instead of being ignored for the first half second of each scene; the opening credits card, which couldn't be skipped at all, now skips to the disclaimer. The disclaimer still has to slide in and finish fading in its text before it can be dismissed. Controllers already connected at startup are opened while the game loads, rather than once the intro's first frames have been drawn.

## Performance

### Rendering

- **Level precaching** *(works on Xbox)*. Legacy GL warms walls, flats, brightmaps, FOF control sectors, existing models, and current player models/colors during loading, then repeats player warming after spawning and hooks. Dedicated servers, reloads, snapshots, and rewind skip it; sprite-textured models, future animation frames, later objects, and view-dependent remaps remain lazy, and Models must be enabled for model warming.
- **Rolled sprites** *(untested on Xbox)*. VibeRant D3D draws sprites tilted by roll (karts on slopes, spinning objects) from the unrotated sprite texture, with the pixel shader applying Software's exact integer rotation, instead of rotating each new angle on the CPU and uploading it as a new texture. Races on Xbox created 20-60 such textures a second (about 1.8% of 3D time rotating and 3% of race CPU creating them, plus hitches). Sizes, offsets, and cropping still come from the CPU, cached per frame and angle, so sorting and clipping are unchanged; brightmaps use the same mapping. Floor and paper sprites, linked sprites, custom sprite shaders, Shaders off, filtering other than nearest, mipmaps, and very large art keep CPU rotation. The perf log reports how many rolled sprites each path drew.
- **Batch sorting** *(untested on Xbox)*. On every platform, Legacy GL batches sort an index array by compact keys copied out once per frame, instead of comparing large polygon entries and their texture pointers on every comparison, which cost about 7% of 3D drawing time on Xbox. Sorting the keys themselves was tried first and doubled the sort time, since qsort moves whole elements. Ties fall back to submission order, so the order is total; polygons with different colors may draw in a different order than before, where the old comparison was inconsistent.
- **Horizon lines** *(untested on Xbox)*. VibeRant D3D remembers which parts of the map have a horizon line (special 41) instead of checking every edge of every floor, ceiling, and sky surface it draws for one, every frame, which took 4.6% of 3D time on Xbox. The record is rebuilt whenever a line becomes or stops being a horizon line, so the result is identical.
- **Drop shadows** *(untested on Xbox)*. On every platform, Legacy GL finds the `DSHADOW` lump once, and again only after a file is added, instead of searching for it by name for every shadow every frame.
- **Rotated flats** *(untested on Xbox)*. On every platform, Legacy GL computes a rotated floor or ceiling texture's cosine and sine once per plane instead of four times per vertex, with identical results.
- **3D floor light lists** *(untested on Xbox)*. UWP keeps a sector's 3D floor light list when its allocation is big enough instead of freeing and reallocating it, which happened every time a sector with moving 3D floors was prepared, because a list that came out shorter than counted never matched the count again. The contents are identical.
- **Device-removal checks** *(untested on Xbox)*. Upload rings read a removal flag set by failed calls or fences instead of making a kernel query on every allocation. A full device check still runs once per frame.
- **Video memory safeguard** *(untested on Xbox)*. Exceeding the local budget schedules a texture-cache flush for the next frame, at most once every five seconds. Model buffers remain, but reloading textures can hitch.
- **GL2 call reduction** *(works on Xbox)*. Every platform skips redundant state/texture/buffer binds, disables only enabled vertex arrays, caches uniform locations, changes sampler uniforms only when needed, and retains framebuffers. Colormap/lighttable textures upload only after changes and expire after 300 unused frames; palettes upload only when changed and the default colormap once, while UWP uses `GL_RED` with `EXT_texture_rg` where available to avoid ANGLE's luminance conversion.

### Software renderer

- **Planes and sorting** *(works on Xbox)*. Every platform clears only visible visplane columns, skips draw nodes outside a sprite's columns before reading them, and computes 3D-floor plane bounds once during sorting.
- **Columns** *(works on Xbox)*. Every platform leaves unused thick-side slots alone, copies wall-column data only for remapping, computes masked clipping limits once, and passes read-only column data directly to drawers. UWP also inlines `R_GetTextureNum`.
- **Screen tilting** *(works on Xbox)*. Every platform steps along source rows instead of rebuilding a full-screen pixel map, preserving float stepping, clipping, zoom, and mirrored sampling. Large views share work across Software workers.

### Game logic

- **Arithmetic and references** *(works on Xbox)*. UWP inlines `FixedMul`, release-build `P_SetTarget`, and `P_MobjWasRemoved`, preserving collision callback reference order and `PARANOIA` checks.
- **Subsector cache** *(works on Xbox; the larger cache is untested)*. UWP caches `R_PointInSubsector` results for 4096 recent points (2048 sets of two; 512 before, which answered only about 60% of lookups in races) and clears them when the BSP loads or is freed.
- **Lua userdata** *(works on Xbox)*. Every platform tracks pointers with Lua userdata, letting frees skip Lua when none exists.
- **State bookkeeping** *(works on Xbox)*. Every platform gives each `P_SetMobjState`/`P_SetPlayerMobjState` nesting depth its own table and clears only recorded states. Calls that remove an mobj balance the nesting count instead of making later calls look nested.
- **Interpolation list** *(works on Xbox)*. Every platform records each mobj's interpolation-list slot so removal needs no search.

### Frame pacing and threads

- **Pacing** *(skipped frames work on Xbox; the schedule is untested)*. On UWP the frame cap sleeps to a running schedule instead of padding every loop to a whole frame on its own. A quick frame right after a slow one (one that ran game tics) is drawn straight away until the schedule catches up, and more than four frames of debt (after a load, say) is dropped. Scenes faster than the cap still run at an even rate. On tracks below 60 FPS, the old padding left the game idle 5–12% of the time on Xbox. Frames skipped to catch up on simulation never sleep, Unlimited never sleeps, and V-Sync with a matching-refresh cap still sleeps, following worleydl's Xbox timing fix.
- **Thread pool** *(works on Xbox)*. The pool uses Xbox's allocated processor count, falling back to upstream's hardware count when no processors are marked.

## Diagnostics

- **Startup and performance logs** *(works on Xbox)*. Startup records graphics/device capabilities, surface size, shader compilation, first-frame steps, loading/asset times, and logging cost, memory budgets, CPU sets, and thread-pool size. Every five seconds `UWP perf:` reports FPS, frame/tic, and HUD/present times, draws/uploads/resources, mobj/collision/Lua activity, subsector-cache hits, main-thread CPUs, profiler pauses, and renderer/portal CPU and GPU costs.
- **Driver counters** *(works on Xbox)*. `UWP perf:   D3D12:` includes `per frame` constant updates (`root CBV ring`), `pipeline:`, `rings:`, `textures:`, `models`, `texture heaps:`, `palette:`, `screens:`, `water:`, `portals:`, and `present:` statistics. These identify pipeline creation, upload peaks/wraps/stalls, storage, lazy models/mips, screen/fog/water copies, and synchronization, including the swap chain's copy, latency-wait, `Present`, and failure counts.
- **ANGLE cost** *(works on Xbox)*. With the Software renderer, `UWP perf:   ANGLE GPU:` adds per-frame GPU time (timestamp queries on ANGLE's Direct3D 11 device) for the screen upload, 2D/upscale/ImGui, and total, with worst frame, idle until the next frame, and timed/not-ready/disjoint counts. Idle is not cost: the GPU reaches the end of the present only with the next frame's commands, so it's excluded from total. A stage the CPU feeds slowly reads as an upper bound. The profiler splits level samples by renderer (`Software: 3D view`, `Legacy GL: 3D view`), and `tools/profile-report.py` shows each phase's and renderer's share inside ANGLE (`libGLESv2.dll`/`libEGL.dll`); `perf-summary.py` averages the new line. On Xbox One X at 1920x1080, a Software race spends about 1.4 ms of GPU and 8% of its main-thread time in ANGLE, so a Direct3D 12 RHI for Software is deferred.
- **Spring probe** *(works on Xbox)*. `gr_springprobe` waits for the console to close, then logs one main-world view, excluding skybox/portal passes. `UWP spring probe camera:`, `UWP spring probe:`, `UWP spring entry:`, `UWP spring result:`, and `UWP spring probe end:` record camera/settings, sprite heights/quad/depth, wall/plane tests and cuts, remaining area, and piece limits without changing drawing.
- **Pixel history** *(untested on Xbox)*. `gr_surfaceprobe [x_percent y_percent]` defaults to `15 35` from the top-left and requires a level, hardware rendering, split-screen off, and Batching off; it captures after the console closes. `surface probe:` logs `begin`, changed-color `sample=` rows with source/texture/flags/shader/depth/alpha and up to eight vertices, and `end`; one 4 MB readback buffer holds up to 8,192 samples with 256 color-change reports and explicit overflow/omission counts, is released after the frame, and does no work while inactive. The requested frame stalls for readback and is unsuitable for benchmarking; see [Direct3D 12 diagnostics](https://github.com/ZebulanStanphill/RingRacers/blob/master/docs/d3d12-diagnostics.md) for row formats and timeout logs.
- **Screenshot camera position** *(untested on Xbox)*. Each screenshot taken in a level also logs `UWP screenshot camera:` with the file name, map, level time, renderer, the last drawn view's position, yaw, pitch, roll, FOV, and sector, so the view can be drawn again on a PC without holding still for the console. It's only logging; nothing else changes.
- **Frame, title, and fade traces** *(works on Xbox)*. `UWP frame:` records positions, camera, elapsed time, tics, interpolation, title timers, and copied/shown slot IDs (the swap chain's back buffer) during titles and level seconds 10–20, capped at 300 frames per window. `UWP: track title:` summarizes animation timing; `UWP fade:` records state/load/wipe/palette changes in ten-second, 200-event windows and caps title-map/light-fade samples at 20 each.
- **Memory and stalls** *(works on Xbox)*. Perf summaries include DXGI local budget/usage and tracked texture, buffer, ring, render-target, and swap chain storage. `GPU frame exceeded 250 ms` logs once, while abandoned fence waits log at most once per second with suppressed warnings counted.
- **GPU failure details** *(untested on Xbox)*. Device removal and the first GPU-wait timeout dump DRED breadcrumbs when available, with page-fault details on removal. Search for `GPU wait for <what> timed out after N ms; breadcrumbs:` and `DRED:`.
- **Profiler and crashes** *(works on Xbox)*. `src/sdl/i_uwpprofile.cpp` samples the main thread about 50 times a second from the start of startup, writing stacks/activity to `E:\ringracers\uwp-profile.txt`. Play is split into phases by activity; startup, menus and the title screen, a paused or loading level, intermission, voting, the podium, and cutscenes each form a phase of their own, which `tools/profile-report.py` reports separately from play. A vectored exception handler logs crashes and stacks because the app runtime bypasses the game's signal handler; it cannot catch stack-cookie termination.
- **Error dialog** *(works on Xbox)*. The short Xbox dialog contains the error plus visible drives and their `ringracers` folders, and saves the text to `E:\ringracers\error.txt`.
- **Frame capture and comparison.** `-shottics 70,350,700` with a replay (`-shotghost RR_GREENHILLS-sonic-Name` plays a staff ghost straight from `staffghosts.pk3`, which `-playdemo` can't) draws exactly one frame per tic without interpolation, saves a screenshot of the finished frame at each listed level time as `<MAP>_<tic>.png` in the game folder's `framecapture` (or `-shotdir`), and quits. While capturing, the unsynced random numbers and the clock-driven HUD animations depend on the level time alone, so two runs of the same replay give identical files with any renderer, on Linux and on Windows. `tests/frame-compare` runs a list of replays on two builds or renderers (native, or a Windows build under Wine) and reports, per frame, how many pixels differ and by how much, with side-by-side images and an HTML summary. Its baseline: VibeRant D3D against itself, 90 of 90 frames identical.
- **`-warp` and `-d3ddebug`: VibeRant on a machine without a GPU.** On a desktop build, `-warp` makes VibeRant D3D use Windows' WARP adapter and VibeRant Vulkan a CPU device (lavapipe), and `-d3ddebug` turns on the Direct3D 12 debug layer and copies its error messages to the log as `D3D12 debug ERROR` (with VibeRant Vulkan it means `-vkdebug`). They exist so that a CI runner can play the game with a renderer and have its errors reported; neither is in a menu, nothing changes without them, and UWP builds ignore them. See [docs/d3d12-diagnostics.md](docs/d3d12-diagnostics.md).
- **Automated map sweeps.** The Map sweep workflow, run on demand and nightly when `master` has moved, plays each of the 213 maps' staff ghost with Software, Legacy GL, and VibeRant Vulkan on Ubuntu hosted runners (Xvfb, Mesa llvmpipe and lavapipe, Vulkan validation on) and with VibeRant D3D on Windows (WARP, Direct3D debug layer on), takes five frames per map at 640x400 (320x200 or 1280x720 on request), and fails on a crash, a hang, a missing or wrongly sized frame, `I_Error`, a "not implemented" line, a fallback to Software, or a validation or debug layer error. Each renderer's frames are compared with its last complete sweep of `master` (a plain and a texel-edge-insensitive measure, before, after, and difference crops of the worst frames, and whether the runner image or driver changed); the frames of each sweep of `master` become the next baseline, and VibeRant Vulkan is compared with VibeRant D3D as information. The ghost list, sharding, comparer, and report generator are Python with unit tests (CTest `map_sweep`), and `AGENTS.md` asks for a sweep of any branch that changes rendering. See [tests/README.md](tests/README.md), "Automated map sweeps".
- **Tools.** `uwp/tools/` summarizes perf logs, resolves profile/crash addresses to functions, and annotates instructions with samples.

## Other fixes

- **Switching to Software after starting in a hardware renderer** *(not on Xbox, which always starts in Software; works on Linux)*. A game started in a hardware renderer (`-opengl`, `-d3d12`, `-vulkan`, or the Vulkan default) crashed when the renderer was changed to Software: the state Software's frames are shown with is made by its first frame, and the switch happens in the middle of a frame that began in the other renderer. The switch now makes that state. Upstream has the same crash after `-opengl`.
- **Quitting when asked by a signal** *(not on Xbox; works on Linux)*. Ctrl+C in the terminal the game was started from, `kill`, and the end of a desktop session ask the game to quit with a signal, and the game ran its whole shutdown from inside the signal handler, wherever the signal had interrupted it. When that was inside a memory allocation or a graphics driver call, the shutdown hung or crashed, and the frozen window stayed until the desktop offered to end it. The handler now only notes the request, and the game quits from its event loop, as it does when its window is closed. A second signal ends the process at once, for a game that isn't getting back to its event loop. Seen with Software and with VibeRant Vulkan, and upstream has the same handler. In a test that kept changing the window with Vulkan's validation layers on, three of four runs ended hung or crashed before, and none of four after. `quit_signal` tests the handler.
- **Options button slide** *(works on Xbox)*. Submenu title buttons start their slide once and finish at or after the final tic, preventing repeated bouncing when low frame rates skip a menu tic.
- **Console slide** *(works on Xbox)*. On every platform, opening and closing use elapsed time since the last movement, keeping the intended speed through skipped frames and stalls.
- **Controller ignored after loading** *(works on Xbox)*. Moving a stick or pressing buttons a lot during the loading screen could leave the controller dead for the whole session: the title screen reacted to a press, then every menu ignored it. The game's input queue holds 128 events and lost all of them when it filled, including the one that registers the controller, and nothing reads the queue while the game loads. A full queue now drops only its oldest event, and still registers or removes a controller when it does. The same loss was possible on every platform during any long load.
- **Duplicate controllers** *(works on Xbox)*. `uwp/patches/sdl-controller-duplicates.patch` stops each controller from appearing twice, and each press from counting twice, in Game mode.
- **Camera Position** *(untested on Xbox)*. Options → Video → **Camera Position...**, between Color Profile and Advanced, gives each of the four local players a **3rd Person** (the default) or **1st Person** view. It sets the game's own `chasecam`, `chasecam2`, `chasecam3`, and `chasecam4`, which had no menu entry and weren't saved; they are now saved in `ringconfig.cfg` and still take `on` and `off` in the console. The view is local, so netplay and replays are unaffected, and the menu is there on every platform. An unmodified game given the same config file starts in first person too; `chasecam on` in its console switches it back.
- **Title screen in first person** *(untested on Xbox)*. With a player set to 1st Person, going to the title screen crashed the game (`access violation` in `R_SetupFrame`): first person looks out of the player's kart, and the title screen's map has none. The title screen, and any other view of a player with no kart, now uses the ordinary camera. Upstream has the same crash after `chasecam off`; it mattered more here because Camera Position saves the setting. Fixed on every platform.
- **First-person view on slopes** *(works on Linux with VibeRant Vulkan and Software; untested on Xbox)*. In first person the view stayed level whatever the kart stood on, so on a steep slope, as in Marble Garden, it stared into the ground on the way up and over the track into the sky on the way down. Third person doesn't have this, because its camera sits behind the kart and looks at it. A first-person view now pitches with the ground under the kart: by the slope's angle in the direction the view faces, uphill and downhill alike, eased over a few tics (a quarter of the way each tic) so that a change of slope doesn't snap the view, and back to level in the air. Only the view changes: nothing of the game's state, a netgame, or a replay depends on it, and third person is pixel for pixel what it was. **Screen Tilting** (the sideways roll on inclines) is separate and unchanged.
- **First-person view after the finish** *(works on Xbox)*. In first person, the view keeps turning with the kart once the game takes over its steering after the finish line; it used to stay pointing where the player last steered while the kart drove on. The chase camera already followed the kart there, and first person now does the same on every platform, so netplay and replays are unaffected. The first version of this did nothing *(confirmed on Xbox)*: it sat in the chase camera's code, which doesn't run for a first-person view. The view's angle is now updated in the camera pass that runs every tic for every view *(checked under Wine with a script that makes the game steer the kart)*.

## Removed or disabled

- **Old hardware driver** *(untested on Xbox)*. The Direct3D 11 driver, Shader Model 4 built-ins/tests, and `gr_d3d12` Off/Once/On selector are removed; an old config line reports `Unknown command` once. A saved `renderer VibeRant D3D11` is rejected as an invalid value and keeps the VibeRant D3D default. The old sharing/shader probes no longer run, and VibeRant D3D replaces `r_opengl.c` only in builds with `SRB2_CONFIG_D3D12` (UWP by default).
